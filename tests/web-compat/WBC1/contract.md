# Pinned compatibility data ingestion

Implements the data half of the [compatibility contract](../WBC0/contract.md)
(`DR1`–`DR5`, `SR1`–`SR3`). Later compatibility work consumes this; it does not
re-read the datasets.

## Boundary

| Concern | Owner | Path |
| --- | --- | --- |
| Explicit generation, integrity, schema validation | Generator | `scripts/web-compat/{generate,snapshot-builder,json-schema}.mjs` |
| Generated bytes, license texts, notice, schema copies | Corpus | `test-corpora/web-compat/{pinned,schemas}` |
| Snapshot admission, record reads, support evaluation | Session | `crates/verter_session/src/compat/data` |

`compat::data` is private to `verter_session`, and its surface is
`pub(in crate::compat)`, so the sibling compatibility modules are its only
possible consumers. `CompatSnapshot` has private fields and one minting path,
`SnapshotState::resolve`. The current consumer population is empty: no code at
this head reads the snapshot outside this module's tests. The deletion set is
empty, since no compatibility reader existed to displace.

## Snapshot and offline behaviour

The session never opens a file or a socket here. A host supplies one of three
inputs, and each has a distinct outcome:

| Input | State | A support query answers |
| --- | --- | --- |
| Bytes passing every check below | `Ready` | Evidence from the records |
| Bytes failing any check | `Rejected(SnapshotRejection)` | `Unknown(SnapshotRejected)` |
| `ProvenAbsent` | `ProvenAbsent` | `Unknown(SnapshotAbsent)` |
| `NotSupplied` | `NeedInputs` | `Err(NeedSnapshotInput)` |

Admission verifies, in order: the format and version, the strict header shape,
the payload SHA-256, the `snapshot_id` derived from the ordered dataset
identities plus recipe and payload digests, and the caller's exact `SnapshotPin`.
It then checks record layout and counts and parses browser release data. Feature
records are not parsed until asked for, so one malformed record answers unknown
and leaves its neighbours untouched.

## Generation

```bash
node scripts/web-compat/generate.mjs            # regenerate from the official artifacts
node scripts/web-compat/generate.mjs --check    # regenerate in memory, compare bytes
node scripts/web-compat/generate.mjs --fixture  # regenerate the offline test fixture
```

Generation fetches only the artifacts the contract names, verifies each one's
digest before reading it, and checks each package's name, version and license
against its pin. Editing a generator file changes the recipe digest, and so
`snapshot_id`. After any such edit, regenerate and update `ADMITTED_SNAPSHOT_ID`
in `compat/data/snapshot.rs`; the suites fail until both agree.

## Schema validation

Records validate against the upstream schemas with a closed draft-07 subset that
throws on any keyword it does not implement. Failures are quarantined at the
narrowest level that keeps the rest truthful: one browser's statements, otherwise
the whole record. The quarantine names the instance path and keyword and is
counted in the header. Structural failures in browser release data stop
generation, because every answer depends on that data.

Each raw browser is validated as `{ browsers: { [id]: browser } }` against
the pinned `browsers.schema.json` before projection, including discarded fields
and the `engine` dependency on `engine_version`. Browser release status comes
from that schema; the generator additionally requires numeric release keys and
a nonempty release population for the session's exact-target representation.
The BCD `schema_digest` is SHA-256 of canonical JSON mapping both schema filenames
to their raw-byte SHA-256 labels. This binds both schemas without changing the
strict generated header shape or weakening the Rust reader. Regeneration changes
the admitted snapshot pin; old snapshots remain unpinned.

The pinned BCD release has 75 browser statements using `version_removed: false`,
which its own published schema forbids. They answer
`Unknown(SchemaMismatch)` for that browser; they are not repaired, because
choosing a meaning for the value would be a guess.

## Support evaluation

`SupportVerdict` is `Supported { since }`, `Conditional { kinds }`, `Unsupported`
or `Unknown(reason)`. The condition kinds are partial, flagged, prefixed and
aliased, and the exact limits, flag, prefix or name sit on the retained
statements. Each statement's interval is evaluated before its conditions:

| Upstream value | At a target |
| --- | --- |
| `version_added: "10"` | Before 10: outside. From 10: inside |
| `version_added: "≤37"` | From 37: inside. Below 37: indeterminate |
| `version_added: "preview"` | Beta, nightly or planned: indeterminate. Other releases: outside |
| `version_added: true` | Indeterminate, unless a definite removal already excludes it |
| `version_added: null` | Indeterminate |
| `version_added: false` | Explicit negative |
| `version_removed: "20"` | From 20: outside (exclusive upper bound) |
| `version_removed: "≤20"` | From 20: outside. Below 20: indeterminate |
| `version_removed: true` | Indeterminate once added |
| `version_removed: "preview"` | Beta, nightly or planned: indeterminate. Other releases: not removed |

An in-interval unconditional statement with a known addition answers `Supported`.
Otherwise any in-interval conditions answer `Conditional`, any indeterminate
statement answers `Unknown(Indeterminate)`, and all-outside answers `Unsupported`.
Every statement for the family stays on the answer, applicable or not. Flags carry
exactly the data's `type`, `name` and optional `value_to_set`; default-enabled
state has no field because the data does not supply it.

Target checks precede the record: a family or release absent from the data answers
unknown, even for a record that would otherwise cover it. `BrowserTarget::exact`
accepts only one dotted-numeric version, so a range, bound or tag cannot become a
target.

## Baseline

`baseline` on an answer is computed after the verdict and cannot reach it. A
widely available feature with an unsupported, flagged or partial record answers
from that record. A web-features id whose mapping is missing is
`WebFeatureMembers::NoCompatMapping`, and a mapped key the pinned BCD lacks answers
`Unknown(FeatureAbsent)`; the BCD and web-features releases differ, so such keys
exist in the admitted data.

## Browserslist vocabulary

`BrowserslistQueryForm` is closed, and `admission` is an exhaustive match.

| Standing | Forms |
| --- | --- |
| Admitted | Exact version, range, comparison, last N (browser/major) versions, `firefox esr`, unreleased (browser) versions, `since`, composition |
| Usage statistic not carried | `defaults`, global usage, `cover` |
| Regional statistic not carried | Regional usage |
| Dead list not carried | `dead` |
| Clock dependent | `last N years` |
| caniuse not admitted | `supports` |
| Node release schedule not carried | `node`, `current node`, `maintained node versions` |
| Electron mapping not carried | `electron` |
| Resolved by the project model | `extends` |

`browserslist_family` maps Browserslist family names to dataset browser ids. A
name with no dataset family returns `None`. Parsing query text and expanding
targets are not implemented here.

## Permissions, uncertainty and migration

- **Permissions:** static and read-only. No execution and no network in any query;
  generation is a separate, explicit command.
- **Evidence class:** a data-backed static prediction, never an observed browser
  behaviour.
- **Uncertainty:** the verdicts above. `Unknown` never coerces to supported or
  unsupported.
- **Dataset upgrade:** change the pins, regenerate, update
  `ADMITTED_SNAPSHOT_ID`, and review the regenerated corpus diff. A new snapshot
  identity changes snapshot-derived answers only. Earlier snapshots are rejected
  as unpinned rather than read.

No public operation exists yet, so no VIM/DX exposure row, host receipt or
DOC1-tested example is registered here. Those obligations, including surfacing the
exact data versions that `SnapshotIdentity` carries, stay with the public delivery
named in the compatibility contract.
