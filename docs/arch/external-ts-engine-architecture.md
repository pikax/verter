# External TypeScript Engine Architecture (LSP / TSC)

**Status:** This is the active architecture contract for how Verter drives the external TypeScript engine. The architecture stands or falls on the falsifiable invariants and the Block-0 conformance fixtures in §3/§6 — never on external agreement.
**Evidence basis:** The design is grounded in a source-verified investigation of the reference engines (vize/corsa-bind, Volar, golar, typescript-go issue #2824 + PRs #711/#2620) and is validated against the Block-0 `--api` capability fixtures, which are reproducible in-repo.
**Scope:** This document governs ONLY how Verter drives the **external** TypeScript engine (tsserver / the TS JS language service for TS<7; tsgo/"Corsa" for TS≥7) to type-check generated **carrier** files and answer IDE queries on them. Verter's own semantic type-resolution engine (`SemanticGraphStore`/`ProjectSemanticDispatch`, the 5 query modes) and the `typeinfo`/component-meta feature are **explicitly out of scope** — they never call tsserver/tsgo and the LSP/TSC path never routes through them.

**FRAMEWORK-NEUTRAL by construction (read first).** This architecture keys off the **carrier** (a generated, valid TSX/TS surface) and its **source carrier file**, NOT off `.vue` specifically. Every part of the design — the §2.1 contract, the carrier store, the FS/LSP overlay, ownership/discovery, `.x`→companion redirection, both engines, the TSC path, the WASM path — is framework-agnostic. The **only** framework-specific pieces are: (i) the **carrier source extension** and its redirection specifier (`.vue`, `.svelte`, future `.astro`), and (ii) the **SFC→carrier codegen** itself (the per-framework adapter). Those live behind Verter's **Framework Adapter Substrate** (`/framework-adapters`): each adapter produces the carrier for its component format, and the **companion naming** is owned by the per-adapter `VirtualFileNaming` descriptor. The **gate-proven** naming (§2.2, GATE 5) splits by how the engine reaches the surface: the bare-import resolution target is the **declaration carrier** `{name}.d.vue.ts` / `{name}.d.svelte.ts` (extension-MIDDLE, the path tsgo's basename-extension probe reaches FIRST — `.d.<ext>.ts` wins over `.<ext>.tsx` — path-collision-free against a *different* `.svelte.ts`/`.svelte.js` rune-module extension, though the carrier path sits in the USER namespace, so a real same-path file or a same-stem rune is a resolution conflict Verter detects and FAILS CLOSED, §2.2 Carrier-path conflict model); the `{name}.vue.tsx` / `{name}.svelte.tsx` **component IDE carrier** is the self-diagnostics surface, not the bare-import target; the **redirect-reached `.ts` public-API carrier** — never bare-probed — uses the Verter-reserved `.verter.` infix `{name}.vue.verter.ts` / `{name}.svelte.verter.ts` so it cannot alias a real rune module. **Vue and Svelte are the first two adapters** (a Svelte compiler is being built in Verter now); this doc must read framework-neutral with Vue/Svelte as concrete instances. Where a token like `.vue` appears below it is an **example of the carrier source extension**, read it as "`.vue`/`.svelte`/…". This aligns with the Carrier IDE TS Surface Principle (explicitly Vue AND Svelte): the script block(s) + supported template/markup expressions of every carrier-bearing format lower into ONE generated TS/JSX surface.

**Two distinct surfaces under "LSP / TSC" (do not conflate — see §2.4):** the interactive **LSP** surface (an editor session driving tsserver's language service or tsgo's `--api`/LSP, or the in-context TS JS language service in WASM — §2.11) and the batch **TSC** surface (a `vue-tsc`/`svelte-check`-equivalent whole-project typecheck). They do **not** share a backend on TS<7: **a tsserver language-service plugin does NOT load for the `tsc` command line** (it affects editing only). The TSC path therefore has its own design (§2.4) and is a first-class deliverable, not an afterthought of the plugin.

## 1. Context & problem

Verter compiles each component SFC (`.vue`, `.svelte`, … — via the per-framework adapter's `CompileTarget::IDE` codegen) into a real, valid TSX **carrier** file that mirrors the script block(s) + supported template/markup expressions, with a token-precise `CodeTransform` source-map back to the source carrier file. An external TypeScript engine type-checks that carrier; results are mapped back through `ProviderPositionMapper`. Everything below is framework-neutral (per the header); `.vue` tokens are example carrier-source extensions.

Two problems, **one root cause:**

- **Correctness:** the engine places the carrier in a **config-less inferred project** (tsserver gets hardcoded `compilerOptionsForInferredProjects`, `tsserver/ipc.rs:738-761,934-947`; tsgo gets only `rootUri` in `initialize`, no project association, `tsgo/ipc.rs:1466-1481`). So the real `tsconfig.json` — `paths`, `baseUrl`, `lib`, `types`, `jsx`, `moduleResolution`, project references — never applies to the carrier → false `TS2307` and a class of wrong diagnostics. An identical *on-disk* file resolves fine.
- **Performance:** the fastest reference (vize) is ~20–84× faster than `vue-tsc`. vize is **not** in-process magic — it drives a stock user-provided tsgo as a subprocess over msgpack stdio (`ubugeeei-prod/corsa-bind`, no fork/patch). Its speed comes from (a) **rooting its virtual docs in the real workspace tsconfig** so they are real project members, (b) **one persistent project-Program reused** across the whole graph (keyed by tsconfig), (c) lean transport, (d) MT + targeted queries. Verter already runs one persistent engine per session, so spawn cost is *not* the gap.

**The fix has two parts, not one.** (1) The carrier must be made a member of the real configured project — but membership is **injected, not inherited**: a `.vue` (or its carrier) is *not* a configured-project member merely because it sits under the tsconfig's directory. TypeScript's default `include` is `**/*` **filtered to known extensions** (`.ts`/`.tsx`/`.d.ts`, `.js`/`.jsx` iff `allowJs`, plus declared `extraFileExtensions`); an explicit `include: ["src/**/*.ts"]` or a `files` array excludes `.vue` entirely. So each engine must be *told* the carrier is a member, by a **different mechanism**: tsserver via `extraFileExtensions` + `getExternalFiles` on the language-service plugin; tsgo via the `--api` **FS overlay + `open_project`** (the carrier is served through the overlay's `read_file`/`get_accessible_entries` and made a member of the `open_project` configured Program — see §2.3; the shipped API has no inline `default_project` field). (2) Once a member, single-Program reuse becomes available — and is now **proven** for tsgo: the Block-0 gate (GO, 17/17 against the user-installed tsgo) confirmed off-disk-carrier membership via the FS overlay, project-scoped diagnostics/hover/definition from the configured Program, and content-addressed incremental Program reuse across snapshot edits (§2.3, §2.5). The earlier open question is resolved; the residual discipline is version-pinning the `unstable` `--api` and re-gating on bumps (§2.8). The gate harness + report are committed and reproducible at `tools/tsgo-api-gate/` (run `node tools/tsgo-api-gate/run-gate.mjs`).

Verter's own ownership resolver must match this: today's `verter_workspace` ownership is glob-membership-based and would return **no owner** for a `.vue` under an explicit-`include` tsconfig (and `extraFileExtensions` is not modelled in `verter_workspace` at all), which under the §2.4 "no owner ⇒ no external TS result" rule would silently disable TS for that `.vue`. The corrected ownership definition is in §2.6.

Raw type-answer latency is checker-bound (same tsgo checker); **the lever Verter controls is the systems layer — doing less non-checker work** (skip *re-codegen* on untouched carriers, de-dupe redundant transport). That non-checker budget is exactly what the §2.7 self-referential perf gate measures (candidate vs a pinned Verter baseline). Crucially, skipping re-codegen is **not** the same as skipping an engine re-check: cross-file type invalidation stays the engine's job (see §2.7, the corrected cache contract). (An offline compiler-throughput comparison against vize exists for both axes, but it is manager-run and informational — never a CI bar; see §2.7.)

## 2. The architecture

### 2.1 One project-bound semantic contract; two engine backends
Unify the **semantics**, not the transport. A single provider-neutral contract in which a **config-less / inferred-project operation for a production `.vue` is not representable**. Every operation carries its owning project; every query carries the expected carrier identity (content-hash + source-map id) and fails closed on mismatch (retry once, then no result) — **never** an inferred fallback.

The contract is **thin and three-layered** so the two genuinely different engines (a synchronous in-process tsserver plugin vs an asynchronous out-of-process tsgo `--api` client) do not get forced under one fat abstraction that leaks. The shared layer owns parsing, carrier generation, source-maps, VFS generations, ownership resolution, result mapping, caching, batching, and fail-closed policy. Each backend owns *only* its native project/host mechanics and lifecycle:

```text
ProjectResolver:  source_uri  ->  ProjectBinding | NoProject | Ambiguous | SyntheticScratch
CarrierRegistry:  source_uri  ->  CarrierArtifact { provider_uri, role, content, content_hash, map_hash, version }
EngineBackend  (one per engine kind):
  ensure_project({ workspace_root, tsconfig_uri, ts_version, project_identity, env_dims })
  publish_snapshot({
    project: tsconfig_uri,
    files: [{ source_uri, provider_uri, role, script_kind,
              content, content_hash, map_hash, version, open_state }],
    resolution_map_version,
    fs_generation,
  })
  query({ project, provider_uri, carrier_offset, feature, required_version })
  diagnostics({ project, files?, required_snapshot })
  capabilities()  ->  EngineCapabilities          // negotiated, not assumed — see §2.3/§2.8
```

**Project-resolution states (explicit — config-less is not a silent fallthrough):**
- `ProjectBinding` — a resolved configured project; the only state in which external-TS results are produced for a `.vue`.
- `NoProject` / `Ambiguous` — no owning tsconfig, or two configs claim the file with no deterministic leaf; **fail closed** (no external-TS result; Verter-native non-TS features may still answer per §2.6).
- `SyntheticScratch` — untitled buffers / files outside any tsconfig (e.g. a standalone `.vue` opened with no project). These are **not** production `.vue` project semantics; they may be served by an explicit, clearly-labelled scratch project **only for non-cross-file features**, and never warm any project cache. This is why the invariant is "config-less is illegal *for production `.vue` semantics*," not "config-less is unrepresentable everywhere."

**Roles** (`role`): `CarrierIde` = the `{name}.vue.tsx` / `{name}.svelte.tsx` IDE surface (script + template TSX, full interactive projection) — the **self-diagnostics** surface, NOT the bare-import resolution target (that is the `{name}.d.vue.ts` / `{name}.d.svelte.ts` declaration carrier the probe reaches first, §2.2, GATE 5); `CarrierApi` = the `{name}.vue.verter.ts` / `{name}.svelte.verter.ts` macro-derived public-API surface a cross-file rename resolves against — **redirect-reached**, so it carries the reserved `.verter.` infix; `CarrierBatch` = a provisional minimal-diagnostic carrier the design contemplated for the cold TSC surface (script + template-expression type-checkable surface + import/redirection shape, WITHOUT the interactive-only IDE embellishments) that the measurement **merged away** into `CarrierIde` — see below; `Shadow` = a self-file shadow / rune-module surface; `Real` = a genuine non-carrier `.ts`/`.tsx` synced verbatim for context. `CarrierIde`/`CarrierApi`/`Shadow`/`Real` are modelled by the existing `ProviderSurfaceStore`. **`CarrierBatch` was a provisional role** (a distinct `compile_profile` minimal-diagnostic surface for the batch run) that the measurement **merged away**: it concluded with no material cold-perf gain and no valid diagnostic-preserving minimal codegen profile, so `CarrierBatch` was **merged into the single `CarrierIde` surface** — the cold TSC path reads `CarrierIde` directly — and the provisional role, its `compile_profile`, and the `carrier_batch_typechecks_same_as_ide` guard were **removed**. The single `CarrierIde` surface trivially type-checks identically to itself, so the cold path still cannot silently drop a type-observable template-expression construct (§2.7). Each role's snapshot/ownership/cache semantics are defined where it is produced.

**Env dimensions (`env_dims`), not one bundled hash:** per the project's fact-based-cache R21 rule, `env_dims` carries the *orthogonal* dimensions the value actually depends on — at minimum `parse_env_hash`, `resolve_env_hash`, `lib_env_hash`, and `project_identity` — never a single bundled `compiler_env_hash`. Each cache layer (§2.7) keys only on the subset it depends on.

Queries are illegal without a resolved `ProjectBinding`; `NoProject`/`Ambiguous` fail closed. All LSP features depend on this contract — never on a raw `open_tsx`/`update_file` path-only primitive.

### 2.2 The carrier-serving host-proxy (TS<7 / JS language service) — shared by two instantiations
Drive the TypeScript **JS language service** with a Verter **carrier-serving host-proxy**. This host-proxy has **two instantiations that reuse one shared carrier-serving CORE** — the carrier store/overlay, the §2.9 `.x`→companion redirection + specifier-rewrite, and the fail-closed `ProviderPositionMapper` — but they are **NOT identical host hooks** (the §2.1 contract is unchanged across both): **(a)** the Node **tsserver plugin** on native (this section), which feeds tsserver's plugin-host APIs (`getExternalFiles`/`getScriptSnapshot`/`resolveModuleNameLiterals`); and **(b)** the **in-context `ts.LanguageService`** in WASM/playground (§2.11), which implements `LanguageServiceHost` directly. Both bind to the same shared CORE; the tsserver-specific negative-cache mechanics below (two-phase publish / sticky-resolution eviction) are instantiation-(a) concerns and do not all carry to (b). **Instantiation (a) extends the existing `@verter/typescript-plugin`, which already implements the load-bearing hooks** (`getExternalFiles` returning the descriptor-owned virtual companion, `resolveModuleNameLiterals`, `getCompilationSettings`, `getScriptSnapshot` overrides) — Block 4 is a hardening of that plugin, not a greenfield build; factor the shared CORE so instantiation (b) reuses it.

**File identity = the descriptor-owned virtual companion, NOT the source path. Each component projects THREE distinct virtual surfaces with distinct roles, all named by the `VirtualFileNaming` descriptor.** A source carrier file projects to virtual companions whose suffixes are owned by the `VirtualFileNaming` descriptor (CRITICAL: the byte-pinned `packages/language-shared/src/virtual-file-naming.generated.ts`, mirrored from `crates/verter_session/src/framework/descriptor.rs`, guard `virtual_file_naming_ts_freshness`). The engine has **no module-resolution-map endpoint** (§2.3, GATE 5), so the path Verter serves a carrier at IS the engine identity and the **bare-import resolution target** MUST live at a path the engine's appended-extension basename probe actually reaches. Three surfaces follow:
- **Declaration carrier = `{name}.d.vue.ts` / `{name}.d.svelte.ts` — the consumer-facing public declaration a bare `import B from "./B.vue"` resolves to.** This is the **bare-import resolution target**: declaration-only (a valid `.d.ts` — no runtime/value code), the **extension-MIDDLE** `.d.<ext>.ts` form (the `.d.` sits between the stem and the carrier extension), generated by the shared public-API projector in its **`PublicApiMode::Declaration`** mode (descriptor authority: `DeclarationSurface::ExtensionMiddleTs`, the `declaration_carrier_identity()` transform). tsgo's native basename-append probe reaches it FIRST (probe order `.d.<ext>.ts` → `.<ext>.ts` → `.<ext>.tsx`, so the declaration wins over the IDE carrier). It is **path-collision-free** against a *different* real source extension in the normal case (a real Svelte **rune module** is user source at exactly `*.svelte.ts`/`*.svelte.js`, never a `.d.svelte.ts`). The **probe mechanism** this rides is GATE-5-proven (the committed `tools/tsgo-api-gate/` harness empirically established that tsgo's basename-append probe reaches an overlay-served companion, that `.verter.` is unreachable, and the probe order; a `.svelte.tsx` carrier coexists with a real `state.svelte.ts` rune module); the **production target is the `.d.<ext>.ts` declaration carrier the same probe reaches first**, enforced by the Rust guard `component_bare_import_resolves_to_declaration_carrier`. **But the carrier path is in the USER namespace, NOT a reserved one — path-collision-free is NOT resolution-unambiguous (see the Carrier-path conflict model below).** A real same-path file, or a same-stem `Foo.svelte.ts` rune module beside a `Foo.svelte` component, is a RESOLUTION conflict that Verter **detects and fails closed** rather than silently shadowing or surfacing a wrong edge.
- **Component IDE carrier (`CarrierIde`) = `{name}.vue.tsx` / `{name}.svelte.tsx`** (or `.jsx` per source lang). This is the **self-diagnostics surface** verter_lsp owns — the file B.vue is type-checked AS, for its own hover/diagnostics/go-to-def/template-checking, source-mapped back to B.vue. It is **NOT a bare-import resolution target**: a consumer's `import "./B.vue"` resolves to the declaration carrier above, not here. A `.verter.`-infixed *component* identity is **REJECTED** — serving `Comp.vue.verter.tsx` does NOT satisfy `import "./Comp.vue"` (tsgo never probes a `.verter.` segment → TS2307, GATE 5).
- **Public-API carrier (`CarrierApi`) = `{name}.vue.verter.ts` / `{name}.svelte.verter.ts`** — the Verter-reserved `.verter.` infix is correct and necessary HERE, and ONLY here. This `.ts` surface is **redirect-reached** (project-reference redirect / cross-package `.d.ts`-equivalent — §2.6) and reached by internal/self-import callers (the IDE carrier self-imports it to type `___VERTER___instance`); it is **never bare-probed**, so a reserved infix does not break any probe; it is *required* because a bare `{name}.svelte.ts` API carrier WOULD collide with a rune module (GATE 5 records tsgo probing `.svelte.ts` **before** `.svelte.tsx`, so a `.svelte.ts` carrier identity would be shadowed by a same-stem rune module). No real on-disk file carries a `.verter.ts` segment.

**Uniform declaration-resolution invariant.** ALL component-to-component references resolve to the `.d.<ext>.ts` declaration carrier — the public declaration boundary — regardless of importer kind: a plain `.ts`/`.js` consumer importing `./B.vue` AND another component's `<script setup>`/template importing `./B.vue` both land on `B.d.vue.ts`. The `.vue.tsx`/`.svelte.tsx` IDE carrier is no longer a bare-import resolution target on any path; it is composed and type-checked only as B.vue's own self-diagnostics surface.

**Why `.d.<ext>.ts` (extension-MIDDLE), not extension-LAST `.vue.d.ts`.** tsgo treats `.d.<any>.ts` as a declaration file, and the extension-MIDDLE form (`B.d.vue.ts`) resolves in **all** module modes (`node16`/`nodenext`/`bundler`/classic); the extension-LAST form `B.vue.d.ts` is **bundler-only** and would not bare-resolve under the others. `allowArbitraryExtensions: true` (ALREADY set in Verter's synthesized compiler options) is a **post-resolution DIAGNOSTIC gate** — it suppresses TS6263 ("module cannot be imported … consider adding an `allowArbitraryExtensions`") once the carrier is reached, NOT a resolution enabler: the resolver builds the `.d.<ext>.ts` candidate **ungated**, and the flag only keeps the resolved import from being flagged as an arbitrary-extension import.

**Carrier-path conflict model — the carrier path is in the USER namespace, so a model conflict FAILS CLOSED; Verter NEVER overlay-shadows a real user file (cross-referenced from §2.6 ownership).** The `{name}.vue.tsx` / `{name}.svelte.tsx` component-carrier path is **path-collision-free** against a different real source extension in the normal case, but it is **NOT a Verter-reserved namespace** — a user may legitimately have a real file at that exact path, or a same-stem rune module that resolution reaches first. Such a case is a **resolution conflict**, detected and fail-closed:
- **A real user file at the exact carrier path ⇒ CONFLICT → fail closed (never overlay-shadow).** Before Verter serves a carrier at a target path (`Foo.vue.tsx`), if a real file already occupies that **exact path on disk**, that is a CONFLICT: the source is marked **`Ambiguous`/conflicted** (the §2.1/§2.6 `Ambiguous` state), Verter **does NOT place the overlay** (it never shadows the user's real `Foo.vue.tsx`), and **produces no external-TS result for that source** — Verter-native (non-external-TS) features may still answer. The `path_is_carrier` / `all_adapter_module_extensions()` classifier (above) names the candidate carrier path; the disk-occupancy check is the conflict gate.
- **Same-stem Svelte rune ⇒ AMBIGUOUS → fail closed (DETECTED, not a silently-wrong edge).** Because GATE 5 proved tsgo probes `.svelte.ts` **before** `.svelte.tsx`, if a real same-stem `Foo.svelte.ts` rune module exists beside a `Foo.svelte` component, a bare `import "./Foo.svelte"` is **AMBIGUOUS** — the rune shadows the carrier. Verter **detects** this same-stem collision (the rune module and the component carrier share the exact stem under `path_is_carrier`) and **fails closed** (the source is `Ambiguous`, no external-TS result, no silently-wrong edge surfaced to the user). This **replaces** the prior "documented wrong-edge / accepted TS1192" disposition: the collision is no longer surfaced as a wrong edge — it is a detected ambiguity that produces no result. The bare import resolves to the `.d.svelte.ts` declaration carrier normally (and the `.svelte.tsx` IDE carrier is composed) whenever **no** same-stem `.svelte.ts` rune exists (the normal case, since rune-module stems differ from component stems).
- **Non-fail-closed future path (not in the shipped `--api`).** A static **module-resolution-map API** (an upstream tsgo capability the shipped `--api` does NOT expose — §2.3/§2.8) would let Verter **redirect the bare import to a non-colliding carrier path without shadowing** any real file, dissolving both conflicts above without failing closed. Record it as the **future enhancement**; **fail-closed is the behavior until/unless that API exists.**
- *Guards:* `carrier_never_shadows_real_user_file` (a real file at the exact `{name}.vue.tsx`/`{name}.svelte.tsx` carrier path ⇒ `Ambiguous` + no overlay placed + no external-TS result, asserted for `.vue` AND `.svelte`; the user's real file is never shadowed) and `same_stem_svelte_component_rune_fails_closed` (a `Foo.svelte` component beside a real same-stem `Foo.svelte.ts` rune ⇒ DETECTED ambiguity, no silently-wrong edge — fail closed). Registered to Block 1 (ownership/`Ambiguous`) and Block 4/5 (the per-engine overlay-placement gate).

(The `.vue.tsx`/`.svelte.tsx` and `.verter.ts` examples below read for every adapter.) The plugin:
- declares the carrier extension via `extraFileExtensions` (script kind TSX/JSX per source lang) and exposes project-owned carrier-source files through `getExternalFiles`/`readDirectory` so the **configured project** owns the virtual companion;
- serves the **carrier TSX** as the *companion's* `getScriptSnapshot`/`getScriptVersion`/`readFile`/`fileExists`/script-kind (the companion's content IS the carrier; the source file itself stays the user's source);
- redirects module resolution for carrier-source specifiers (`./C.vue` → the `C.d.vue.ts` declaration carrier — matching the bare-import target tsgo's probe reaches first (`.d.<ext>.ts` wins over `.<ext>.tsx`), so both engines resolve the in-project bare import to the SAME surface; the `C.vue.tsx` IDE carrier is the self-diagnostics surface, not the bare-import target; the macro-derived `.verter.ts` API surface is the cross-package redirect target of §2.6, not the in-project bare import) via `resolveModuleNameLiterals` (the modern hook; not the legacy `resolveModuleNames`) **without rewriting generated text** (CodeTransform-is-source-of-truth). NB: tsserver's `resolveModuleNameLiterals` returns a `resolvedFileName` directly (a true resolution map), so unlike tsgo it is not basename-probe-bound — but Verter targets the same `.d.vue.ts` declaration identity on both engines for parity;
- leaves `paths`/`baseUrl`/`types`/`lib`/`jsx`/project-references owned by tsserver's real configured project.

**Descriptor authority (all three surfaces).** The committed `VirtualFileNaming` descriptor (`packages/language-shared/src/virtual-file-naming.generated.ts`, mirrored from `crates/verter_session/src/framework/descriptor.rs`, byte-pinned by `virtual_file_naming_ts_freshness`) is the single authority for every adapter's carrier-surface suffixes, and it renders all three roles: the **IDE carrier** via the `ide` column (Vue `ide: jsxConditional` → `App.vue.tsx`/`App.vue.jsx`, Svelte `ide: .tsx` → `App.svelte.tsx`); the **public-API carrier** via the `importSurface` column (`importSurface: .verter.ts` → `App.vue.verter.ts` / `App.svelte.verter.ts` — the reserved `.verter.` infix uniformly across adapters, collision-proof against the Svelte rune-module `.svelte.ts` extension which the API carrier would otherwise alias); and the **declaration carrier** via the `declarationSurface` column (`declarationSurface: extensionMiddleTs` → `App.d.vue.ts` / `App.d.svelte.ts`, the `declaration_carrier_identity()` transform that inserts `.d.` between the stem and the carrier extension). A consumer composing any carrier path MUST route through the descriptor — never a hardcoded literal. The rune-module row (`SVELTE_RUNE_MODULE`: `ide`/`importSurface` = `selfFile`, `declarationSurface: none`) projects no companion and no declaration carrier. Any new carrier suffix or a fourth surface is a descriptor + byte-pinned-mirror change landing under `virtual_file_naming_ts_freshness` + `carrier_companion_suffix_collision_free`; it cannot land guard-silent.

**TWO carrier-projection policies — the contract spans BOTH `VirtualPathPolicy::{Suffix, SelfFile}` (D3, framework parity).** Verter's adapter substrate (`verter_session::framework`, `VirtualPathPolicy`) already defines two ways a source carrier file maps to its engine surface, and the membership/overlay/redirection/leak-suppression contract must cover **both** (the above describes only `Suffix`):
- **`Suffix` (companion ≠ source path)** — the common case (Vue components and Svelte components). The **component IDE carrier** identity is `{name}.vue.tsx` / `{name}.svelte.tsx` and the **public-API carrier** identity is `{name}.vue.verter.ts` / `{name}.svelte.verter.ts` (the GATE-5 split above). The overlay serves carrier content **at the companion path** and falls through to disk for the bare source path; `.x`→declaration-carrier redirection applies (the §2.9/GATE-4 + GATE-5 extension-probing — `Foo.svelte` → `Foo.d.svelte.ts`, identical to Vue's `Foo.d.vue.ts`, the extension-MIDDLE path the probe reaches first); the source `.x` is NOT a TS document; B2 suppresses companion-path results (both the `.vue.tsx`/`.svelte.tsx` IDE carrier and the `.verter.ts` API carrier are Verter-owned companion paths the user never opens).
- **`SelfFile` (the carrier IS the source path, rewritten in place)** — Svelte **rune modules** (the REAL `.svelte.ts`/`.svelte.js` user source) and any adapter surface whose engine identity equals its own canonical path, serving `<prelude> + <rewritten source bytes>`. This is **distinct from the `Suffix` companion** and leak-suppression does NOT apply to it. Here: engine identity = **the source path itself** (no companion, no infix — the rune module keeps its real `.svelte.ts` path); the overlay serves **rewritten content for that real path** (it does NOT fall through to disk — it overrides the on-disk bytes); **redirection is a no-op** (the import already targets the real path, no `.x`→companion hop); the per-line specifier rewrite the rune path performs is an **explicit, sanctioned exception** to §2.7's "carrier text stable / no post-hoc rewriting" (which holds for `Suffix` companions but NOT for `SelfFile`, where in-place rewrite is the mechanism); and **B2 leak-suppression must NOT suppress results on a `SelfFile` path** — it is a real user document (the inverse of the companion rule), so its diagnostics/edits map through `ProviderPositionMapper` (prelude/rewritten regions fail-closed) and surface normally.
- **Collision invariant (gate-proven) — path-collision-free, NOT resolution-unambiguous.** The two `Suffix` identities are **path-collision-free against a *different* real adapter source/module extension** for two distinct reasons: the **component IDE carrier ends in `.tsx`**, which is never a Svelte rune-module extension (`*.svelte.ts`/`*.svelte.js`) — so `Foo.svelte.tsx` is not a *different-extension* rune module (GATE 5 proves a `.svelte.tsx` carrier and a real `.svelte.ts` rune module coexist); the **`.ts` API carrier carries the reserved `.verter.` infix** precisely because a bare `{name}.svelte.ts` WOULD collide with a rune module (GATE 5 records `.svelte.ts` probed before `.svelte.tsx`), and the API carrier is redirect-reached so a reserved infix breaks no probe. **Path-collision-free is NOT resolution-unambiguous, and the carrier path is in the USER namespace:** a real same-path file OR a same-stem rune module is a **RESOLUTION conflict that Verter detects and FAILS CLOSED** (the Carrier-path conflict model above; cross-referenced in §2.6) — never an overlay-shadow of a real user file, never a silently-wrong edge. The descriptor's `path_is_carrier` / `all_adapter_module_extensions()` split is the authority that disambiguates a generated companion path from a real rune-module path. **Same-stem edge (GATE 5 D2) — FAIL CLOSED, not a documented wrong-edge:** a component carrier and a rune module that share the EXACT same stem (`Widget.svelte.tsx` + `Widget.svelte.ts`) make the bare `import "./Widget.svelte"` ambiguous (tsgo probes the `.ts` rune first — the underlying tsgo behavior GATE 5 records as TS1192); this is inherent to Svelte's rune-module naming and is NOT fixed by any infix (a `.svelte.verter.tsx` component carrier is unreachable by the bare probe anyway), so **Verter detects the same-stem collision and fails closed** (the source is `Ambiguous`, no external-TS result — no silently-wrong edge surfaced). The component carrier stays `.svelte.tsx` and resolves the bare import normally **whenever no same-stem `.svelte.ts` exists** (the normal case). The non-fail-closed dissolution (a future module-resolution-map API redirecting to a non-colliding path) is recorded in the conflict model above. *Guard:* `carrier_contract_covers_selffile_and_suffix` (the membership/overlay/redirection/leak rules are exercised for BOTH policies, e.g. a Vue component (`Suffix`) AND a Svelte rune module (`SelfFile`)); `carrier_companion_suffix_collision_free` (the component carrier ends in `.tsx` ≠ any *different* rune-module extension, and the `.ts` API carrier's reserved `.verter.` infix equals no real adapter source/module extension — asserted for `.vue` AND `.svelte` incl. the `.svelte.ts` rune-module form; this guard covers PATH-collision-freedom only, NOT resolution ambiguity — the Fix-1 fail-closed guards below cover that); `component_bare_import_resolves_to_declaration_carrier` (the Rust production-target guard — a bare `./Comp.vue`/`./Comp.svelte` import resolves to the `Comp.d.vue.ts`/`Comp.d.svelte.ts` declaration carrier, the extension-MIDDLE path tsgo's basename-append probe — whose order GATE 5 established — reaches FIRST (`.d.<ext>.ts` wins over `.<ext>.tsx`); the `.vue.tsx`/`.svelte.tsx` IDE carrier is the self-diagnostics surface, not the bare-import target; a `.verter.`-infixed identity is API-only — unreachable by the bare probe); `carrier_never_shadows_real_user_file` + `same_stem_svelte_component_rune_fails_closed` (the resolution-conflict fail-closed pair from the Carrier-path conflict model above — a real file at the exact carrier path, and a same-stem rune beside a component, both fail closed).

**Full host-proxy matrix (each hook tested for `.vue`, helpers, type-reference directives, package `exports`, directory scans):** `getScriptSnapshot`, `getScriptVersion`, `getScriptKind`, `readFile`, `fileExists`, `resolveModuleNameLiterals`, `resolveTypeReferenceDirectiveReferences`, `readDirectory`, `directoryExists`, `getDirectories`, `realpath`, `getCanonicalFileName`. A partial proxy silently constructs the wrong Program graph.

**Critical: the plugin does not compile Vue, and a missing/stale carrier must never poison tsserver's caches.** Plugin host APIs are **synchronous** and tsserver **caches their results into the Program and the module-resolution cache** — including *negative* results. If the plugin returns "no snapshot" / `fileExists=false` for a `.vue` companion that the project owns before Verter's async carrier store is warm, tsserver records a sticky failed resolution (`TS2307`) and a missing file, and will not spontaneously re-resolve. So:
- The plugin reads carriers from a Verter-published **content-addressed carrier snapshot store + atomic manifest (epoch)** — never a per-read synchronous callback into Rust.
- **Two-phase publish:** content files are written to the store first, *then* the manifest epoch is advanced. A file is never advertised through `getExternalFiles` before its content exists.
- For a path the plugin *knows* is a project `.vue` (from `getExternalFiles`), a cold read **bounded-blocks** on the manifest epoch (a short, bounded wait on a condition — never a busy-spin, never an unbounded block) rather than returning a negative result; for a previously-known file it returns the **last-good** snapshot/version, not `undefined`.
- After the store warms a path that tsserver had already probed cold, Verter forces a `projectService` "file changed" notification for those paths to **evict tsserver's negative resolution cache**.
- LSP responses are gated **in Verter** (the §2.7 version-gate), not inside the plugin read path: a query whose required snapshot is not yet synced returns no result and retries once — it does not let the plugin fabricate a degraded answer.

Verter remains the parse/codegen/VFS authority; the store is an engine mirror. A genuinely unavailable carrier ⇒ no TS result (never parse raw SFC text, never emit bogus `TS2307`).

### 2.3 tsgo (TS≥7) — a DUAL-SURFACE backend (`--api` typecheck + `--lsp` interactive features) over one shared CORE, FS-overlay project membership
**Not** the tsserver plugin model (tsgo cannot dynamically link third-party code into its server process). Drive the user-installed tsgo's `--api`. This section specifies the **OWNED mode** — Verter spawns its own `--api` instance and the FS overlay backs carriers. **OWNED is the correctness BASELINE and the architectural center of the tsgo backend: it is the actual tsgo path, works in every editor, and is what the rest of this doc means by "the tsgo backend."** The **SHARED mode** (attach to the editor's own tsgo, carriers injected as LSP overlay documents on the shared session — §2.10) is an **optional layered optimization** built ON TOP of this OWNED `--api` backend, enabled only where a full editor TS-LSP proxy exists (VS Code today); it is never on the core path. In OWNED mode the plain LSP `didOpen` overlay is **not** the membership mechanism (the FS overlay + `open_project` is); in the SHARED optimization an LSP overlay document on the *shared* session is the carrier-injection channel (§2.10) — both are bindings of the same carrier contract, OWNED being the primary one. **The TS≥7 distribution is the npm `typescript` package at v7** — e.g. `typescript@7.0.1-rc` (the Go-port "Corsa" `typescript` release; per-platform native binaries `@typescript/typescript-{platform}-{arch}`; `--api` client exported at `typescript/unstable/sync`). **This mechanism is empirically verified (Block-0 gate = GO, 17/17 + GATE 5 7/7; reproducible repo gate at `tools/tsgo-api-gate/`, report `tools/tsgo-api-gate/GATE-REPORT.md`).**

**The tsgo backend is DUAL-SURFACE — `--api` (the checker oracle + batch/TSC typecheck) and `--lsp` (interactive IDE features + interactive diagnostics), SEPARATE surfaces sharing one CORE.** The user-installed tsgo exposes two distinct surfaces and the backend drives **both**:
- **`--api` (MessagePack) = the project-bound CHECKER ORACLE + the BATCH/TSC/vite-perf typecheck surface** — the internal checker / type-reflection primitives Verter needs (carrier membership, the `semantic_diagnostics_for_carrier_in_project` typecheck oracle, type reflection), AND the tsc-like vite-performance BATCH typecheck surface. This is the surface the FS overlay + `open_project` membership of this section, the §2.4 batch typecheck, and the §2.7 cold/warm perf gates all ride. It is the typecheck AUTHORITY (the project-bound oracle S3 proves), but it is **NOT** the INTERACTIVE editor-diagnostics surface (see the diagnostics ruling below).
- **`--lsp` (the `tsgo --lsp --stdio` server) = ALL interactive IDE/LSP features** — its internal handlers serve hover, definition, type-definition, references, rename, completion + `completionItem/resolve`, signature-help, document-highlights, semantic-tokens, and inlay-hints over the project-bound carrier membership.

Both surfaces share a **CORE** — the carrier-snapshot identity (content-hash + source-map id) and the project-bound membership (the same configured-project carrier membership the `--api` FS overlay establishes); they are separate transports onto one carrier contract, not two independent backends.

**The one-surface-per-concern rule (a rule, not a preference).** ALL interactive LSP features — hover, definition, type-definition, references, rename, completion + `completionItem/resolve`, signature-help, document-highlights, semantic-tokens, inlay-hints — are served by **ONE** surface, `--lsp`, **regardless of whether `--api` could derive them from checker primitives**. `--api` is **NOT a source for interactive LSP features.** There is **NO DUAL PATH**: never both `--api` and `--lsp` answering LSP-feature requests in the same session — this is Verter's no-dual-path discipline applied to the feature surface (two engines answering one feature is exactly the divergence/hang class the project forbids). The per-feature "use `--api` wherever it is lossless" idea is **WITHDRAWN**: even where `--api`'s checker primitives could reconstruct a feature, the feature is served by `--lsp` so there is exactly one answer path.

**VERIFIED MECHANISM (evidence-grounded, stated as fact).** The shipped `@typescript/native-preview` exposes **NO `./unstable/lsp` export**; its `--api` clients (`./unstable/sync` / `./unstable/async`) expose ONLY checker-reflection primitives (`getType*` / `getSymbol*` / `getSemanticDiagnostics` / `getProperties` / `getSignatures` / …) and have **NO rename / references / completion / definition / hover / signatureHelp / documentSymbol request types**. There is no `--api` route to those features; the `tsgo --lsp --stdio` server's internal handlers are what serve them. So the one-surface rule is not only Verter discipline — the `--api` surface structurally cannot answer interactive LSP features, and the `--lsp` surface is the only one that can.

**Diagnostics ruling (FINAL — supersedes any earlier "`--api` = THE diagnostics surface" wording).** INTERACTIVE editor diagnostics — the RICH set (semantic + syntactic + suggestions + the LSP `tags` (unnecessary/deprecated) + related-information) — are served by **`--lsp`** (the LSP diagnostic pull), so there is exactly ONE diagnostics authority per epoch, and carrier spans are mapped back to the `.vue`/`.svelte` source through `ProviderPositionMapper` (generated-only spans suppressed). `--api`'s `getSemanticDiagnostics` carries NONE of the syntactic/suggestion/tag/related-info richness and its per-carrier program can diverge, so it CANNOT serve the interactive squiggles. `--api` remains (a) the project-bound CHECKER ORACLE — the internal typecheck authority (`semantic_diagnostics_for_carrier_in_project`, proven project-bound + non-vacuous in the OWNED-provider live tests) — and (b) the designated SEPARATE BATCH / TSC / vite-perf typecheck surface (§2.4), which is a DISTINCT surface from the interactive editor diagnostics, not a competing answer to them. Wiring `verter-tsc` onto the `--api` batch surface (the `--api`-batch productization) is a SEPARATE TRACKED follow-up, not part of the interactive LSP path. (The interactive FEATURE responses also ride `--lsp`, per the one-surface rule above.)

**Production transport = a Rust-native `--api` client in a dedicated crate (working name `verter_tsgo_api`); there is NO Node process driving tsgo in production.** Verter (Rust) spawns `tsgo --api --cwd <dir> --callbacks=<…>` directly and speaks the `--api` MessagePack wire itself — request/response plus the host callbacks `read_file` / `file_exists` / `get_accessible_entries` / `realpath` / `directory_exists` (the same FS-overlay callbacks below, now answered Rust-side). The install also ships an **official generated JS `--api` client** (`{typescript|@typescript/native-preview}/unstable/sync`, class `API`, plus an `unstable/async` JSON-RPC twin) that spawns `tsgo --api --cwd … --callbacks=…` over MessagePack; **Verter retains that JS client ONLY as a test/parity oracle (the §2.8 / Block-0 gate), NEVER as the production transport.** *(The original recorded gate run used the `@typescript/native-preview 7.0.0-dev.20260526.1` dev-preview channel. `npm view typescript@7.0.1-rc` confirms the production package carries the platform tsgo binary + the SAME `./unstable/sync`/`./unstable/async` exports, so the **surface is npm-confirmed equivalent** — and BEHAVIOR is now **gate-proven** against the prod package: the gate + fixtures run against `typescript@7.0.1-rc` (B4). Engine selection is **rc-only** — the gate selects the installed `typescript` whose **major is ≥ 7** with **no `@typescript/native-preview` fallback source** (a Block-5 spike showed native-preview converged to rc's exact integer `--api` wire, so the prior fallback was redundant legacy and was removed — see the rc-only convergence note below).)*

**Why a Rust-native transport (and its bounded risk).** The production transport is a Rust-native client speaking the `unstable`/generated `--api` wire directly. The risk is real and bounded by guards: the wire is `unstable`/generated, so version-skew against the user's tsgo is a correctness hazard, and a Rust client generated from an authoritative published schema is only a future option (no published schema exists today — the official JS `--api` client is retained instead as the parity oracle, mitigation 4). The Rust-native transport is therefore sound **only under five mandatory risk-mitigations** that convert the version-skew risk into guards — sound **only under all five**:
1. **A dedicated crate isolates the unofficial-wire client.** Only the MessagePack `--api` wire lives in `verter_tsgo_api`; ALL semantics — carrier generation, source maps, scheduling, cancellation, cache keys, fallback — stay in the rest of the Rust stack and never leak into the wire crate, and the crate **reuses Verter's VFS + the shared stores** (per the host-fs paragraph below) — it is a thin wire+adapter, NOT a new overlay/fs/semantics layer.
2. **The codec is HAND-WRITTEN against the shipped typed proto as its correctness reference; version-bump correctness is verified by a maintainer-run agent.** *(There is NO code generator: the codec is hand-written, never derived from the shipped `.d.ts`, and a manual version-update check re-verifies it against the shipped proto on each bump.)* The Rust MessagePack encoder/decoder is written by hand to MIRROR the typed proto the package ships — `dist/api/node/msgpack.d.ts` + `dist/api/proto.d.ts` + the encoder + the `./unstable/proto` typed exports (field names/tags/order/op set cited in-code) — so the wire shape is taken from the shipped types as the authoring reference, never blind-guessed. On a TypeScript/tsgo version update the maintainer runs an agent to re-verify the hand-written codec against the updated shipped proto and bumps the maintained `schema_manifest` wire pin. The AUTOMATED rails that keep a hand-coding or version mismatch from shipping silently are mitigations 3 (the runtime fail-closed wire gate, which refuses a tsgo whose version/wire-hash does not match the maintained pin) and 4 (the parity-oracle test against the official JS client).
3. **A version-pinned capability gate FAIL-CLOSES on any wire-shape change.** The existing `tsgo_capability_gate_on_version` guard (§2.8) is extended to validate the Rust client's wire against the installed tsgo per version; a tsgo bump that changes the wire **fails the gate** — Verter never ships a silently-diverged client (it fails closed for TS≥7 on that surface instead).
4. **A PARITY-ORACLE test asserts byte-for-result identity against the official JS client.** The same `--api` operations run through BOTH the Rust-native client AND the official generated JS client and must produce IDENTICAL results; the JS client exists ONLY as this test/parity reference (Node is allowed in the gate, NEVER in production).
5. **An async (non-blocking, concurrent) interactive lane is required** (the §2.7 interactive lane; the §2.8 handshake proves the async `--api` wire), so the Rust client is not a sync-only transport. Cancellation, though, is surface-specific (Finding 1): the `--api` wire has **no wire-level cancel**, so `--api` cancellation is **client-side abandonment only** (the async client buys concurrency, not a wire cancel); real protocol cancellation (`$/cancelRequest`) lives on the `--lsp` interactive-feature surface (§2.3/§2.7).

**Host-fs callbacks are served by Verter's VFS — the crate does NOT reinvent a filesystem.** The `--api` engine→host `fs` callbacks (`read_file` / `file_exists` / `get_accessible_entries` / `realpath` / `directory_exists`) AND the carrier overlay are backed by **Verter's VFS** (the shared workspace/VFS file authority), not a filesystem the crate invents. `verter_tsgo_api` reuses the SAME shared substrate the Block-4 tsserver backend already uses — the carrier surface store (`ProviderSurfaceStore`), the §2.6 ownership resolver, the `verter_scheduler`, source maps, and generation/epoch invalidation (reuse-first per the "Shared Optimized Codebase" rule, exactly as the tsserver backend reused this substrate without a second store). The dedicated crate owns ONLY the `--api` wire / codec / protocol plus a **thin fs-callback adapter** that delegates into Verter's VFS; it is explicitly NOT a parallel file / overlay / semantics layer.

The surface is marked `unstable`/generated, so it is **version-pinned and re-gated on bumps** by re-running the gate harness (the §2.8 capability handshake), which under mitigations 3–4 now validates the Rust client's own wire.

**Membership mechanism (CORRECTED — this is the shipped API, not the #2824 proposal).** The shipped public `updateSnapshot` does **NOT** take an inline `open_files: [{ uri, content, default_project, version }]` payload (that was the typescript-go #2824 *proposal* shape). The actual param is `{ open_project?: tsconfig_path, file_changes?: { changed?[], created?[], deleted?[] } | { invalidate_all: true } }`. The carrier is made a **configured-project member via the FS OVERLAY**, which is a *better* fit for Verter than the proposal shape (it maps 1:1 onto the VFS and needs no special per-file open call):

- `new API({ tsserver_path: <user tsgo exe>, cwd: workspace_root, fs: { read_file, file_exists, get_accessible_entries, realpath, directory_exists } })` — the FS callbacks ARE the VFS overlay (`read_file` ≈ `WorkspaceRead::read_file`).
- `update_snapshot({ open_project: <abs tsconfig path> })` resolves and **holds the configured-project Program**. The off-disk carrier becomes a real **root file** of that Program because the overlay's `read_file`/`file_exists` serve its content and `get_accessible_entries` injects it into its directory listing so the tsconfig's `include` enumeration discovers it (GATE 1: `carrier_in_program_rootfiles = true`, `scriptKind = TSX`).
- **The overlay is sparse:** return carrier content for the carrier path; return `undefined` for `node_modules`/libs/real `.ts` so they **fall through to real disk** (`null` forces not-found). Verter mirrors nothing.
- Association is **queryable**: `snapshot.get_default_project_for_file(carrier)` → the real tsconfig (GATE 1: not an inferred project). The negative control proved that with **no `open_project`**, `get_projects()` is `[]` and the carrier errors "no project found for file" — today's inferred path provably cannot pass, so this is the RED baseline the new fixtures encode.
- **Engine file identity for the bare import = a single, stable, path-collision-free virtual carrier path** (the declaration carrier of §2.2 — `Comp.d.vue.ts` / `Comp.d.svelte.ts`, extension-MIDDLE, *not* a temp path and never a *different* real source extension; path-collision-free ≠ resolution-unambiguous — a real same-path file or a same-stem rune is a resolution conflict that fails closed, §2.2 Carrier-path conflict model; the `.vue.tsx`/`.svelte.tsx` IDE carrier is the separate self-diagnostics surface, and the redirect-reached public-API surface is the separate `.verter.ts` carrier), so module identity, project membership, rename/reference identity, and source-mapping all key off one path. The path MUST be one tsgo's appended-extension probe reaches for the bare `.x` import (GATE 5 — hence the extension-MIDDLE `.d.<ext>.ts` declaration carrier, which wins the probe over `.<ext>.tsx`, NOT a `.verter.`-infixed path which the probe never reaches), and MUST round-trip **byte-identically** through both tsgo's path handling and Verter's `ProviderPositionMapper`/`CanonicalPath` (§2.6 portability).

**Carrier discovery — making the companion a Program root, by the verified overlay mechanisms.** The shipped `--api` exposes `{ open_project, file_changes, fs-callbacks }` and **no explicit `rootNames`-override**, so "root-set injection" must be realised through the FS overlay, which backs **every** read tsgo makes — *including the tsconfig file itself*. The deciding factor is whether the user's config **enumerates the companion's `.tsx`/`.ts` extension**, not whether the glob is "directory-style":
  - **When the config's enumeration ALREADY matches the companion extension** — the default include, a directory/bare-star glob (`"src"`, `"src/**/*"`), OR an **extension-specific glob that matches `.tsx`/`.ts`** (`"src/**/*.tsx"`) — the overlay's `read_file`/`file_exists` (+ `get_accessible_entries` augmenting the directory listing) make the companion a discovered root file directly. This is the case Block 0's fixture (`include: ["src/**/*.tsx"]`, which enumerates the `.tsx` companion) exercised and proved.
  - **When the config does NOT enumerate the companion extension** — a `.vue`-specific glob (`"src/**/*.vue"`), or a `files` list, or any glob whose extensions exclude `.tsx`/`.ts` — `get_accessible_entries` cannot help (it cannot override a `files` list, and a non-matching glob filters the injected name out), so the adapter **virtualizes the tsconfig** as a **first-class identity model**, not a casual content overlay:
    - **The virtualized config is its own cache identity.** It carries its **own virtual-config hash** (over the user config's content hash ∪ the injected companion-path set) and its own derived **`project_identity`** distinct from the user config's, so a virtualized-config Program never aliases a non-virtualized one in any §2.7 cache slot. The overlay serves a `read_file` of `tsconfig.json` whose `include`/`files` is augmented with the companion paths (a Verter-computed overlay of the user's config content, never written to disk; the user's real config is unchanged). tsgo then parses the virtualized config and the companion is a root file.
    - **Injected roots are config/options-diagnostic-invisible (batch promises config/options parity).** The companion entries Verter injects into `include`/`files` are **mapped/suppressed** so they NEVER surface in user-visible config-file-parse / options diagnostics (`get_global_diagnostics` / options diagnostics / config-file parse diagnostics, §2.4) — a virtualized config must produce the **same config/options diagnostic set** the user's real config would; only the real-config entries are user-visible, the injected roots are Verter's and are stripped from any config/options diagnostic before it maps back. Apart from the injected `include`/`files` entries the virtualized config is byte-identical to the user's.
    - **Explicit invalidation.** The virtualized config is invalidated and recomputed when ANY of: the user's `tsconfig.json` content changes (its content hash advances), the owned companion-path set for that project changes (a carrier-source file added/removed/renamed), or an `extends`-chain ancestor changes — each advances the virtual-config hash and re-roots the virtualized-config Program. A pure carrier-*text* edit does NOT touch the virtual config (the path set is unchanged) — only the §2.7(b) engine notify fires.
  Either way the companion is a member of the `open_project` Program; the choice is driven by whether the user's config enumerates the companion extension (the §2.6 ownership resolver records which). **Block 5 must prove both** mechanisms: the **companion-extension-enumerated** case is **gate-proven** (Block 0's fixture used `include: ["src/**/*.tsx"]`, an extension-specific glob that matches the `.tsx` companion — this is that case, NOT a directory glob); the `.vue`-specific-`include` and `files`-list cases via the tsconfig-virtualization path are the unproven ones.

**Bare `.vue`/`.svelte` resolution = tsgo's NATIVE probe over a PROACTIVELY-PROVIDED declaration overlay (no module-resolution hook).** tsgo exposes FS callbacks but **no module-resolution hook** — no `resolveModuleNameLiterals`, plugins are inert, `extraFileExtensions` is dormant (typescript-go #2824 confirms the TS team refuses resolution callbacks). So Verter does **not** intercept resolution; it is **PROACTIVE**. For `import X from "./Comp.vue"`, tsgo's own resolver appends to the `Comp.vue` basename and probes `Comp.d.vue.ts` → `Comp.vue.ts` → `Comp.vue.tsx`; the FS overlay (consulted before disk) answers the FIRST probe with the `Comp.d.vue.ts` declaration-carrier content Verter has **already opened**, so the declaration wins (GATE 1/2 also proved `paths` alias + project-reference redirect resolve on an off-disk carrier). There is no per-import redirection set, no "Verter supplies a redirect when resolution reaches a `.vue`" callback — those would require the hook tsgo does not expose. Verter never reimplements module resolution; it only ensures the declaration carrier is a present overlay before the probe reaches it.

**Proactive transitive-declaration-closure (what makes hookless resolution work).** Because there is no hook, every declaration an opened carrier transitively imports MUST already be an open overlay when that carrier is type-checked, or its bare import fails `TS2307`. When an SFC carrier is opened, Verter therefore opens its own `.d.<ext>.ts` declaration AND the transitive closure of its imported components' declarations as overlays. The closure is a **per-open-root BFS over the carrier-dependency graph driven by the typed analyzed import set** (the carrier subset of the script imports, resolved through the workspace resolver — never a scan of generated declaration text, per the typed-IR-only rule), **bounded by a per-root visited set** so an import cycle (`A → B → A`) terminates (the root is seeded once; the back-edge is a no-op). A **reachability refcount** keys each declaration-overlay path to the set of open carrier roots whose closure reaches it; the `did_close` lifecycle **releases** the closing root from every set and closes only the overlays whose reaching-root set drains to empty (an overlay still reached by a different open root is retained — closing it would strand that root's bare imports on `TS2307`). This proactive closure is the production mechanism; the declaration carriers are **virtual overlays, never written to disk**. *(The probe mechanism is GATE-5-proven — an overlay-served companion at a probed path resolves the bare import with types flowing, and a `.verter.`-infixed path does NOT (`TS2307`); the production bare-import target is the `Comp.d.vue.ts`/`Comp.d.svelte.ts` declaration carrier the probe reaches first, enforced by the Rust guard `component_bare_import_resolves_to_declaration_carrier`, while the `.vue.tsx`/`.svelte.tsx` IDE carrier is the separate self-diagnostics surface, never this bare-import target.)* If a future tsgo ships a static module-resolution-map API (#2824's other endpoint shape — client-pushed mapping, not a callback), the bare import could be mapped to a non-colliding carrier path without an overlay, which is also the **non-fail-closed dissolution** of the §2.2 Carrier-path conflict cases (a real same-path file or a same-stem rune); fail-closed holds until that API exists.

### 2.4 The TSC (batch typecheck) surface — a separate backend, not the LS plugin
The `vue-tsc`-equivalent whole-project typecheck is a **first-class deliverable with its own backend**, because **a tsserver language-service plugin does NOT load for the `tsc` command line** (LS plugins affect interactive editing only). The §2.2 plugin therefore cannot serve TS<7 batch typecheck at all, and the perf benchmark (a cold full-project run, §2.7) is a *TSC-surface* measurement.

The no-fork TSC path per engine:
- **TS≥7 (tsgo):** the same `--api`/`open_project` Program drives batch diagnostics over the configured Program with carriers as FS-overlay members (the same membership as §2.3, proven in Block 0). A `vue-tsc`-equivalent emits the **complete** diagnostic set, not semantic-only: per file the **syntactic** and **semantic** diagnostics (`get_syntactic_diagnostics` + `get_semantic_diagnostics`), plus the program-level **global/options/config diagnostics** (`get_global_diagnostics`, options diagnostics, config-file parse diagnostics) and any **declaration** diagnostics when the user config emits declarations — all classified through `ProviderPositionMapper` (generated-only spans suppressed, §2.7). Mapping a tsgo carrier diagnostic back to the `.vue` is the same fail-closed mapping as the LSP surface. This reuses one backend for both LSP and TSC on tsgo, and is what the §2.7 cold benchmark targets.
- **TS<7 (tsserver / `tsc`) — the MIRROR-HOST / compiler-host model ONLY.** Since no plugin loads, batch typecheck drives a **`ts.CompilerHost`/tsc-API driver** that re-roots reads so generated carriers live in a **mirror tree** — **the generated carriers NEVER touch the user's working tree** (no source-tree writes, no co-located sidecars; the user's checkout is read-only as far as Verter's batch is concerned). The precise filesystem/config model:
  - **Mirror-host carrier placement.** For `src/Foo.vue`, the carrier is materialised into a Verter-owned mirror root (e.g. `<mirror>/src/Foo.d.vue.ts` declaration carrier as the bare-import target, plus the `<mirror>/src/Foo.vue.tsx` self-diagnostics IDE carrier of §2.2), not next to the source. (On this TS<7 batch path the host `resolveModuleNames` override is a true resolution map — D7 — so the carrier path is not basename-probe-bound; Verter targets the same `.d.vue.ts`/`.d.svelte.ts` declaration identity as the engine surfaces for cross-engine parity, and the `.verter.ts` API carrier for referenced-project `.d.ts` emit per build mode below.) The driver's host `readFile`/`fileExists`/`getSourceFile` serve the mirror carriers and fall through to the real user tree for everything else; relative imports inside a carrier (`./bar`, `../lib/x`) resolve **identically to the same specifier from the source's own directory** because the host's `resolveModuleNames`/`resolveModuleNameLiterals` re-roots resolution into the user tree (or the mirror is overlaid via `rootDirs`), so `baseUrl`/`paths`/relative/`node_modules` resolution is byte-for-byte the user's — with **zero working-tree mutation**.
  - **A `.x` → companion module redirection** is required so `import C from "./C.vue"` resolves to the carrier. **`paths`/`baseUrl` do NOT solve this (B3):** per the TS module-resolution docs, `paths` mappings apply only to **non-relative (bare) module specifiers** — a relative `import "./C.vue"` is never matched by a `paths` entry. The mirror-host model uses the **host `resolveModuleNames`/`resolveModuleNameLiterals` override** on the `ts.CompilerHost`/tsc-API driver to map the `.x` specifier to its companion (resolver-version-independent — it does not rely on stock `tsc`'s appended-extension probing); `rootDirs` may overlay the mirror as a secondary aid. Verter's import lowering may *also* reference the companion via `CodeTransform` (never text-splice). `paths` is reserved for bare/aliased specifiers only.
    - **Proof scope (D7):** the host `resolveModuleNames` override (the mechanism above) is **resolver-version-independent** and does NOT depend on stock `tsc`'s appended-extension behavior, so the tsgo GATE-4 extension-probing result is NOT assumed to transfer to the JS `tsc` resolver. The Block-4 spike validates that the host-override carrier resolution matches the user's own diagnostics on a `composite`+reference+`paths` fixture.
  - **The generated tsconfig (consumed by the driver, served from the mirror) `extends` the user config** and changes only what is required: it adds the carrier companions to a `files` list (or `include`), and **preserves `rootDir`, `outDir`, `composite`, `declaration`, `declarationDir`, `types`, `lib`, `paths`, and `references` verbatim from the user config**. The injected companion entries are **config/options-diagnostic-invisible** exactly as the §2.3 tsconfig-virtualization identity model requires (the batch promises the user's own config/options diagnostic set); `rootDir` stays valid because the mirror re-roots the carriers under it.
  - **Emit/invocation mode is reference-dependent (the `noEmit` + references incoherence is fixed here).** A referenced project is consumed through its emitted `.d.ts`, and `noEmit` produces no such boundary — so forcing `noEmit` on a referenced project breaks cross-project resolution (and contradicts §2.6's `disableSourceOfProjectReferenceRedirect: true` mode, which is exactly "use the `.d.ts` boundary"). Therefore:
    - **No project references:** invoke the driver in `noEmit: true` diagnostics-only mode — nothing written.
    - **With project references:** invoke in **build mode** (`tsc -b`-equivalent through the driver), which respects `composite` and **emits each referenced project's real `.d.ts`** so the referencing project resolves it the way the user's own build does. `noEmit` is **not** forced on referenced projects; the leaf being type-checked may still be `noEmit`. Emitted `.d.ts`/`.tsbuildinfo` are written into the **mirror tree** (a Verter-owned `tsBuildInfoFile`/`outDir` under the mirror root), never the user's working tree — the Block-4 spike validates the mirror-emitted boundaries match the user's own `tsc -b` diagnostics.
    - **§2.6's source-of-project-reference redirect is a LANGUAGE-SERVICE (LSP) feature, not a CLI-build one** — do not conflate the two surfaces. On the **batch** path, build mode consumes a referenced project **through its emitted `.d.ts` boundary regardless of the redirect setting** (build mode does not source-redirect); `disableSourceOfProjectReferenceRedirect` only affects the LSP/editor surface (§2.3, where the in-memory source carrier can be the resolution target). So on the batch path the model is uniform: build mode emits each referenced project's `.d.ts` (including the `CarrierApi`-equivalent declaration for a referenced `.vue`) and every cross-project import resolves through it. The LSP surface (§2.3/§2.6) is where the default-vs-`disable…` distinction (source carrier vs `.d.ts`) actually applies. No virtual-`.d.ts` channel is needed because build mode produces the real one in the mirror.
  - **Project references** are otherwise followed as the user declares them; a referenced project's carriers are materialised in **its own mirror subtree** under its own generated tsconfig, and the referencing project's generated tsconfig points `references[].path` at the **referenced project's generated (mirror) tsconfig**.
  - *(This mirror-host physical-carrier path is also the §2.8 fallback for any TS≥7 workspace where `--api` batch diagnostics prove insufficient.)*
  - **Why mirror-host, not source-tree sidecars (the rejected alternative):** co-located gitignored sidecars would touch the user's working tree (perturbing file watchers, other tools, or a read-only checkout) — that intrusiveness is exactly why the source-tree sidecar model is **rejected** (see §4). The Block-4 spike validates the mirror-host model against the user's own `tsc -b` diagnostics on a `composite`+reference+`paths` fixture (both with and without `disableSourceOfProjectReferenceRedirect`); it does not bake off against sidecars, which are off the table.

**Minimal/cheap Verter footprint for the TSC surface (A6).** The batch typecheck must run a **lean** Verter — only what carrier codegen + driving the engine needs — because the cold run's only Verter-owned lever is doing less non-checker work (§2.7), which is exactly the budget the self-referential gate holds against the baseline. The TSC footprint **includes**: the framework adapter's carrier codegen, the VFS/source read, ownership resolution (§2.6), the generated-tsconfig/compiler-host driver, and the `ProviderPositionMapper` for diagnostic mapping. It **excludes** the LSP/interactive machinery: the editor session/`SyncCoordinator`, the LSP server + document registry, the interactive query de-dupe/cancellation lanes (§2.7), the SHARED-mode attach path (§2.10), the **eager-`CarrierApi` auto-import INDEX** (§2.7 — auto-import is an editor feature; the *index* is not built for batch), inlay/semantic-token/hover scaffolding, and the `ProviderSurfaceStore`'s editor-rename history. The reduced host instantiates only the carrier-store **cache layer** (the §2.1/Block-2 content-addressed slots — including the leaf diagnostic-carrier slot it reads, the single `CarrierIde` slot — the provisional `CarrierBatch` slot was merged away, §2.1), not the full LSP `ProviderSurfaceStore` with rename history (reconciling A6's exclusion with B6's storage slot).
- **Which carrier(s) batch generates — depends on references (D5, reconciling A6 with §2.4's build mode).** The **leaf** project under check uses the single **`CarrierIde`** diagnostic carrier (the provisional `CarrierBatch` role was merged away — §2.1). But when project references are present, build mode **emits each referenced project's `.d.ts`** (§2.4), and a referenced project's `.vue`/`.svelte` needs a **declaration carrier** to emit from — that is the **`CarrierApi`** surface (the macro/adapter-derived public declaration). So batch generates `CarrierApi` (the `.d.ts`-producing surface) for **referenced** projects' carrier sources, and the `CarrierIde` diagnostic carrier for the leaf being diagnosed. (`CarrierIde` is diagnostics-only and not declaration-equivalent, so it cannot stand in for a referenced project's emit — `CarrierApi` is the distinct declaration role.) The eager-`CarrierApi` *index* is still excluded (that's the auto-import accelerator); batch generates `CarrierApi` *carriers* on demand for the reference closure it must emit declarations for.
Concretely the TSC entry point constructs a reduced host (carrier codegen + VFS + cache layer + engine driver) rather than the full LSP host, so a `vue-tsc`/`svelte-check`-equivalent run carries no per-keystroke/interactive overhead. This is the footprint the §2.7 cold perf gate measures.

Both TSC variants are fail-closed and version-gated exactly like the LSP surface; a `.vue` with `NoProject`/`Ambiguous` ownership is excluded from the batch run rather than checked under a synthesised config.

### 2.5 VFS-driven incrementality; one Program per tsconfig (reuse PROVEN — Block 0)
The VFS is the authority for source + carrier artifacts + source-maps + generations + project ownership. Provider sync is a pure **projection**:
1. source edit/disk change enters the VFS → bump generation;
2. ownership resolves to a `ProjectBinding` (or `NoProject`/`Ambiguous`/`SyntheticScratch`) per the §2.6 algorithm;
3. carrier looked up by its content-addressed key (§2.7); if absent, compiled **once** from the shared parse into IDE carrier + source-map + (lazily) IDE TSX, with the public-API surface eagerly indexed per §2.7;
4. the sync planner computes per-project **deltas** (changed/removed carriers + resolution-map delta + fs generation), AND forwards every dependency-closure generation bump (§2.7 — a dependency change is the engine's to re-check, not Verter's to suppress);
5. the adapter applies **one atomic batch per project**;
6. queries are allowed only after the engine acknowledges the matching generation/epoch.

One persistent workspace session, with **one configured Program per tsconfig, reused — now PROVEN for tsgo** (Block 0, GATE 3): a carrier-only edit pushed as `update_snapshot({ open_project, file_changes: { changed: [carrier] } })` flips diagnostics on the **same stable project handle** (`p.<canonical-tsconfig-path>`, unchanged across the edit); an **unchanged dependency keeps its source-file identity** (retained, not re-parsed); and a redundant identical delta returns an **empty `changed_files`** because tsgo **content-hashes** and reports nothing changed (content-addressed incremental invalidation — it does not blindly trust the `changed` hint). tsserver configured projects reuse Program structure by construction. Correctness still **never** depends on Program identity: if a future engine rebuilds, results stay correct (just slower) and the §2.7 perf gate is re-derived per §2.8. Ordinary `.vue` edits bump only that carrier version (push a per-file `file_changes.changed` delta); tsconfig/lib/types/project-reference changes bump the **project** generation and invalidate the whole configured project (`invalidate_all` or re-`open_project`). No owner / ambiguous owner ⇒ no external TS result (Verter-native non-TS features may still answer).

### 2.6 Project ownership, project references, and solution-style configs
Ownership resolution must match TypeScript's own configured-project semantics, **not** literal glob membership of the `.vue` path (which fails because `.vue` is not a known extension — §1). The resolver:

1. **Parses configs with TS-equivalent rules** — `files` / `include` / `exclude`, `extends` chains, and the implicit default include.
2. **Computes `.vue` ownership by the SAME extension rules TypeScript applies — `.vue` is NOT picked up by an extension-specific glob.** Automatic supported-extension expansion (`.ts`/`.tsx`/`.d.ts`, `.js`/`.jsx` iff `allowJs`, **plus declared `extraFileExtensions`**) happens ONLY when an `include` glob's last segment has no extension and no extension-bearing wildcard — i.e. a directory glob (`"src"`) or a bare star (`"src/**/*"`). An extension-specific glob like `"src/**/*.ts"` matches **only** `.ts` and does **not** expand to `.vue`. So a `.vue` is owned by a configured project ONLY when one of these holds: (a) the **default include** (no `files`/`include`); (b) a **no-extension directory/bare-star glob** that covers it (`"src"`, `"src/**/*"`); or (c) a **glob or `files` entry that explicitly covers `.vue`** (`"src/**/*.vue"`). Under `"include": ["src/**/*.ts"]`, the sibling `.vue` is **NOT** a member ⇒ `NoProject`. (This is also why the tsgo carrier-discovery of §2.3 works for the component IDE carrier — `Foo.vue.tsx`/`Foo.svelte.tsx`: its final `.tsx` extension matches a `.tsx` glob or the default include, so the carrier is enumerated even though the bare `.vue` is not — and a project whose config does NOT enumerate the carrier extension reaches it via §2.3 tsconfig-virtualization. Note these are two SEPARATE facts: the `.vue` SOURCE ownership follows the §2.6 extension rules above (a `.ts`-only glob does not own the `.vue`), while the COMPANION reachability is the §2.3 discovery mechanism; the ownership resolver records the source-ownership case and the adapter selects the matching discovery mechanism. The redirect-reached `.verter.ts` API carrier is NOT enumerated — it is resolved on demand via the §2.6 project-reference redirect, so its reserved infix never needs to match a glob.)
3. **Solution-style (referenced-only) roots resolve to a leaf project**, never to the solution root: the owner is the leaf configured project whose include/files claims the file (by the rules in step 2). Two leaves claiming one file with no deterministic winner ⇒ `Ambiguous` ⇒ fail closed (this must be rare; a common monorepo layout has exactly one leaf per file).
4. **Carrier-path conflict ⇒ `Ambiguous` ⇒ fail closed (the carrier path is in the USER namespace — §2.2).** Even when steps 1–3 resolve a clean `ProjectBinding`, a carrier cannot be served if its target path collides with real user resolution. The carrier-companion path (`{name}.vue.tsx` / `{name}.svelte.tsx`) is **not a Verter-reserved namespace**, so the ownership resolver records two model-conflict cases that downgrade the source to `Ambiguous` (no external-TS result; Verter-native features may still answer) — the full model + guards (`carrier_never_shadows_real_user_file`, `same_stem_svelte_component_rune_fails_closed`) live in §2.2's Carrier-path conflict model: (a) a **real user file at the exact carrier path** — Verter NEVER overlay-shadows it; (b) a **same-stem Svelte rune** (`Foo.svelte.ts` beside `Foo.svelte`) that the GATE-5 `.svelte.ts`-before-`.svelte.tsx` probe reaches first — a DETECTED ambiguity, never a silently-wrong edge. The non-fail-closed dissolution (a future static module-resolution-map API redirecting to a non-colliding carrier path) is the recorded future enhancement; fail-closed holds until it ships (§2.2/§2.8).

**Project references / `composite` / `disableSourceOfProjectReferenceRedirect`.** A `.vue` in package `B` imported from package `A` is reachable through **two** Programs with **redirect-dependent** resolution, which the single-valued ownership of step 2 cannot express alone. Per the TypeScript docs, in 3.7+ the **source of truth is the referenced project's TypeScript source**, and `disableSourceOfProjectReferenceRedirect` reverts to the pre-3.7 behaviour where the `.d.ts` is the module boundary:
- **DEFAULT (redirect ON, `disableSourceOfProjectReferenceRedirect: false`):** `A`'s import of `B`'s `.vue` resolves to `B`'s **SOURCE** — i.e. `B`'s full IDE carrier (`CarrierIde`, §2.1) — so `A` sees `B`'s live source types. The adapter must make `B`'s carrier visible to `A`'s Program (publish it into both `B`'s and `A`'s Programs).
- **`disableSourceOfProjectReferenceRedirect: true` (pre-3.7 boundary):** `A` resolves to `B`'s **declaration output** — for a `.vue` that is the **macro-derived public-API surface** (`CarrierApi`), which Verter presents as `B`'s emitted-`.d.ts`-equivalent (no `.d.ts` is written to disk; the surface is served virtually to `A`'s Program and content-addressed). `B`'s own Program still uses its full IDE carrier.
- Each referenced project is published with its **own** ownership, API surfaces, and invalidation generation. Where no faithful mapping exists, **fail closed** for the cross-package query rather than guess.

**Ownership ≠ discovery — two steps, bridged by the §2.3 overlay mechanisms.** Step 2 decides whether a `.vue` is *owned* (a member of a configured project). Making its *component IDE carrier* reachable by the engine is a separate step with **two concrete mechanisms by config shape** (fully specified in §2.3): for **any config whose enumeration matches the carrier's `.tsx` extension** (the default include, a directory/bare-star glob, OR an extension-specific `.tsx` glob — the case Block 0 proved), the FS overlay surfaces it directly; for a `.vue`-specific `include` or a `files` list that does NOT enumerate `Foo.vue.tsx`, the adapter **virtualizes the tsconfig** (the first-class identity model of §2.3 — own virtual-config hash/`project_identity`, injected roots config/options-diagnostic-invisible, explicit invalidation; overlay-serves a `read_file` of `tsconfig.json` with `include`/`files` augmented by the companion paths — never touching the user's real config). For tsserver, `getExternalFiles` returns the companion for the configured project (same effect). So "owned" (§2.6) and "discoverable by the engine" (§2.3/§2.2) are always reconciled: ownership is computed by the §2.6 extension rules; the companion is then surfaced by the matching §2.3 mechanism, independent of glob shape.

Verter's `verter_workspace` ownership must be extended to encode (a) the carrier extension as a member-extension, and (b) reference-graph awareness; until it does, the §1 "no owner ⇒ no TS" rule would mis-fire on legitimate `.vue` files. This is Block 1/3 work, gated by the §3 ownership fixtures (including the `.vue`-specific-`include` and `files`-list discovery cases).

### 2.7 Performance: do less *non-checker* work — and never less *checker* work than correctness requires

*Host-mode / resource-policy design (the systems-layer lever this gate measures): see [host-mode-perf-design.md](./host-mode-perf-design.md). PERF-0 lands its carrier-byte + diagnostic-set parity oracle.*

Both engines are checker-bound on the same tsgo, so equal work is at parity. The durable win is doing less work **around** the checker, with a hard line: Verter may skip **re-codegen** and redundant **transport**, but it must **never** suppress an engine re-check that a type change requires. The two decisions are split:

**(a) Carrier *regeneration* skip (Verter's decision — safe).** Keyed by the orthogonal env dimensions the carrier text depends on: `source_content_hash + parse_env_hash + (codegen) compile profile + file_language_row + helper/runtime_version` (R21 — no single bundled hash). If this key is unchanged, **do not regenerate the carrier and do not re-send its text to the engine.** This is strictly less work than vize, which regenerates virtual TS per request. "Carrier-hash-stable" means *reuse the cached carrier text* — it does **not** mean "the type result is still valid."

**(b) Engine re-check / notification (the engine's decision — Verter must not suppress it).** Once a carrier is a real configured-project member, the engine's Program owns cross-file type invalidation. A carrier can be byte-identical while its *types* changed — a dependency `.d.ts` edit, a sibling `.vue`'s public-API surface change, an `@types`/`lib`/tsconfig change, a `paths` remap, a package upgrade. Therefore Verter **forwards every dependency-closure VFS-generation bump** to the engine and **never** gates a re-check on "carrier text unchanged." Concretely, the carrier-regeneration cache (a) carries a separate `import_signature_hash` (the hash of the carrier's resolved import surface); when a dependency's generation advances, the dependent's `import_signature` is re-evaluated and the engine is notified even though the carrier *text* is cache-stable. This mirrors the project's fact-based-cache discipline (`ReadSetSignature` — cache correctness is read-side authoritative, revalidated against the live view on every warm hit; never cache on path alone).

**Source-map changes (C3 — corrected).** A `CodeTransform`-built source-map is derived from the same chunk list that produces the text, so a map change with byte-identical carrier text is essentially impossible *except* a helper-preamble metadata-boundary move. The previous "map changed ⇒ don't re-check" claim is **withdrawn**: `map_hash` is part of the version-gate identity (below), so a `map_hash` change **invalidates every cached mapped result** keyed by the old map. Raw engine results are cached by `(carrier content_hash, project epoch)`; mapped results are cached by `map_hash`. On a map-only change, mapped outputs are dropped and raw spans are re-mapped through the new map **only if** the carrier content and project epoch still match — never remap a stale diagnostic through a new map.

**Other systems-layer wins:**
- **No post-hoc import rewriting** — the static resolution overlay (§2.3) keeps carrier text stable across graph changes.
- Per-project **batched** `publish_snapshot` (not per-file IPC).
- **Singleflight** carrier generation per canonical file and `ensure_surface(project, source, role, generation)`; concurrent hover/diagnostic/completion join one build.
- **Async wherever the engine permits; the tsserver/JS-LS exception is explicit (A4 + user-review P1) — not a "switch to async if bottlenecked" deferral.** The interactive lane is **async, priority-laned from the start** wherever the engine supports it: **tsgo** via the **`unstable/async` (JSON-RPC) `--api` client** for the typecheck/diagnostics surface, plus the **`--lsp` surface** for the interactive features (§2.3 dual-surface), with an **active-file priority lane** that preempts background work, so a keystroke's hover/completion/diagnostic is never head-of-line-blocked behind a project-wide pull. **Cancellation is surface-specific (Finding 1, corrected):** the `--api` wire has **NO wire-level cancellation** (verified — neither the shipped sync nor the async client wires a `CancellationToken`), so `--api` interactive/batch cancellation is **CLIENT-SIDE ABANDON-ONLY** — drop the pending waiter, discard the eventual response, and skip not-yet-sent requests; the engine keeps computing because it cannot be told to stop, and true mid-flight preemption on `--api` is a process restart. The async client buys **concurrency / non-blocking**, NOT a wire cancel. The **`--lsp` surface uses LSP `$/cancelRequest`** (real protocol cancellation) for the interactive features it serves. **Explicit exception (A4, D8-tightened): the tsserver / in-context JS language service drives SYNCHRONOUS language-SERVICE APIs** — the `ts.LanguageService` host-callback methods and tsserver's `LanguageServiceHost` are synchronous *by API contract* (a host read returns a value, not a promise), so the *checker invocation* for one query executes synchronously and cannot be "made async." (Precise, not sloppy: the tsserver *protocol* is request/response and cancellable, and Verter still runs the tsserver subprocess transport I/O asynchronously; it is the language-SERVICE API — not "the protocol" — that is synchronous.) Preemption uses the **TS cancellation token** (`--cancellationPipeName` for the tsserver process; the host's `getCancellationToken`/`ThrottledCancellationToken` for the in-context LS) instead of async cancellation. (The tsgo `unstable/sync` client is likewise acceptable only for the Block-0 gate and the batch/TSC baseline, where one-request-at-a-time is fine.) Query **de-dupe + cancellation** keyed by `(project, provider_uri, carrier_offset, feature, content_hash, map_hash, required_version, feature_param)` — the FULL fail-closed query identity: `required_version` keeps a query against a newer snapshot from joining a stale in-flight slot (a byte-identical re-sync advances the generation while preserving `content_hash`/`map_hash`), and `feature_param` (e.g. a rename's new-name hash) keeps two parameterized queries at the same offset distinct. Cancellation is surface- and engine-specific: on tsgo's **`--api`** (typecheck/diagnostics) surface it is **client-side abandonment only** (no wire cancel exists — drop the waiter + discard the response + skip unsent requests; the engine finishes its in-flight compute regardless), while tsgo's **`--lsp`** (interactive-feature) surface uses real **LSP `$/cancelRequest`** to preempt in-flight feature work; tsserver/JS-LS cancel via the TS cancellation token. A superseded generation therefore abandons in-flight `--api` work and `$/cancelRequest`-cancels in-flight `--lsp` work. The de-dupe registry ELIDES the duplicate engine query for an identical in-flight key and shares one cancellation token across the join group; broadcasting the leader's RESULT to joiners is the engine backend's concern (the registry is de-dupe + shared cancellation, not itself a result rendezvous).
- **Version-gated, multi-file-aware responses (C12).** A stale result is dropped, never mapped through a non-matching source-map. Provider epoch is encoded into script versions; the engine/project epoch is captured **before and after** each request and the result is dropped if **any touched provider file or map** changed mid-flight (not just the queried file — rename/find-references/definition return multi-file spans that can span epochs). **Every returned span/edit is classified** as `source-mappable` (mapped back to the `.vue`), `generated-only` (a synthetic helper region with no `.vue` correlate — **suppressed**), or `external` (a real on-disk `.ts` — returned as-is). Generated-only spans never escape.

**Surface generation — lazy IDE, EAGER public-API index, on-demand materialization under redirect (C8).** Full IDE TSX (`CarrierIde`) is generated lazily for open/diagnosed/queried carriers. The macro-derived **public-API surfaces (`CarrierApi`) for ALL project-owned `.vue` files are generated and import-indexed up front** — TypeScript auto-imports and find-all-references draw from the project's indexed export surfaces (the auto-import provider project), so a closed `.vue` whose API surface is missing would vanish from completions and references. **But "lazy `CarrierIde`" must not starve the default project-reference redirect:** under the DEFAULT redirect (ON, §2.6), a cross-package import of `B/Foo.vue` from `A` resolves to `B`'s **source** carrier (`CarrierIde`), so resolution of such an import is itself a **materialization trigger** — the referenced `CarrierIde` is generated on demand when `A`'s Program resolves the import (it is "lazy" only in the sense of *not generated before any consumer needs it*, never "absent when a member Program references it"). Equivalently: the eager index covers `CarrierApi` for every owned `.vue` AND the `CarrierIde` head of every `.vue` that is *imported across a redirect-ON reference*. Only the IDE TSX of a carrier that no member Program references stays lazy; the lightweight API surface is always eager. **Materialization-ordering rule:** the on-demand `CarrierIde` must be generated and published to the overlay **before** the engine first observes `file_exists`/`read_file` for it — otherwise a cold read returns "absent" and the engine can pin a sticky negative resolution (the same poisoning class as §2.2 on tsserver). The redirection/sync path therefore materializes the referenced carrier as part of resolving the import (synchronously w.r.t. the engine's FS probe), never lazily-after-the-probe.

- Background population is **priority prewarm, not correctness** (active file + dependency closure first); `Arc`-cached source-map tables.

**Cold-path strategy — minimize the per-carrier non-checker overhead.** On a cold full-project run the carrier-regeneration cache is empty, so every carrier is codegen'd once; the way to keep the cold non-checker budget low (and to keep it from regressing against the pinned baseline, §2.7) is to make Verter's *one* cold codegen + sync cheap AND amortize it across the batch. The cold pipeline therefore:
- **Parallel carrier codegen through `verter_scheduler` (A9).** Do not hand-roll thread pools — route through **`verter_scheduler`**, which already owns BOTH the **rayon CPU pool** and the **tokio I/O runtime** and provides the CPU-vs-I/O routing (`/scheduler`: `submit_request`/`submit_batch`, the scheduler-owned `cpu_pool` + the host-owned `HostCpuPool` coordinator shared by every host batch API). The shared parse + carrier codegen (CPU-bound, embarrassingly parallel) is submitted as CPU-lane work and fans out to a single batched engine snapshot rather than per-file opens; engine transport I/O (the `--api`/stdio channel) and the §2.7 async interactive lane are I/O-lane work. Stated once for the whole doc: **all carrier codegen / source-map build / hashing → `verter_scheduler`'s CPU (rayon) lane; all engine/transport I/O + the interactive lane → its I/O (tokio) lane** — never block a tokio worker on CPU codegen or a rayon worker on engine I/O. This reuses the existing scheduler (the shared owner layer per CLAUDE.md), not a second pool.
- **The cold TSC surface reads the single `CarrierIde` carrier.** The design contemplated a provisional minimal-diagnostic `CarrierBatch` role (§2.1) that would carry the full script surface AND every type-observable template-expression construct (interpolations, directive/attribute expression values, `v-for`/`v-if`/`v-bind`/`v-on`/`v-model`/`v-slot` expressions) plus the import/redirection shape, while OMITTING the interactive-only IDE embellishments (inlay/semantic-token scaffolding, hover-only helper regions). The measurement found **no material cold-perf gain and no valid diagnostic-preserving minimal codegen profile**, so `CarrierBatch` was **merged into `CarrierIde`** and the `carrier_batch_typechecks_same_as_ide` guard was **removed**. Because the cold path now reads the SAME `CarrierIde` surface the interactive path type-checks, it can never silently drop a type-observable template-expression construct (honoring the Carrier IDE TS Surface Principle: every supported template expression is still type-checked).
- **Lazy source-map construction on the cold path** — the source-map table for a carrier is built only if/when a diagnostic actually lands in it (most cold-clean files never need their map materialized), versus eagerly building every map.
- **A precomputed overlay/resolution manifest** handed to the engine once, so the FS-overlay + `.vue`→companion redirection set is not recomputed per file during the cold sweep.
These let the cold TSC run do measurably less non-checker work than a per-request regenerator while running the identical tsgo checker.

**Carrier pre-compile-to-warm — a FLAGGED, measured experiment, NOT a baseline (A7).** An opt-in experiment (behind a flag, default off): proactively compile/warm carriers into the VFS-resident carrier store **ahead of the engine's demand** (e.g. on workspace open, warm the active file's import closure, or the whole project for a batch run), so the engine's first touch hits a ready carrier instead of triggering codegen. The eager-`CarrierApi` index (below) already does a bounded version of this for auto-import; the experiment generalizes it to the full carrier set (`CarrierIde` — the provisional `CarrierBatch` role was merged away, §2.1). It is **implementation-validated, not assumed**: shipped only if measured to improve cold/warm latency without a memory regression on the perf corpus; the baseline design never *depends* on pre-warming for correctness (carriers are still generated lazily-on-demand if the flag is off). Pre-warm runs on the rayon pool (A9) and respects the §2.7 cache invalidation (a pre-warmed carrier is just a cache fill, subject to the same content-hash/dependency invalidation).

**Perf gates — a SELF-REFERENTIAL regression gate (Verter candidate vs a pinned Verter baseline), measurable, statistical, and hermetic.** The CI perf gate is **self-referential**: it compares a **candidate** Verter build against a **pinned-baseline** Verter build on the **same** runner / job / corpus / tsgo / thread regime (axis-A thread-pinned, axis-B subprocesses machine-default — identical both sides; see the Tooling protocol), interleaved, and gates **ratios** (candidate/baseline) — never absolute milliseconds, which are too noisy on shared CI hardware to be a pass/fail truth. It covers **BOTH axes**, both Verter-vs-Verter-baseline and **vize-free**:

- **AXIS A — the compiler axis.** Verter's OWN native compiler (`verter_compiler` via NAPI) SFC→carrier **codegen throughput**, measured as a **SERIAL per-file `compileWithAudit` loop** (each SFC compiled one at a time, not a whole-corpus or concurrent call) — the candidate-vs-baseline RATIO is valid because both sides run the IDENTICAL serial orchestration; tsgo is not involved. Gated on a codegen-throughput-regression predicate over the empirically-present audit signals (files/sec ratio + generated-carrier-count + output-bytes + source-map-bytes + the codegen(+source-map) emit-time split + the carrier+source-map content hash); per-PID peak RSS and the full non-checker aggregate are DEFERRED (see the manifest `deferred`).
- **AXIS B — the typecheck axis.** Verter+tsgo carrier typecheck/LSP — the five §2.7 workloads below — gated against the pinned Verter baseline.

`vize` is **OFFLINE-INFORMATIONAL only, for BOTH axes**, and is in **NEITHER CI gate** (see "Offline vize comparison" below). The gate's correctness rail asserts diagnostic-SET equality between the **candidate and the pinned Verter baseline ONLY** — it does **not** invoke `vue-tsc`/`svelte-check` as an external oracle (cross-tool diagnostic parity against them is a separate, non-gate compatibility concern, not enforced here). The historical headline "20–84×" was multi-threaded-`vize` vs single-threaded-`vue-tsc` on a partial checker (≈13× at equal threads on a 15k-SFC corpus) — that is `vize`-over-`vue-tsc` *context*, not a Verter target. The gate is measurable, not hand-wavy: every threshold below is a numeric ratio against the pinned baseline on the **same machine, same run**.

**The gate's pass/fail predicate (conservative — a thresholded, statistically-significant regression predicate).** For each gated metric, FAIL only if `statisticRatio(candidate, baseline) > threshold` **AND** the **bootstrap 95% CI lower bound** on the ratio (the 2.5th percentile of the resampled ratio distribution) also exceeds the threshold (so pure CI-host variance, which widens the CI downward, cannot trip the gate). The bootstrap resamples POOLED per-operation values and does NOT model per-run clustering, so on strongly correlated per-run noise the CI can be over-confident — but the bias is toward a false RED (a spurious regression flag), the SAFE direction, never a false green; a cluster-aware bootstrap is a tracked follow-up (§2.7.1). The statistic is the **median** for time/throughput/RSS scalars and the **named percentile (p50/p95/p99) over the POOLED per-operation latency distribution** for tail-latency metrics (the percentile is genuinely computed over the pooled distribution — never collapsed to the median). The ratio is a ratio of per-side statistics; the interleaving balances drift, it is not a paired per-sample comparison. ≥ 7 samples/side for the nightly blocking gate. On a **FULL** (non-smoke) run a skipped/unavailable workload, a degenerate (all-zero) gated metric, an engine-version mismatch, or an armed run that fell back to self-check are HARD FAILS — the gate never reads a misconfiguration or missing instrument as green. The gate **GATES the axis-A Verter-owned codegen overhead** — codegen(+source-map) emit time, codegen throughput, carrier output count, output + source-map bytes, and the carrier+source-map content hash (the audited compile's own measured signal) — **PLUS the axis-B END-TO-END regression signals**: the carrier-typecheck exit-code + diagnostic-SET correctness, the interactive/warm LSP latency distributions, and the IDE-query hover/completion content equality (the `verter-tsc` child peak RSS is DEFERRED — the wrapper-PID misses the tsgo child, see the manifest `deferred`). The axis-B signals are **whole-pipeline (Verter + tsgo) end-to-end measurements, NOT a Verter-owned attribution** — the Verter-vs-tsgo phase split that would isolate Verter's share is DEFERRED (see the manifest `deferred`), so "Verter-owned overhead/attribution" names ONLY the axis-A codegen/source-map emit signal. The gate does **NOT** gate cold total wall-time, which is tsgo-checker-dominated and noisy (reported, not gated). The committed baseline manifest (`packages/benchmark/baselines/block6.json`) holds the methodology version, the pinned baseline ref, the corpus content hash, the exact tsgo pin (verified against the resolved engine), the thread-count policy, the per-workload thresholds, and a `deferred` list of follow-ups (mostly Rust-bearing axis-A/axis-B attribution + instrumentation, plus the TS-side cluster-aware-bootstrap arming prerequisite); the gate refuses to run on a corpus-hash mismatch unless the manifest is refreshed in the same change.

**Arming lifecycle (the honest end-state).** A PENDING `baselineRef` is physically incapable of a green *armed* verdict: the gate forces self-check mode and HARD-FAILS a non-self-check invocation against an unpinned baseline. The **SCHEDULED nightly blocking run fails RED-until-armed** while `baselineRef` is PENDING — that is the intended honest state, not a green self-check — while a manual `workflow_dispatch` run (and a local / on-demand `--smoke` run) executes the same-commit self-check green. An *armed* comparison REQUIRES `--baseline-root`: the baseline tsgo engine is resolved from that separate worktree and is **never** borrowed from the candidate root. Because a squash-merge SHA cannot self-reference at author time, the baseline is **armed by a subsequent `perf: refresh baseline` change** (not the landing change itself) that pins the real baseline commit SHA (see `packages/benchmark/baselines/README.md`).

**Out of scope.** Verter's component-meta / `SemanticGraphStore` type-resolution is OUT of this workstream's perf scope — that engine serves component-meta, and its perf is governed by the component-meta corpus gates, not this external-TS-engine gate.

**Corpus (fixed, pinned, hermetic).** A committed, version-pinned synthetic corpus (no third-party checkout — Testing-Hermeticity): **15,000 SFCs** across **~600 modules**, with a realistic shape — a mean of **~8 imports/SFC**, cross-file type edges (props/emits types imported across files), at least one **`composite` project-reference closure** (so the redirect-ON `CarrierIde` and `disable…:true` `CarrierApi` boundaries are both exercised), a `paths`/`baseUrl` alias layer, and a `lib` floor (explicit empty `types: []` — no ambient `@types`, by design). The generator emits POSIX paths + LF content, so the committed content hash is byte-identical on every OS; its content hash is recorded with each result so a corpus change is never silently a "perf improvement". **Block-6 perf scope is Vue `.vue` SFCs ONLY** — the corpus generator, the axis-A carrier-discovery (`collectVueFiles`), and the LSP workloads (`firstVue`/`countVue`) all target `.vue`; the perf gate makes **no claim of current Svelte perf coverage**. Svelte (`.svelte`) carriers are a later block (B8), so a Svelte perf corpus + a carrier-extension discovery layer is **DEFERRED** until Svelte LSP/IDE support lands (see §2.7.1). (The framework-general `vue-tsc`/`svelte-check`-equivalent framing elsewhere in this doc describes the ENGINE/TSC surface's capability, not the Block-6 perf corpus, which is Vue-only.)

**Tooling protocol (identical for candidate and baseline).** Same machine, same tsgo binary, **identical thread regime** (axis-A's in-process native host is thread-PINNED to N via `hostCpuThreads`, N = `--threads`, default `os.availableParallelism()` — logical; the axis-B subprocesses — `verter-tsc`, `verter_lsp`, and the tsgo child — do NOT accept a thread-pin flag through the harness, so they run at MACHINE-DEFAULT parallelism, NOT a harness-enforced fixed count — identical on both interleaved sides; N is recorded for the axis-A pin + provenance, not as an enforced subprocess setting — see the manifest `deferred` for the thread-pin follow-up), warm OS file cache, candidate and baseline runs **interleaved** (`baseline, candidate, candidate, baseline`, repeated) so any monotonic drift balances across the two sides. **≥ 5 runs per workload (≥ 7 for the nightly blocking gate)** reporting **median + p95** (interactive workloads additionally p50/p99). The comparison is always **candidate vs pinned-baseline** — both Verter builds; there is no cross-tool performance reference in CI. **The diagnostic SET is asserted equal between candidate and baseline ONLY** — the gate invokes no external `vue-tsc`/`svelte-check` oracle (those remain the conceptual compatibility TARGET, but the gate does not run them). **Cold vs warm is explicit:** *cold* = a fresh process with an empty carrier-regeneration cache and no Program (every carrier codegen'd once); *warm* = the persistent session with the carrier cache populated and the Program retained, then the measured edit/query applied.

**Memory ceilings — DEFERRED (not a gated metric today).** A bounded resident set is still a design goal (the carrier store + source-map tables are the only structural additions and must stay bounded; the pre-warm experiment A7 must show no RSS regression vs the flag-off baseline or it does not ship), but it is **not gated by the perf gate**. `verter-tsc` spawns tsgo as a **separate child process** (`crates/verter_tsc/src/checker.rs` `invoke_checker`: `std::process::Command::new(checker_bin).arg("--project")…spawn()`), so the harness's wrapper-PID `VmHWM` sample (Linux `/proc`) measures only `verter-tsc`'s own codegen resident set and **misses the tsgo type-check engine's (dominant) memory** — gating that wrapper-PID figure would be a memory metric that misses the engine. Full subprocess-**tree** peak RSS is not cleanly portable in TypeScript today (`/proc` is Linux-only; a summed per-PID `VmHWM` is not a faithful tree peak; Windows/macOS expose no equivalent), so the cold + warm-incremental `peak_rss_ratio` was **removed from the gated set** and DEFERRED (see the manifest `deferred` and §2.7.1). `rssBytes` is still recorded raw in the artifact (wrapper-PID only); no metric gates it.

**Overhead attribution (the axis-A non-checker budget).** The axis-A result attributes time to **(i) Verter codegen** (carrier generation), **(ii) source-map build**, and **(iii) producer parse/transform + store/capture/serialize transport** — honestly named for the audit fields that exist; there is NO dedicated "hashing/cache/sync" timing bucket in the substrate today, so the gate does not pretend one exists (a dedicated bucket + a real source-map segment count are tracked Rust follow-ups, see the manifest `deferred`). Checker time (the tsgo invocation) is the dominant, ~constant term across the two sides at equal threads; the gate's lever and its pass/fail margin live in the codegen-side budget. The attribution reuses Verter's existing audit substrate: each side runs in its OWN child process loading THAT side's `@verter/native`, and the audited compile path (`compileWithAudit`) emits the **(i) codegen + (ii) source-map phase timings** plus output and source-map bytes and a CodeTransform-op count, consumed as a `RequestAuditRecord` — no new query-time instrumentation. The axis-A gate therefore gates the **MEASURABLE codegen(+source-map) emit-time sub-signal** ((i)+(ii), `codegen_time_ratio`) plus output/source-map bytes and the carrier-output invariant. The **(iii) parse/transform/transport phase timing** and the **per-PID peak RSS** are NOT populated by the compile audit record today (the in-process compile has no spawned child to RSS-sample and the footprint sampler is unarmed), so the **full non-checker aggregate** and **axis-A peak RSS** are honestly **DEFERRED** with named Rust follow-ups (see the manifest `deferred`), never faked from a coerced zero or a parallel measurement. The same non-checker split for the AXIS-B `verter-tsc` subprocess is **DEFERRED** (verter-tsc emits only `error TSxxxx` lines today; it needs a `--audit/json` mode — see `deferred`).

The AXIS-B workloads (each at machine-default parallelism, identical on both interleaved sides — the verter-tsc/verter_lsp/tsgo subprocesses do not accept a harness thread-pin; see the Tooling protocol). **Each gates the candidate's ratio against the pinned Verter baseline on the honestly-TS-measurable subset; the diagnostic SET is asserted equal between candidate and baseline ONLY (the gate invokes no external `vue-tsc`/`svelte-check` oracle). The Rust-requiring axis-B attribution is DEFERRED, not faked — see `deferred`:**
1. **Cold full-project typecheck** (`verter-tsc` fresh process) — gate the **exit-code + diagnostic-SET correctness** ONLY (a behavioral regression fails the gate); `total_wall_time_ratio` is **reported (≤ 1.25), not gated** (tsgo-checker-dominated). The child `peak_rss_ratio` is **DEFERRED** (verter-tsc spawns tsgo as a SEPARATE child, so the wrapper-PID `VmHWM` misses the engine's memory, and process-tree RSS is not cleanly portable in TS — see §2.7.1); the non-checker codegen split for the TSC surface, and a real carriers-generated count, are **DEFERRED** (need a `verter-tsc --audit/json` mode); the static `.vue` file count was REMOVED from the gated set (it never discriminated).
2. **Incremental re-typecheck** (on-disk carrier cache + a TYPE-CHANGING dependency edit) — `verter-tsc` is always a fresh process, so this is the on-disk (tsbuildinfo) incremental re-typecheck, **NOT** a retained Program: the measured edit retypes a USED field (so the dependent MUST re-diagnose) and the workload asserts the post-edit diagnostic SET actually transitioned (an ignored edit is a hard failure); gate the **exit-code + diagnostic-SET correctness** (candidate vs baseline on the post-edit set); `total_wall_time_ratio` (**≤ 1.12**) is **reported, not gated**. The child `peak_rss_ratio` is **DEFERRED** (same wrapper-PID-misses-tsgo reason as cold); the changed-carrier count is **DEFERRED** (needs a Rust per-edit changed-set counter).
3. **Warm incremental re-typecheck via the PERSISTENT LSP** — the genuinely-warm signal: ONE persistent `verter_lsp` client retains the Program across many edits. Each measured edit re-points an inline `import("./types").WarmDepProbe<i>` type annotation in the DEPENDENT SFC's OWN buffer at the next pre-declared alias, so every edit forces a warm CROSS-FILE re-resolution against the imported type module plus a dependent re-diagnose (genuinely cross-file — the erroring type lives in the imported module). It does NOT re-edit the imported module itself: repeated overlay edits to an imported module do not re-invalidate an already-open dependent under verter-lsp today (a one-shot cross-file-invalidation limitation — see §2.7.1). Gate `p50_latency_ratio` (**≤ 1.08**), `p95` (**≤ 1.12**), `p99` (**≤ 1.20**) over the pooled per-edit distribution + the diagnostic-SET correctness.
4. **Single-file-edit latency** (interactive) — drive MANY in-file edits against ONE persistent client; gate the REAL `p50` (**≤ 1.08**), `p95` (**≤ 1.12**), `p99` (**≤ 1.20**) over the pooled per-operation distribution, the diagnostic-SET correctness, and a **diagnostic-publication-locality** invariant: a single-file edit must NOT re-PUBLISH diagnostics for ~the whole project (a published-`publishDiagnostics`-URI proxy, NOT real invalidated/rechecked URIs — true LSP invalidation/recheck instrumentation is a **DEFERRED** Rust follow-up). The Verter-vs-tsgo phase split is **DEFERRED** (needs a per-phase LSP timing split).
5. **IDE query latency** (interactive) — drive MANY hovers and MANY completions as SEPARATE pooled distributions (a regression in one path cannot hide behind the other); gate each path's `p50`/`p95`/`p99`, require a non-empty hover (contents) + completion (items > 0) per measured op (a no-result query fails — a broken no-op LSP cannot pass), and gate candidate/baseline hit + item-count parity (two-sided). The candidate's hover **CONTENT** (normalized text per probed position) and completion **LABEL SET** are additionally compared candidate-vs-baseline for equality over a fixed deterministic set of probed positions — a content divergence at a probed position is a correctness regression **even when the counts match** (counts alone cannot catch a bogus-but-same-count answer). The Verter-vs-tsgo phase split is **DEFERRED**.

The AXIS-A workload (the compiler axis, same corpus + threads) is gated on its empirically-present audit signals — each side measured in its OWN child process loading THAT side's `@verter/native` build (two native builds cannot coexist in one process, so a single-process comparison would be invalid): `compile_throughput_ratio` (files/sec; a DROP vs baseline beyond **1.10×** fails), `codegen_time_ratio` (**≤ 1.10**, the PRESENT codegen + source-map emit-phase wall — `codegen_ms + sourcemap_ms` — named for what it measures, NOT the full non-checker aggregate), `source_map_bytes` (**two-sided invariant, ±2%** — a deterministic codegen-output byte signal, like `output_bytes`: a candidate that truncates/omits source maps DROPS bytes and would otherwise read as a perf win, but a source-map loss breaks IDE position mapping, so a drop is a correctness regression — and a zero/missing measurement, since source maps are requested on this path, is treated as missing instrumentation), `generated_carrier_count` (**≤ baseline × 1.01**, defined as the count of audited compiles emitting output — NOT a static file count), `output_bytes_ratio` (**≤ baseline × 1.02**, a two-sided codegen-output invariant on generated bytes), and a carrier+source-map **content-hash equality** (`carrierContent`, compared candidate-vs-baseline — a content hash over every generated IDE carrier + its source-map that catches a codegen change which PRESERVES output bytes + carrier count but alters the emitted CONTENT, which the byte/count invariants cannot catch) — Verter-compiler candidate vs Verter-compiler baseline, the codegen-throughput regression surface. Axis-A per-PID `peak_rss_ratio` (the in-process compile has no spawned child to sample and the footprint RSS sampler is unarmed) and the full `non_checker_time_ratio` aggregate (the compile audit record does not emit the parse/transform/transport phase timing) are **DEFERRED** with named Rust follow-ups (see the manifest `deferred`); axis-B cold/warm `peak_rss_ratio` is now **DEFERRED** too — `verter-tsc` spawns tsgo as a SEPARATE child, so the sampled wrapper-PID `VmHWM` misses the tsgo engine's resident set, and full process-tree peak RSS is not cleanly portable in TS (see §2.7.1).

**Offline vize comparison (manager-run, reported, NEVER CI), for BOTH axes.** A separate, OPT-IN, `VIZE_PATH`-gated script measures Verter vs `vize` OFFLINE on the same committed hermetic corpus, ST + MT at the fixed thread count: **AXIS A** is the legitimate apples-to-apples compiler-throughput number (Verter's native compiler vs `vize compileSfcBatch`, files/sec + ratio); **AXIS B is INFORMATIONAL only** — `vize`'s `typeCheck` is AST-based shallow analysis (`getTypeCheckCapabilities` mode `'ast-based'`), NOT a real TS typecheck, so the comparison is reported with that caveat explicit, never as apples-to-apples. This comparison is **excluded from CI**, never a `cargo` test, and env-gated so the hermeticity guards stay green — the manager runs it and reports the numbers; CI is 100% self-referential.

A **diagnostics scheduler** backs the interactive workloads: active-file diagnostics first, affected-set next, full-project only for the TSC/CLI surface; cancellation tokens wired to the engine; never a synchronous whole-project semantic pull on every keystroke.

Invalidation safety: VFS generation + content hash + source-map hash + import-signature + project generation + provider synced-version are authoritative. **Never cache on path alone.**

### 2.8 No-fork, capability-gated, fail-closed
**Installed workspace TypeScript ALWAYS wins.** Resolve the user's TypeScript first by reusing the existing discovery path (`verter_type_runtime/src/discovery.rs`: walk up to `<workspace>/node_modules/typescript`, then tsdk, then global — one discovery path, not a second): if the workspace has a `typescript` install, Verter uses **that exact install**, regardless of version/dist-tag, and never overrides it. The **`typescript` package major version** decides the backend — **major `< 7`** ⇒ the user's `tsserver`; **major `≥ 7`** ⇒ tsgo, where a `typescript` package at major ≥ 7 (e.g. `typescript@7.0.2`) declares the per-platform native binary as the optional dependency **`@typescript/typescript-{platform}-{arch}`** (the `--api` client is at `typescript/unstable/sync`). Binary selection is documented exactly: the platform/arch triple (incl. musl vs gnu on Linux), the optional-dependency binary package above, version/integrity match against the `typescript` package, PnP/workspace-hoisting layouts, and **no-network** behaviour. *(Engine discovery is **single-source**: the sole tsgo engine source is the installed `typescript` (major ≥ 7) package's `@typescript/typescript-{platform}-{arch}/lib/tsc[.exe]` binary. The `@typescript/native-preview` dev-preview channel — binary `@typescript/native-preview-{platform}-{arch}/lib/tsgo` — is **no longer a discovery source**: a Block-5 spike (2026-06-27) proved `@typescript/native-preview@latest` converged to the SAME integer `--api` wire as `typescript@7.0.1-rc` (no separate channel remains), so a `tsgo`-on-`PATH` lookup or a `.bin/tsgo` shim probe would only resolve the retired native-preview binary; both were removed and discovery now fails closed. This SUPERSEDES the earlier "native-preview = last-resort fallback source" decision — see the rc-only convergence note below.)*

**No bundling — the no-TypeScript fallback is package-DOWNLOAD only (A3).** Verter **never bundles, ships, forks, or patches a TypeScript engine binary.** Two cases: (i) **the workspace HAS TypeScript** — use the user's install, **regardless** of version (their `tsserver`/JS-LS for `<7`, their `typescript@7.x`'s tsgo for `≥7`); never override it (the always-wins rule above). (ii) **the workspace has NO TypeScript** — Verter **downloads the npm `typescript` package** into a Verter-managed location and uses that — **download only, never a bundled/shipped/forked binary.** **Version policy for the no-TS case (D10): download `typescript` at the `latest` dist-tag** — the current TS7 channel now that TS7 has shipped stable (e.g. `typescript@latest` resolving to `typescript@7.0.2`), consistent with the project's tsgo-preferred posture, so a TS-less workspace gets the fast native tsgo path rather than an arbitrary `<7` JS lib. **The policy is "the current TS7 channel"**: it was `rc` during the release-candidate window and retargeted `latest` when TS7 shipped stable (the trigger has fired). The fallback unit is **download-the-package** (which for v7 carries the platform tsgo binary as its optional dependency), so the engine is always a real npm `typescript` release, version-resolvable and integrity-checked, never a Verter fork/bundle. (On a WASM host, where tsgo can't run — §2.11 — the no-TS fallback is instead the in-context JS language service over a **fetched/downloaded** JS `typescript`, the same download-not-bundle discipline.) The download respects offline/no-network — **fail closed when offline** (no external-TS until the package is available) — and is version-matched by construction (the downloaded package's tsgo binary matches that package version). This satisfies the no-fork/no-bundle constraint while still giving a TS-less workspace a working engine.

The native `--api` is shipped but marked `unstable`/generated, so the tsgo backend stays **capability-gated by a handshake** (`capabilities()`, §2.1/§2.3) that re-runs the Block-0 spike assertions against the installed binary. **The production transport is the Rust-native `--api` client (§2.3); the `node tools/tsgo-api-gate/run-gate.mjs` JS gate is NOT the production transport.** Its role is twofold: **(i) a SERVER-capability oracle** — it proves the installed tsgo `--api` SERVER still exposes the required capabilities per version (the version-bump handshake below), independent of which client speaks the wire; and **(ii) the PARITY-ORACLE source** — the official generated JS client the gate drives is the parity reference the Rust-native client is asserted byte-for-result identical against (§2.3 mitigation 4). Under §2.3 mitigation 3 the same gate is extended to validate the **Rust client's own wire** against the installed tsgo, so a tsgo bump that changes the wire fails it. The required-capability set splits into **what the recorded Block-0 gate already proved** and **what the Block-5 handshake additionally proves** (the gate used the SYNC client, so the async/non-blocking `--api` lane is NOT among the already-proven set; `--api` wire cancellation is not in the set at all — `--api` has none, and cancellation on the interactive features is the `--lsp` surface's `$/cancelRequest`, Finding 1):
- **Proven by the Block-0 gate** (sync client; now run against the production package `typescript@7.0.1-rc` — B4 — after the rc-only consolidation; the original recorded run used the `@typescript/native-preview 7.0.0-dev.20260526.1` channel, whose `--api` surface is npm-confirmed identical and which the Block-5 spike showed has since converged to rc's exact integer wire): `{ off-disk virtual files visible to a configured project via FS-overlay callbacks (read_file/file_exists/get_accessible_entries), explicit open_project configured-project ownership, file→configured-project association queryable (get_default_project_for_file), sparse read-through overlay, bare-.x→declaration-carrier extension redirection through the overlay (GATE 4), the production declaration-carrier identity .d.vue.ts/.d.svelte.ts is the bare-import-probe-reachable resolution target (extension-MIDDLE, .d.<ext>.ts wins over .<ext>.tsx) while a .verter.-infixed identity is NOT (GATE 5), a .svelte.tsx IDE carrier coexists with a real .svelte.ts rune module (GATE 5), content-addressed incremental snapshot updates (update_snapshot file_changes) with Program reuse, project-scoped diagnostics/hover/definition from the configured Program }`.
- **Additionally REQUIRED, proven at the Block-5 handshake (not yet exercised by the committed gate):** `{ a virtualizable tsconfig (the overlay can serve tsconfig.json content — for §2.3 companion root-injection under .vue-specific include/files), the typescript/unstable/async client (concurrent, non-blocking — for the §2.7 interactive lane), root-set injection under a .vue-specific include / files-list }`. The **async (non-blocking) capability is part of the gate** (a sync-only `--api` client must NOT be the production transport): it verifies `unstable/async` is importable and gives concurrent, non-blocking request handling. **Cancellation is NOT a wire capability of `--api` (Finding 1):** neither the sync nor the async shipped client wires a `CancellationToken`, so `--api` cancellation is **client-side abandonment** (drop the waiter + discard the response + skip unsent requests), NOT a request-cancel wire — the gate does not (and cannot) prove an `--api` wire cancel. Real protocol cancellation (`$/cancelRequest`) is a property of tsgo's separate **`--lsp` surface** (§2.3), which serves the interactive features; §2.7's `$/cancelRequest` mention applies to that `--lsp` surface. Block 5 extends `tools/tsgo-api-gate/` to cover these (an async-client probe + a tsconfig-virtualization probe), so they graduate from "required" to "gate-proven". The gate runs on **every tsgo version bump**: if a future build regresses a required capability, **do not ship a "nearly correct" tsgo LSP path on that build** — fail closed (no external TS results for TS≥7 on that surface), keep non-TS features alive, and **upstream the minimal missing *generic* API shape** (never Vue-specific concepts). For the **TSC surface only**, the mirror-host + generated-`extends`-tsconfig path (§2.4) is a no-fork fallback independent of `--api` batch diagnostics, so a `--api` regression need not strand TS≥7 *batch typecheck*. **Never fork, patch, or bundle a TS engine** — the no-TS fallback is package-DOWNLOAD only (above), not an exception to no-bundle.

### 2.9 `.vue`-import from plain `.ts`/`.js` — first-class enhanced DX on BOTH engines
A plain `.ts`/`.js` file that does `import Comp from "./Comp.vue"` (or `import { x } from "./Comp.vue"`) must get the **full enhanced type experience** at that import and at every use of the imported symbol — correct `$props`/emits/slots/expose typing, hover, go-to-definition into the SFC, find-all-references back into and out of it, completion, rename — exactly as if `Comp.vue` were a `.ts` module. This is a **primary IDE-DX bar** (it is the entire point of the existing `@verter/typescript-plugin`), and it must be first-class on **both** TS<7 and TS≥7. The two engines reach it by **different mechanisms** (the same split as the rest of this doc), unified behind the §2.1 contract:

- **TS<7 (tsserver) — the in-process plugin (existing model, kept first-class).** The `@verter/typescript-plugin` (§2.2) makes `import "./Comp.vue"` resolve (via `resolveModuleNameLiterals`) to the descriptor-owned declaration carrier (`Comp.d.vue.ts`/`Comp.d.svelte.ts`, the bare-import target), so the user's `.ts` Program sees a real typed module. (tsserver's `resolveModuleNameLiterals` returns a `resolvedFileName` directly — a true resolution map — so it is not basename-probe-bound like tsgo; Verter still targets the same `.d.vue.ts`/`.d.svelte.ts` declaration identity on both engines for parity; the `.vue.tsx`/`.svelte.tsx` IDE carrier is the self-diagnostics surface, and the separate `.verter.ts` API carrier is the cross-package redirect target of §2.6.) This is the load-bearing path for plain-script `.vue` imports on tsserver and stays first-class (the full host-proxy matrix + readiness protocol of §2.2 apply).

- **TS≥7 (tsgo) — NOT a plugin; the `--api` FS-overlay + carrier-extension redirection (PROVEN).** tsgo **cannot load in-process LS plugins** (typescript-go #2824: "we can't dynamically link third-party code into the server process"), so the plugin model is unavailable. The capability is served by the FS overlay, and the **exact resolution mechanism is verified** (gate probe + GATE 4 + GATE 5): when the user's `A.ts` (a member of the `open_project` Program) resolves a bare `import "./Comp.vue"`, **tsgo's own resolver appends to the `Comp.vue` basename and probes `Comp.d.vue.ts` before `Comp.vue.ts`/`Comp.vue.tsx`** — Verter's overlay answers `read_file`/`file_exists` for that probe with the declaration carrier content. **The carrier's canonical engine/store identity for the bare import IS `Comp.d.vue.ts` (the extension-MIDDLE declaration carrier of §2.2)** — the path the probe reaches first (`.d.<ext>.ts` wins over `.<ext>.tsx`); `path_is_carrier` classifies it, and the `Comp.vue.tsx` IDE carrier is the separate self-diagnostics surface. (GATE 5 falsified the `.verter.` alternative: a `.verter.`-infixed path — `Comp.vue.verter.tsx` — is NOT reached by tsgo's basename probe → TS2307. The reserved `.verter.ts` infix belongs only to the redirect-reached API carrier, never this bare-import target.) Critically (probe Strategy A): serving TSX content at the **bare** `Comp.vue` path does **NOT** work (tsgo emits `TS2307`); the redirection MUST be served at a probe the resolver reaches, resolving to the `.d.vue.ts`/`.d.svelte.ts` declaration carrier (§2.2/§2.3). No module-resolution-map endpoint is needed. Hover/definition/references/rename/completion are then served by tsgo's **`--lsp` surface** (the dual-surface backend of §2.3) over the same project-bound carrier membership, riding the §2.7 query path with `ProviderPositionMapper` mapping any span inside the carrier back to the `.vue` and the §2.9 specifier-rewrite layer applied to inserted-import edits — **all interactive features served by `--lsp`, with NO per-feature `--api` derivation** (the one-surface rule of §2.3; `--api` carries the carrier membership, the typecheck oracle, and the SEPARATE batch/TSC typecheck — never the interactive features and never the INTERACTIVE editor diagnostics, which also ride `--lsp` per the §2.3 diagnostics ruling, even where `--api`'s checker primitives could reconstruct them). **No plugin, no fork** — the plain-`.ts` importer is just another configured-project member whose bare `.vue` import tsgo resolves to the overlay-served declaration carrier.

**Cross-engine, cross-framework DX contract (the bar, mapped through the carrier source-map):** for a carrier-source file (`.vue`/`.svelte`/…) imported from a plain script, on **either** engine — (1) the imported default/named symbols carry the component's **real public surface as the framework adapter defines it** (Vue: `$props`/emits/slots/expose; Svelte: the component's props/events/slots/snippets per the Svelte adapter; future adapters per their own surface) — the *contract* is "the adapter's real public types flow," not any Vue-specific shape; (2) **go-to-definition** from the `.ts` use lands in the source file (mapped from the carrier); (3) **find-all-references** spans both the `.ts` importer(s) and the source (script + template/markup); (4) **rename** of an exported member updates the source and every `.ts` importer; (5) **completion** of `Comp.`'s members and **auto-import** of the component into a `.ts` file work (auto-import relies on the eager `CarrierApi` index, §2.7); (6) unmapped synthetic/carrier-only regions **fail closed** (never a mis-mapped result). Items (4)/(6) reuse the cross-file rename fail-closed machinery already in `ProviderSurfaceStore`. The per-adapter public-surface *semantics* are framework-specific (the adapter computes them); the DX *contract* above is framework-neutral. **On tsgo this contract (1)–(6) STILL HOLDS — the feature items are served by the `--lsp` surface (§2.3), over the project-bound carrier membership, with carrier offsets mapped back through `ProviderPositionMapper` and the specifier-rewrite layer applied; there is NO per-feature `--api` derivation** (the one-surface rule). The contract is unchanged; only the surface that answers it is named.

**Module-specifier mapping for inserted imports (completion/auto-import/code-action edits).** Because the engine's file identity for the SFC is the **carrier companion** (the `Comp.vue.tsx` component carrier, or the `Comp.vue.verter.ts` API carrier under a cross-package redirect), an auto-import or quick-fix that the engine generates will, left raw, insert the **companion** specifier (`./Comp.vue.tsx` / `./Comp.vue` -as-`.tsx`, `./Comp.vue.verter` for the API carrier, or even a bare `./Comp`), not the user-facing `./Comp.vue`. A **module-specifier rewrite layer** is therefore required on inserted-import text edits (the same direction as position mapping, applied to the specifier string): any engine-produced import whose target is a `.vue`/`.svelte` companion is rewritten to the bare `.vue`/`.svelte` specifier before the edit reaches the user; an edit whose specifier cannot be mapped to a user-facing form **fails closed** (the edit is suppressed, not mis-inserted). This is the one place §2.9 needs logic beyond raw redirection, and it is part of the contract (item 5). **CodeTransform note (D9):** this rewrites the **engine's output** — a tsserver/tsgo code-action `TextEdit`/`WorkspaceEdit` specifier string destined for the **user's source file** — NOT any `CodeTransform`-built carrier text; so it does not violate "CodeTransform is the single source of truth" (which governs modifications to *Verter's generated carrier*, never an LSP edit the engine emits for user source). The carrier text itself stays CodeTransform-authored and stable.

**`tsconfig` association for the plain script.** The plain `.ts`/`.js` importer must itself be a member of a configured project (§2.6) for the redirect to apply — a `.ts` outside every tsconfig is `NoProject` and gets no enhanced `.vue` types (fail closed), same as any other file. The `.vue` it imports is discovered/owned per §2.6 + §2.3 root-set injection.

**Verification — the tsgo half is ALREADY PROVEN; tsserver + the full contract land in the blocks.** The committed gate's **GATE 4** (`tools/tsgo-api-gate/`) shows a plain `Consumer.ts` importing a **bare `"./Exported.vue"`** (overlay serving only the `Exported.vue.tsx` companion, the bare path asserted absent on disk) resolve with zero diagnostics and the companion's exported type flow into the `.ts` — i.e. the tsgo redirection + types-flow of contract item (1) is green NOW. The remaining contract items (2)–(6) on both engines, and the module-specifier rewrite layer, land with Block 4 (tsserver, via the plugin) and Block 5 (tsgo, via the gate-proven overlay). *Guard:* `carrier_dx_enhanced_both_engines_both_frameworks` (the contract (1)–(6) holds on tsserver AND tsgo, with inserted-import specifiers rewritten to `.vue` or the edit failing closed).

### 2.10 Shared-engine mode — an OPTIONAL optimization layered on the OWNED `--api` backend
The tsgo backend (§2.3) is the **OWNED `--api` path** — that is the correctness baseline and architectural center. **SHARED mode is an OPTIONAL layered optimization built on top of it**, selected per session by capability negotiation and enabled **only where a full editor TS-LSP proxy exists** (VS Code today). It is never on the core path; OWNED always works without it.

> **Scheduling note (settled decision).** SHARED mode is **NOT a Block-5 deliverable** — Block 5 ships the OWNED backend only. SHARED is deferred to a **separate, later, spike-gated phase (Block 8 in §3)** that OPENS with a live-spike investigation and scopes everything before any implementation. This section's prose describes the SHARED *mechanism* as investigated; the open SHARED-capability unknowns (third-party pipe access, the B2 proxy feasibility) and the SHARED-diagnostics ruling are settled by that phase's spike, not pre-decided here.
- **OWNED mode (the backend itself)** — Verter spawns its own `--api` instance (`new API({ tsserver_path, cwd, fs })`); the FS-overlay backs carriers. The **portable baseline** (works in every editor, version-controlled by Verter, stable lifecycle) and the actual tsgo backend. This is what Block 0/GATE 1–4 proved.
- **SHARED mode (optional optimization)** — Verter attaches to the editor's already-running tsgo and drives carriers against the **editor's own Program** (one engine, no double-checking, instant consistency with what the editor sees). It is an **opt-in enhancement layered on OWNED**, enabled only under the gating preconditions below (editor attach bridge + full TS-LSP proxy); it is **secondary to OWNED**, not co-equal, and OWNED is always the fall-back. **Full carrier parity is a property of the combined tsgo adapter (OWNED + the SHARED optimization with OWNED fall-over), and OWNED alone already provides it**: SHARED cannot serve configs that need tsconfig-virtualization (Verter doesn't own the editor's FS), so for those it routes to OWNED. The OWNED baseline, not the optional optimization, guarantees parity.

Both modes serve the **identical** §2.3/§2.7/§2.9 carrier/redirection/query contract; they differ only in **how carrier content reaches the Program** and **which Program it is**. The adapter abstracts the difference behind a `CarrierInjectionChannel` so every higher layer (§2.5 sync, §2.7 queries, §2.9 DX) is mode-agnostic.

**Architectural note — the carrier-resolution scheme IS the shared-engine / #2824 endpoint shape (A is the convergent endpoint, not an interim).** The §2.2/§2.3 scheme is *proactive virtual files resolved by tsgo's native probe*: Verter provides the `.d.<ext>.ts` declaration overlay (+ its transitive closure) and tsgo's own basename-append resolver reaches it — no resolution callback, no text rewrite of the import specifier. This is **exactly** the shape both SHARED mode and typescript-go #2824 converge on: SHARED injects the very same carrier overlays as `didOpen` documents on the editor's shared `project.Session` and lets the editor's own tsgo resolve them natively (the §2.10 `CarrierInjectionChannel` differs only in *which* overlay store and *which* Program — the carrier identities and the native-probe resolution are identical to OWNED), and #2824's endpoint is **client-pushed virtual files plus a future static module-resolution-map API — explicitly NOT resolution callbacks** (the TS team refuses callbacks; #2824). Approach A is therefore not an interim that SHARED or a future API would replace: a static-map API would simply *carry the same declaration-carrier mapping* the proactive overlay establishes today (the §2.2/§2.3 non-fail-closed dissolution), and SHARED reuses the same overlays. The earlier compile-time L1 textual specifier rewrite (textually appending `.tsx` so the carrier emitted `./B.vue.tsx`) structurally **could not** run in SHARED mode — the editor owns the carrier text and the import specifier, so Verter could not rewrite it on the shared session — whereas the declaration-overlay model needs no specifier rewrite at all and so layers onto the shared session cleanly. A is the forward-compatible scheme every endpoint (OWNED, SHARED, the future static-map API) carries.

**Attach handshake (verified from the shipped Go binary + typescript-go source + the VS Code extension):** the tsgo LSP server exposes `custom/initializeAPISession` (handler `(*lsp.Server).handleInitializeAPISession` → `api.NewSession(s.session, …)`, minting a second API session that **holds the LSP server's existing `project.Session`** — the same projects/Programs the editor checks) returning a pipe; Verter connects with **`API.fromLSPConnection({ pipe })`** (`typescript/unstable/async`; attach is async-only — matches the §2.7 async interactive lane). The VS Code "TypeScript (Native Preview)" extension bridges the pipe to third parties via `ExtensionAPI.initializeAPIConnection(pipe?)` (command `typescript.native-preview.initializeAPIConnection`). This is typescript-go #2824's auxiliary-server model.

**The carrier-injection mechanism in SHARED mode (verified — and DIFFERENT from OWNED mode; the §2.10 design hinge).** An attached `API<true>` has **no content channel of its own**: `fs` callbacks are a SPAWN-only option (`ClientSpawnOptions.fs`); `LSPUpdateSnapshotParams` is `{ openProject? }` only; there is no `openFile`/`overlay`/`Document` API method. So Verter **cannot** push carriers through the attached API client. The verified path is the **LSP text-document overlay on the shared `project.Session`**: because `api.NewSession(s.session)` shares the LSP server's session, and that session's overlay store is what the checker reads through (`overlayFS.getFile` → overlay-map-then-disk; `SnapshotFS.GetFileByPath` → overlays→disk; the frozen compiler host's `GetSourceFile`/`ReadFile` consult the snapshot FS), a carrier opened as an **LSP `textDocument/didOpen` (then `didChange`) document on that same connection becomes a member of the shared Program** and is then visible through the attached `API<true>` `Program`/`Checker`. Therefore SHARED mode's `CarrierInjectionChannel` is:
1. **Open each generated carrier companion** (the component IDE carriers `.vue.tsx`/`.svelte.tsx` and the API carriers `.vue.verter.ts`/`.svelte.verter.ts` — §2.2 GATE-5 identities) **as an LSP overlay document** (`didOpen` with the carrier text, `didChange` on edits, `didClose` on retract) on the editor's tsgo LSP connection — driven by Verter's editor-side LSP client / the editor extension that already owns that connection. Content is the same `CodeTransform`-built carrier (CodeTransform-source-of-truth); never a text-splice.
2. **Program-eligibility** is established the same way as §2.3/§2.6: the companion must be a member of the relevant configured project. Where the user's config does not enumerate the companion, the §2.3 **tsconfig-virtualization** is unavailable in SHARED mode (Verter does not own the editor's FS), so SHARED mode requires the companion to be reachable as a root/included file or via an import edge.
   - **Fail-over granularity is the REDIRECT-ON PROJECT-REFERENCE CLOSURE, never per-file and not even per-single-tsconfig (B1).** A shared Program that imports a carrier only available in OWNED mode would have a broken/missing edge (and cross-file queries — references/rename/auto-import — would be silently incomplete). Per-file fail-over is therefore forbidden; but **per-single-configured-project is also insufficient** because project references create **cross-project** carrier edges:
     - **Intra-project:** if **any** carrier owned by a configured project cannot be made program-eligible in the shared session, **that entire project's carriers route to OWNED** (one `--api` Program for that tsconfig); no intra-project edge is split.
     - **Cross-project under DEFAULT redirect (the hard case):** §2.6 says with source-of-project-reference redirect ON, project A importing project B's `.x` resolves to **B's source carrier (`CarrierIde`) inside A's Program** — so A and B's carriers are entangled in one Program slice. If B must use OWNED (e.g. B needs tsconfig-virtualization, unavailable in SHARED) while A is SHARED-eligible, the A→B carrier edge would split across two engines. **The mode-selection unit is therefore the redirect-ON reference CLOSURE: A plus every project reachable through its `references[]` whose `.x` it imports under redirect-ON share ONE mode** — if any member of the closure must use OWNED, the whole closure uses OWNED.
     - **Cross-project under `disableSourceOfProjectReferenceRedirect: true`:** the edge is the emitted-`.d.ts`-equivalent `CarrierApi` boundary (§2.6), which **decouples** the Programs — A only needs B's API surface, not B's live carrier in A's Program — so the closure rule applies **only to redirect-ON references**; a `disable…:true` reference does not force A and B into one mode.
     - A closure served in OWNED still benefits from SHARED reads for *unrelated* projects/closures in the workspace. Fail-closed: a closure whose carriers can't be made eligible in either mode yields no external-TS result for those carriers. *(This is the §2.10 ↔ §2.6 cross-wiring: SHARED/OWNED selection is redirect-aware.)*
3. **Module redirection** (`import "./Comp.vue"` → declaration carrier) works identically: tsgo appends to the basename and the overlay-opened `Comp.d.vue.ts` declaration-carrier document answers the probe first (`.d.<ext>.ts` wins over `.<ext>.tsx`; the §2.9/GATE-4/GATE-5 mechanism — the carrier is present, now as an LSP overlay instead of an FS-overlay answer).
4. **Queries** (`Program`/`Checker`, diagnostics, hover, definition, references, rename, completion) run through the attached `API<true>`; results map back through `ProviderPositionMapper` exactly as in OWNED mode.

**Read side.** Beyond carriers, the attached session gives Verter the editor's **already-loaded** on-disk `.ts`/`.d.ts` + the editor's open overlays for free — cross-file context that OWNED mode would re-read/re-check. SHARED mode thus does strictly less duplicate work.

**Overlay precedence / conflict model (verified) — gated by the §2.2 same-path conflict check.** Both read paths check the overlay map before disk, so an overlay-opened companion *would* win over any on-disk file of the same path; there is no second content source on the API protocol to conflict with. **But because the engine overlay would shadow a real same-path file, SHARED mode runs the SAME §2.2 Carrier-path conflict gate as OWNED mode BEFORE `didOpen`-ing a companion:** if a real user file already occupies the exact carrier path (`Foo.vue.tsx`), Verter **does NOT open the overlay** for it — the source is `Ambiguous`/conflicted and yields no external-TS result (Verter never shadows the user's real file; §2.2/§2.6 step 4). In the **normal case** (the common one), Verter owns the carrier companion paths (the component IDE carriers `.vue.tsx`/`.svelte.tsx` and the API carriers `.vue.verter.ts`/`.svelte.verter.ts`), the editor never opens them (it opens the bare `.vue`/`.svelte` source and real `.ts`), and **the user has no on-disk file at the companion path** — so there is no contention and the overlay is placed; `path_is_carrier` plus the disk-occupancy check keep a Verter-generated companion (`Foo.vue.tsx`) distinct from a real user `Foo.tsx` AND detect the same-path conflict. If both the editor and Verter would (legitimately) hold the same path, the **single shared overlay store** holds one document. (The same-path conflict is the §2.2 fail-closed case; the same-stem Svelte-rune conflict fails closed identically.)

**Carrier-path leak suppression in SHARED mode requires Verter to PROXY the editor's TS LSP connection — and that requirement gates when SHARED is offered (B2).** Injecting companions as `didOpen` documents into the **editor's own** tsgo session means the editor's tsgo now *knows about* `Foo.vue.tsx` (the component carrier) and `Foo.vue.verter.ts` (the API carrier) and can surface results keyed to those virtual paths **on the editor's OWN channels — including UNPROMPTED ones Verter never queried**: `textDocument/publishDiagnostics` (push, per-document, on the engine's own cadence), `workspace/symbol`, `workspace/diagnostic`, call/type hierarchy, document symbols, code actions / quick fixes, completion-resolve `additionalTextEdits`, organize-imports, `workspace/applyEdit`, semantic tokens, inlay hints, implementation/type-definition, and file-rename edits. A `Foo.vue.tsx` (or `Foo.vue.verter.ts`) diagnostic or symbol reaching the user is exactly the leak B2 must prevent. **This is only enforceable if Verter is the LSP MIDDLEWARE/PROXY sitting in front of the editor's TS language server** — i.e. every TS LSP message between the editor UI and the shared tsgo passes through Verter, so Verter can map-back-or-suppress *every* channel above, not just the results it requested through the attached `API<true>`. **Therefore SHARED mode is offered ONLY when this proxy topology holds**; this is a STRONGER requirement than "the editor exposes the attach pipe" and further constrains SHARED availability (see Editor availability). When Verter cannot proxy the full TS LSP connection, **SHARED is not offered for that workspace — it runs OWNED** (where companions live in Verter's own Program and never touch an editor channel). Within the proxy topology, the suppression is concrete and total:
- (a) **diagnostics** (push or pull) for a companion path are intercepted and **mapped back to the source carrier (`.vue`/`.svelte`) via `ProviderPositionMapper` or suppressed** — never shown against a companion path (the `Foo.vue.tsx`/`Foo.svelte.tsx` component carrier or the `Foo.vue.verter.ts` API carrier); (b) **definition/references/rename/highlights/hover/implementation/type-definition/call+type-hierarchy/document+workspace-symbols** results landing in a companion are mapped to the source (script + markup) or dropped (the OWNED §2.7 fail-closed mapping); (c) **inserted-import specifiers** in **code actions, completion-resolve `additionalTextEdits`, organize-imports, `workspace/applyEdit`, and file-rename edits** targeting a companion run through the §2.9 **module-specifier rewrite layer** → bare `.vue`/`.svelte` or the edit fails closed; (d) **semantic tokens / inlay hints / generated-only spans** for companion regions are suppressed.
- **No companion path is ever a user-visible document or an un-mapped result on ANY channel.** The editor opens `.vue`/`.svelte` (the source surface) and real `.ts`; the companions exist only inside the shared Program as Verter-injected overlays, and the proxy guarantees every engine response naming a companion path is Verter's to translate or swallow before the editor UI sees it.
- *Guard:* `shared_mode_requires_full_ts_lsp_proxy` (SHARED is selected only when Verter proxies the editor's entire TS LSP connection; otherwise OWNED) **and** `shared_mode_no_unmapped_carrier_path_leak` (under the proxy, no companion-path span/edit/diagnostic — on any enumerated channel — reaches the editor UI un-mapped). The honest scope: the second guard is checkable precisely *because* the first establishes the proxy; without the proxy, SHARED is not offered, so there is nothing to leak.

**Lifecycle.** The attached session dies when the editor restarts/changes tsgo; Verter detects disconnect, **re-attaches and re-opens its companion overlays**, and meanwhile **fails over to OWNED mode (per redirect-ON reference closure, per B1)** so no query is ever served without a valid Program (fail-closed). Mode is renegotiated on reconnect.

**Editor availability — TWO requirements, both editor-side (this is why SHARED is opt-in, not the universal default).** SHARED needs BOTH: (1) the editor exposes the **attach pipe** (`custom/initializeAPISession`) so Verter can `API.fromLSPConnection` — **VS Code** exposes it via the Native Preview extension's `ExtensionAPI`; and (2) Verter can **proxy the editor's TS LSP connection** for the B2 leak suppression. Where Verter ships the editor's TS integration itself (or sits as LSP middleware), (2) holds; where the editor owns its own TS LSP client and Verter cannot interpose, (2) fails and **SHARED is not offered — OWNED runs instead** (correct, just a second Program). Other matrix editors (Neovim/Helix/Zed/Lapce) today provide neither bridge, so they run OWNED until their tsgo integration exposes the pipe **and** admits a Verter proxy. This dual requirement is the honest reason SHARED is an optional, where-available optimization layered on the universal OWNED baseline, not a default and not co-equal with OWNED.

**Decision & invariants (OPTIONAL optimization, OWNED baseline):** SHARED mode is an **opt-in enhancement** enabled only where the editor exposes the attach bridge AND Verter can proxy the editor's TS LSP connection (B2) AND the §2.8 handshake passes on the attached session; **OWNED mode is the always-available correctness baseline and the architectural center** — the backend works fully without SHARED ever engaging. The selection is per-session and dynamic (re-evaluated on reconnect), and defaults to OWNED. **Correctness is mode-independent**: both produce real configured-Program results mapped fail-closed; the only differences are memory/consistency (SHARED wins where available) and editor availability (OWNED is universal). The tsgo backend is **DUAL-SURFACE** — it drives BOTH the `tsgo --lsp --stdio` interactive-feature surface AND the `--api` `Checker` surface over ONE connection / Program (the `--lsp` path is **retained and refactored to project-bound membership**, NOT legacy-to-delete; the one-surface-per-concern rule of §2.3) — and the **same client code path serves OWNED's spawned connection and (in the future SHARED phase) an attached editor connection**, so the SHARED optimization, when it is built, layers on cleanly without a provider rewrite. **SHARED mode is NOT a Block-5 deliverable** — Block 5 builds the OWNED dual-surface backend only (gate-proven); the SHARED optimization is a **separate, later, spike-gated phase** (see the SHARED-investigation block in §3) that scopes everything before any implementation. The SHARED-specific guards (`tsgo_shared_mode_carrier_injection`, `shared_mode_failover_is_per_reference_closure`, `shared_mode_requires_full_ts_lsp_proxy`, `shared_mode_no_unmapped_carrier_path_leak`) belong to that future phase, not to Block 5.

### 2.11 WASM / playground — the TS JS language service IN-CONTEXT (third instantiation, accepted boundary)
Verter's Rust core compiles to **WASM** (the playground; `crates/verter_wasm` → `wasm32-unknown-unknown`, `--target web`, verified to export carrier-gen + Verter-native analysis). A WASM host **cannot spawn a subprocess**, which sets a hard, **accepted** platform boundary — not a gap to engineer around:

- **tsgo is native-only (ACCEPTED, verified).** `typescript@7.x` / `@typescript/native-preview` ship the tsgo checker only as **native platform binaries** (no `wasm`/`wasi` optional dependency exists; the launcher is `child_process`-only). There is **no WebAssembly build of tsgo and Verter does not attempt one.** Therefore **TS≥7 external type-check is unavailable in WASM** — the playground gets carrier-gen + Verter-native analysis and (below) the TS<7-style JS language service, never a fabricated TS≥7 result (fail-closed).
- **The WASM type-check engine = the TypeScript JS `LanguageService` run IN-CONTEXT.** TypeScript's language service (`ts.createLanguageService(host)`) is **pure JavaScript and runs in the browser** (the TS Playground and monaco do exactly this; `typescript`'s `package.json` `"browser"` field blanks `fs`/`os`/`path`, and `@typescript/vfs` provides the in-memory `System`/host). The playground instantiates it **directly in the WASM/browser host — no subprocess** — fed by Verter's **carrier-serving `LanguageServiceHost`**.
- **It REUSES the §2.2 carrier-serving CORE — NOT identical host hooks (the architectural consequence, D4).** This instantiation shares the §2.2 **carrier-serving CORE** (the carrier store/overlay, the §2.9 `.x`→companion redirection, the §2.9 specifier-rewrite, the fail-closed `ProviderPositionMapper`), but it **implements `LanguageServiceHost` directly** rather than feeding tsserver's plugin-host hooks — so it is the in-context `ts.LanguageService` sharing the CORE, NOT the identical tsserver/plugin host hooks. Concretely it exposes `extraFileExtensions` for the carrier source extension(s) and serves the carriers as the descriptor-owned companions — the `.d.vue.ts`/`.d.svelte.ts` declaration carrier (the bare-import target), the `.vue.tsx`/`.svelte.tsx` self-diagnostics IDE carrier, and the `.verter.ts` API carrier where reached — via `getScriptSnapshot`/`readFile`/`fileExists`/`getScriptKind` and the `.x`→declaration-carrier redirection. (The in-context JS `ts.LanguageService` resolves bare `.x` imports through the same appended-extension probing as tsgo, so the bare-import target identity must be the probe-reachable extension-MIDDLE `.d.vue.ts`/`.d.svelte.ts` declaration carrier here too — it wins the probe over `.<ext>.tsx`, GATE 5.) So the **JS-language-service backend has two instantiations over ONE shared CORE**: **(a) the Node tsserver plugin** on native (§2.2), and **(b) the in-context `ts.LanguageService`** in WASM/playground (§2.11) — they reuse the CORE, not the same host hooks (the §2.2 tsserver negative-cache mechanics are instantiation-(a) concerns and do not all carry to (b)). The configured-project-membership fix, the enhanced plain-`.ts`-imports-`.vue`/`.svelte` DX (§2.9), and the framework-agnostic carrier mechanism (Vue AND Svelte) therefore **all apply in the playground** — this is the §2.1 contract with a third engine instantiation, the contract itself unchanged.
- **Lib `.d.ts` provisioning.** The lib `.d.ts` set (`lib.es*.d.ts`, `lib.dom.d.ts`) is not in the WASM module; the playground **fetches/loads** it and feeds it through the in-memory host (the standard `@typescript/vfs` browser pattern).
- **Fail-closed matrix posture.** In WASM, where the external engine is the in-context JS LS, TS-version-appropriate results come from it; where no engine applies (TS≥7), the surface returns carrier-gen + Verter-native only, never wrong external-TS.
- **Status: a designed path with a WASM spike obligation.** The in-context LS over Verter carriers is architecturally sound and its dependencies are browser-proven, but it is **not yet implemented** (Verter's only TS transport today is the native subprocess). A **WASM spike** (a Block; see §3) must prove: browser-load `typescript.js` with Node built-ins stubbed; supply lib `.d.ts`; feed the declaration carrier (`.d.vue.ts`/`.d.svelte.ts`, the bare-import target) + `getIde` (`.vue.tsx`/`.svelte.tsx`) + `getPublicApi` (`.vue.verter.ts`/`.svelte.verter.ts`) carriers through the host; `.x`→declaration-carrier redirection + specifier-rewrite; position-map back; acceptable worker perf/memory. *(Also note: `analyzeWithAudit` is `wasm32`-stubbed and `processStyle` is Node-only today — the WASM "Verter-native" column is near-complete, not 100%; the spike records which `analyze_*` entry points are `cfg`-gated.)* Until the spike lands, the doc describes WASM external-TS as designed-but-unproven (it does not block native).

### Block 8 — SHARED-engine mode (attach-inject to the editor's own tsgo) — RESTRUCTURED around the acceptance objective (§2.10)
The SHARED optimization (§2.10) — driving carriers against the **editor's own tsgo Program** — is a **separate, later phase** layered on the OWNED tsgo backend (Block 5) AFTER OWNED consolidation (Block 6) and the WASM work (Block 7). SHARED is never on the core path: OWNED is the universal correctness baseline and is always sufficient on its own; SHARED is opt-in, per-session, additive, defaults to OWNED.

**Settled decision (post-spike, authoritative).** The opening live-spike + a Fable improvement pass + an unprimed codex-architect decision + a release-codec verification (D1a) resolved the open unknowns:
- **attach-inject is the PRIMARY mechanism.** Read-only `ExtensionAPI` pipe access alone cannot inject carriers, so it cannot deliver `.vue`-in-`.ts` typing; the attached `--api` has no content channel (`LSPUpdateSnapshotParams = {openProject?}`, no `fs`), so carriers inject as **LSP `didOpen` overlay documents on the editor's already-configured shared `project.Session`** through a full-wire interposition substrate. Read-only tier is REJECTED as the product path.
- **The release native-preview engine uses i64 handles (D1a: RELEASE-ENGINE-I64).** `typescript@7.0.1-rc` AND the shipping `native-preview 0.20260703.1` both emit bare-integer `updateSnapshot` handles that Verter's i64 codec decodes cleanly; per the D1A-CODEC-VERDICT record, the D1a codec-verification primitive (off-disk carrier → configured-Program member → real `TS2322`, no false `TS2307`) passed on both channels. The earlier "string handle" finding was an obsolete May-26 dev build masquerading as the rc — a mislabeled-layout artifact, not a wire incompatibility. (D1a is the codec-verification lane; **D1 — the real-editor e2e acceptance — remains the BLOCKING gate** and is not substituted by D1a.)
- **Provider-mode (Verter serves the editor's TS/JS itself) is a TRACKED ALTERNATIVE, not primary.** It delivers the objective but at high product/ownership cost (Verter must serve all plain `.ts`/`.js` at native-preview quality; the user disables the Microsoft extension). With the wire alive and i64-aligned, attach-inject delivers the objective more cheaply. Upstream typescript-go #2824 (client-pushed virtual files + module-resolution-map) is the sanctioned successor, tracked, timeline external.

**F8 channel pin + fail-closed wire gate (the release-codec gate).** SHARED attaches only to an engine on the validated channel: `^7\.0\.\d+-rc$` (rc release) OR `^7\.0\.0-dev\.(\d{8})\.\d+$` with date ≥ `20260604` (the exact bisected i64 flip). The version rides an **in-band witness** — the `--lsp` `initialize` result's `serverInfo.version` (the `--api` `initialize` result carries no version) — read per attach and per reconnect; anything off-channel ⇒ UNKNOWN. The **authoritative rail** (version witness is advisory): on the FIRST `updateSnapshot`, require the `snapshot` handle to be a bare JSON integer and the typed decode to succeed; any non-integer handle, decode failure, or UNKNOWN version ⇒ **fail closed** (no SHARED activation, no external-TS product result — classification may require a provisional attached/proxied observation point; the refusal surfaces the engine's serverInfo version). Immune to version-string lies. Never source from `@typescript/native-preview@beta` (stale pre-flip tag). This gate is provider-neutral and shared with OWNED.

Teardown = retract Verter's own `didClose` overlays + drop the pipe only. ## 4. Rejected alternatives
- **Inferred-project overlays** (today's path) — cannot express configured-project membership; the source of the bug. The Block-0 negative control proves it directly (no `open_project` ⇒ "no project found").
- **Import-rewriting as the semantic integration** — destabilises carrier text + fights incrementality; violates CodeTransform-is-source-of-truth.
- **A whole-filesystem proxy worker feeding the engine over IPC** (the stopped block's heavy design) — duplicates project state, floods transport, makes invalidation *harder* than TypeScript's own Program graph; over-engineered and likely **slower**. The shipped tsgo `--api` proves the *targeted* sparse overlay suffices.
- **A plain LSP `didOpen` overlay into a CONFIG-LESS / inferred project as the membership mechanism** — rejected on a precise criterion, not "LSP bad": a `didOpen` into an inferred/config-less project cannot apply the real tsconfig (today's bug). Two things are explicitly NOT this rejected pattern: (i) OWNED mode's `--api` `open_project` + FS overlay (the proven §2.3 path); (ii) SHARED mode's `didOpen` overlay **on the editor's already-configured shared `project.Session`** (§2.10), where the document lands in the editor's REAL configured Program, not an inferred one — that is a verified, accepted carrier-injection channel, distinct from a config-less `didOpen`.
- **Forking / patching / bundling tsgo** (golar-style) — version skew against the user's `typescript` is a correctness bug; cannot drive the user's install. **Rejected outright, with no exception:** the no-TypeScript fallback is **package DOWNLOAD only** (download the npm `typescript` at the `rc` dist-tag, §2.8), never a forked/patched/bundled/shipped binary.
- **Source-tree (co-located, gitignored) sidecar carriers for the TS<7 batch path** — writing `Foo.vue.tsx` next to `Foo.vue` would touch the user's working tree (perturbing file watchers, other tools, or a read-only checkout). **Rejected** in favour of the §2.4 **mirror-host / `ts.CompilerHost`** model, which re-roots reads so generated carriers live in a Verter-owned mirror tree and relative imports resolve via a host `resolveModuleNames` override — zero working-tree writes. There is no sidecar-vs-mirror bake-off; sidecars are off the table.
- **Routing IDE/typecheck through Verter's internal semantic resolver** — creates a second TypeScript that diverges on overloads, contextual typing, module resolution, JSX, libs, refactors. (This independently validates the typeinfo/semantic-engine exclusion: the IDE surface must be *real* TypeScript semantics.)

## 5. Risks & open questions
- **~~Primary risk: tsgo `--api` sufficiency~~ — RESOLVED (Block 0 = GO, 17/17).** Residual: the surface is `unstable`/generated, so a version bump could regress a required capability → mitigated by the version-pinned capability-gate handshake (§2.8) that re-runs the committed gate harness (`tools/tsgo-api-gate/`); a regressed build fails closed for TS≥7, never ships degraded. **The production transport is a Rust-native `--api` client (§2.3, the project-owner decision over the architecture review's verdict), so a second residual is wire-divergence — the Rust client speaking an `unstable`/generated wire that a tsgo bump silently changes.** This is mitigated by §2.3 mitigations 2–4: the codec is **hand-written against the shipped typed proto as its reference and re-verified by a maintainer-run agent on version bumps** (no code generator), the **version-pinned gate fail-closes on any wire-shape change** per installed tsgo version, and a **parity-oracle test** asserts the Rust client is byte-for-result identical to the official JS client (which is retained ONLY as that oracle); a wire-divergent build fails the gate and falls closed, never ships a silently-diverged client.
- **Cross-file type invalidation correctness (the highest-severity class).** The carrier cache must skip only *re-codegen*, never an engine re-check a dependency change requires (§2.7 split + `import_signature_hash`); the discriminating guard `dependency_change_rechecks_unchanged_carrier` is the defense. A regression here produces stale-but-plausible diagnostics — the worst IDE failure mode.
- **tsserver negative-resolution-cache poisoning** — a cold/missing carrier read can pin a sticky `TS2307` (§2.2 two-phase publish + bounded-block + eviction; guard `tsserver_cold_read_no_sticky_ts2307`).
- **Project references / `disableSourceOfProjectReferenceRedirect` / solution-style configs** — a `.vue` reachable through two Programs with redirect-dependent resolution. §2.6 now specifies the **correct** per-mode surface: DEFAULT (redirect ON) ⇒ `A` sees `B`'s **source** carrier (`CarrierIde`); `disable…: true` ⇒ `A` sees `B`'s **`.d.ts`-equivalent** API surface (`CarrierApi`). Ambiguous ⇒ fail closed. Monorepo correctness rests on a `composite` + reference + cross-package `.vue`-import fixture run **both** with and without the flag (Block 0/5 fixture obligation).
- **TSC surface (no plugin on `tsc`) + the `noEmit`/references coherence** — the **mirror-host / `ts.CompilerHost`** + generated-`extends`-tsconfig path (§2.4) is the no-fork TS<7 batch route and the TS≥7 fallback; **generated carriers NEVER touch the user's working tree** (source-tree sidecars are rejected, §4 — no bake-off). Relative-import fidelity is solved by the host `resolveModuleNames` re-root into the user tree (resolver-version-independent); the `noEmit`-vs-project-references hole is fixed (no-refs ⇒ `noEmit` diagnostics-only; with-refs ⇒ build mode so referenced `.d.ts` boundaries are actually emitted into the mirror, coherent with both §2.6 redirect modes). Residual: the **pre-Block-4 spike** validates the mirror-host model matches the user's own `tsc -b` diagnostics on a `composite`+reference+`paths` fixture, both with and without `disableSourceOfProjectReferenceRedirect`.
- **Bare `.vue`/`.svelte` resolution + carrier discovery** — resolution is tsgo's NATIVE basename-append probe over a **proactively-provided** `.d.<ext>.ts` declaration overlay (+ its transitive closure), since tsgo exposes no module-resolution hook (§2.3); the bare-`./X.vue` resolution **mechanism** is **PROVEN (GATE 4 — probe-mechanism evidence)** and the production target is the `.d.<ext>.ts` declaration carrier (Rust-guard-enforced). Carrier discovery (making the carrier a Program member) uses the matching §2.3 mechanism by config shape (enumeration when the config matches the companion extension; **tsconfig-virtualization** when it does not). The one **unproven** case → Block-5: tsconfig-virtualization for root-set injection under a `.vue`-specific `include` / `files`-list config.
- **Proactive declaration-overlay graph — stale-pass close + re-open race RESOLVED.** tsgo has no module-resolution hook, so every `.d.<ext>.ts` declaration overlay a transitively-importing carrier needs must already be OPEN when that carrier is type-checked (§2.3); the `DeclOverlayOwner` is the sole lifecycle authority for that overlay graph, opening the transitive closure reachable from every open carrier root and closing an overlay once the last reaching root drains. The owner's open/reconcile revalidation originally checked only "is the reaching root still OPEN", which is insufficient under **two overlapping closure passes**: the closure pass runs inside a `background_init` invocation, and two overlapping workspace-folder / vite-config rebuilds can leave an older pass (past its pre-pass generation gate) running concurrently with a newer one. The older pass computes a root's reachable-declaration set from its OWN (now-stale) analysis; if the newer analysis reaches a declaration the older pass's analysis does not, the older pass's reconcile could DROP that root's edge and close the overlay — stranding the still-live root's bare import on `TS2307` (transient/self-healing, but a real ordering hazard). **Invariant (the fix):** each reaching-root edge is stamped with the closure-pass generation that established it, and a pass may REMOVE an edge only when its generation is at least as new as the edge's stamp; the close of an emptied overlay re-checks the slot's high-water reachability generation against the deciding pass's generation, so **a stale closure pass may no-op but never closes an overlay still reachable from a newer live root analysis**. **Symmetrically on the ADD side**, a per-ROOT authoritative-reconciliation high-water mark gates re-records and re-opens: a closure pass OLDER than a root's high-water can neither re-record a reaching edge nor re-open an overlay a newer pass already reconciled away and closed, and BOTH add paths — `open_overlay`'s single-edge add AND `reconcile_root_reachability`'s add loop (which records each edge through the SAME atomic gate-and-record) — read the high-water and record the edge under ONE shared per-root critical section, atomic against a concurrent reconcile advancing the high-water, so a newer pass can never advance-and-close BETWEEN an older add's gate and its record (which would otherwise let a stale add re-record/re-open the overlay after the close). A `did_close`-side release is the current ownership truth (a genuinely closed root) and is never superseded by a stale-pass stamp. The pre-existing per-declaration-path serialization (the per-path async lock) and the in-flight-aware close-pending flag are preserved — the close-lifecycle ABA generation and the per-pass reachability stamp are independent gates. Discriminating regressions pin the stale-removal (a stale pass cannot erase a newer pass's edge), the inverse (a genuinely unreached overlay is still eventually closed), the symmetric stale-ADD (a stale pass cannot re-record or re-open an overlay a newer pass closed), and the gate↔record atomicity on BOTH add paths (a high-water advance landing between an add's gate and its record — `open_overlay`'s single-edge add and `reconcile_root_reachability`'s add loop — still leaves the add gated).
- **Carrier path is in the USER namespace — resolution-conflict fail-closed (§2.2/§2.6).** The component-carrier path (`{name}.vue.tsx` / `{name}.svelte.tsx`) is **path-collision-free against a *different* real source extension but NOT a Verter-reserved namespace**, so two model conflicts fail closed rather than shadow real user resolution: (a) a real user file at the **exact carrier path** ⇒ `Ambiguous`, no overlay placed (Verter never shadows it); (b) a **same-stem Svelte rune** (`Foo.svelte.ts` beside `Foo.svelte`, the GATE-5 `.svelte.ts`-before-`.svelte.tsx` probe) ⇒ DETECTED ambiguity, no silently-wrong edge. Guards `carrier_never_shadows_real_user_file` + `same_stem_svelte_component_rune_fails_closed`. The non-fail-closed dissolution is the future static module-resolution-map API (an upstream tsgo capability not in the shipped `--api`), recorded as the future enhancement; fail-closed holds until it ships.
- **Plain-script `.vue`-import DX under tsgo (first-class requirement, §2.9)** — importing a `.vue` from a plain `.ts`/`.js` and getting enhanced types is an in-process `getExternalFiles` plugin capability on tsserver, but tsgo **cannot load in-process plugins** (typescript-go #2824), so under tsgo it is served by the `--api` FS-overlay + companion-extension redirection (PROVEN, GATE 4). Its own cross-engine DX contract + fixtures (§2.9), a primary IDE-DX bar.
- **SHARED-engine mode (DEFERRED to a spike-gated phase, §2.10/Block 8) — attach to the editor's own tsgo.** **Deferral row.** SHARED is **NOT a Block-5 deliverable** — it is deferred to a **separate, later, spike-gated phase (Block 8)** that OPENS with a live-spike investigation and SCOPES everything before any implementation (spike-first → scope-then-implement); OWNED (Block 5) is the universal correctness baseline and always sufficient on its own. **Open SHARED-capability unknowns the spike must settle (the gate for the phase):** (#2 — gates ALL of SHARED) whether a third-party extension can obtain the editor's tsgo connection/pipe via the VS Code Native Preview `ExtensionAPI`; (#1/#3 — the Part-B proxy unknowns) the B2 TS-LSP-proxy feasibility for serving features over the attached session AND intercepting/mapping the editor's diagnostic push. **Deferred ruling:** the SHARED-diagnostics mechanism (`--api`-pull vs `--lsp`-push-mapped) is part of the post-spike scoping, **NOT decided now**. **Proven (so the spike starts from fact):** the `fromLSPConnection` `--api` checker-attach-over-the-minted-pipe mechanism works (a Block-5 probe used it) — the SHARED-specific unknowns are about ACCESS to the editor's engine + the proxy, NOT the provider/transport SHAPE; the phase is additive on Block 5's reusable transport/provider seams, not a provider rewrite. **Verified constraint that shaped the (deferred) design:** an attached `API<true>` has NO content channel (`fs` is spawn-only; `LSPUpdateSnapshotParams` is `{openProject?}`; no `openFile`/`overlay` method) — so carriers are injected as **LSP `didOpen` overlay documents on the shared `project.Session`** (verified: shared session's overlay store is what the checker reads), NOT through the API client. Residual risks the phase carries: (a) **editor availability** — only VS Code (Native Preview `ExtensionAPI`) exposes the pipe today; other editors run OWNED until they expose it (an editor-side gap, tracked per editor); (b) **program-eligibility in the shared session** — if any carrier in a **redirect-ON reference closure** can't be made program-eligible, **the whole closure falls over to OWNED** (per B1 — never per-file, never per-single-tsconfig); (c) **`unstable`/async-only/lifecycle-coupled** — re-attach + re-open overlays on editor tsgo restart, fail over to OWNED meanwhile. All fail-safe: SHARED never yields a wrong result, only falls back to OWNED. Guards (in Block 8, moved from Block 5): `tsgo_shared_mode_carrier_injection` + `shared_mode_failover_is_per_reference_closure` + `shared_mode_requires_full_ts_lsp_proxy` + `shared_mode_no_unmapped_carrier_path_leak` (final assertions pinned when the phase is scoped by its spike).
- **Cross-platform identity** — one canonical identity layer shared by VFS + mapper + both adapters; drive-casing/UNC/case-collision/symlink/pnpm tested (§2.6/§2.7; guard `tracked_paths_are_portable` + a cross-platform real-provider test).
- **tsgo interactive concurrency** — the interactive lane is async/priority-laned from the start (`unstable/async` for the `--api` typecheck/diagnostics surface, the `--lsp` surface for interactive features, §2.3/§2.7); the `unstable/sync` client is used only for the Block-0 gate and the batch baseline. **Cancellation is surface-specific (Finding 1):** `--api` has NO wire cancel (client-side abandonment only — concurrency comes from the async client, not a wire cancel), while the `--lsp` feature surface uses real `$/cancelRequest`.
