### 6.4 `LocatorLoweringKey`

The SESSION-SIDE warm-memo key = the `ResolvedDeclSlotIdentity` slot + `AuthoredBodyLocator` + `parse_env_hash` + `resolve_env_hash` (RULED — mixed-env keys must be UNCONSTRUCTIBLE): `type_env_hash` / `lib_env_hash` / `project_identity` participate TRANSITIVELY through the slot's own env tail — never as standalone key fields or constructor parameters, so a "slot from env A, dims from env B" key cannot be formed BY SHAPE (keeping standalone T/L/J and validating equality in the constructor was REJECTED — duplicate identity in a hot key, a deletable invariant, extra hash/compare surface). A `{locator + resolve_env_hash}`-only key without the slot would still alias distinct lowered nodes. Content-free (no content/whole hash — R6); never appears in a graph-free / lower-crate DTO. `LowerLocator` is strictly UNSUBSTITUTED and carries NO caller projection axis — the body lowers under the FIXED `LocatorShape` context (below); substituted demands route through `Instantiate { args }` (whose `args` are the R6 `SemanticNodeId` value-root carve-out), and `Instantiate` owns substitution plus ALL demand-sensitive reduction. A substitution hash without a resolvable param→node mapping is an identity, not executable substitution state — it cannot key a first-class lowering query.

**Memo identity (RATIFIED — two independent codex legs converged; a code-verifying decider fixed the shape).** `LocatorLoweringKey` enters the graph through a FIRST-CLASS `SemanticQueryKey::LowerLocator { key: LocatorLoweringKey }` variant with its own `FamilyKey::LowerLocator` arm — NOT by overloading `Instantiate`, NOT via any side table. Family fields: `slot`, `locator`, `parse_env_hash`, `resolve_env_hash` — and NOTHING else (`type_env_hash`/`lib_env_hash`/`project_identity` are SLOT-CARRIED, above): NO substitution axis (strictly unsubstituted, above) and NO caller `ProjectionReductionContext` / `ModeSlot` axis. The per-key spec renders the env dims as `P R T L J` but MUST state that T/L/J are slot-transitive, not standalone fields. The authored generic body SHAPE is identical across modes/demands/provenance/merge-roles — full-PRC keying would fragment the family and invite pre-substitution materialisation under the wrong demand state. One reusable body-shape family per locator/env; the full projection axis lives on `Instantiate` alone. Routing locator lowering through bare `Instantiate` was REJECTED: `Instantiate { base, args, context }` has no locator axis, so whole-body vs sub-position vs macro-payload demands under the same slot would either alias distinct lowered values or force fabricated instantiation identities.

**The `Instantiate` P complement.** Once `build_instantiate` composes a locator/`DeclBodyMemo`-derived body, the cached `Instantiate` value depends on the parse env — and a parse-env-only change (file content unchanged) is NOT caught by the `FileWholeHash` self-root rail (`SnapshotKey = (canonical, whole_hash, parse_env_hash)`; project-generation rejection is a coarse freshness fence, not query identity). `InstantiateContext` therefore gains `body_source: InstantiateBodySource`, a SEALED two-state source-kind key folded into `FamilyKey::Instantiate` — NOT a bare `Option` (an `Option` hides meaning and is too easy to forge): `FileBacked(ParseEnvHash)` iff the compute may read ANY real-file parse-derived input (`IndexedReady.shallow_state`, prepared declarations, `DeclBodyMemo`, the Vue synthesized default state); `NonFile` ONLY for the true non-file bases (`""` / `"__builtin__"` / `"<synthetic>"`) whose values genuinely do not depend on the parse env — per R21, an unconditional P would false-miss every parse-env-insensitive instantiation. The dim type is the sealed `ParseEnvHash` newtype (`locator_identity.rs`); the two constructors are sealed (see the construction gate below) — call sites never choose freely. Two lowerings differing only in the `FileBacked` P are DISTINCT FAMILIES — never competing candidates under one slot (no `FAMILY_SLOT_CANDIDATE_CAP` churn across env variants). Contributor rule (BINDING): cross-file real-file contributor bodies demanded while composing an `Instantiate` result — module-augmentation stitch bodies foremost — MUST route through their own source-kinded query (`LowerLocator` keyed by THAT contributor's locator + `ParseEnvHash`); direct inline lowering of a cross-file contributor body inside another file's `Instantiate`/stitch compute is FORBIDDEN. The current `ReadSetSignature` rail is NOT a parse-env rail (`FileWholeHash`/Parse/RouteSurface facts do not carry or validate a contributor `ParseEnvHash` — parse facts are content-addressed); a value-side parse-env fact for the BASE body was considered and REJECTED (base P is key-side via `FileBacked(P_base)` — a base-side fact would duplicate that rail). Same-file merged contributors may lower inline (they share the owner parse env); heritage bases continue through carrier/ref queries, never inline cross-file body lowering.

**Parent transitive contributor rule (RULED — per-contributor queries alone are NOT sufficient on a WARM parent).** A warm parent `Instantiate` returns already-folded contributor nodes without re-running the child `LowerLocator`, and `MemoEntry::validate` checks only the stored `ReadSetSignature` facts — the augmentation facts recorded today (`ModuleAugmentationIndexShape` + per-augmenter `FileWholeHash`) fold `parse_stable_hash`, not `parse_env_hash`, so a parent built when a contributor had parse env P0 would warm-hit after that contributor moves to P1 with unchanged content. Therefore: when an `Instantiate` result folds ANY cross-file real-file contributor body into the parent value, the parent `ReadSetSignature` MUST record one typed source-env observation per folded contributor — a first-class `FactVersionRef::FileSourceEnv { canonical_id, parse_env_hash, parser_version, file_language_id }` arm on the resolver-core fact rail (field names match the existing `FactVersionRef` style) (adding it is a REVIEWED SCHEMA EVENT under the closed-fact discipline), taken via the exact-artifact observation API (`observe_file_source_env_from_artifact_key(...)`-style — from the artifact/source key the contributor `LowerLocator` actually used, never re-derived from canonical/path/env at the stitch site, never a stale index entry) — validated STRICTLY against the live `StoreView` at warm-hit time through a dedicated source-env validation branch comparing exactly those four fields against the view-current artifact identity: a warm parent hit REJECTS if any recorded contributor source-env identity differs, is missing, tombstoned, or untracked, even when `FileWholeHash` and `ModuleAugmentationIndexShape` still validate (content validity stays on the separate contributor `FileWholeHash` fact). The contributor canonical participates in the reverse index through the existing fact canonical-extraction path. Contributor source-env identity that cannot be observed coherently routes the parent result through `ReturnOnly`. `self_root_canonicals` stays `{base} ∪ {contributors}`; the observation is value-side validity only — `query_key_spec` gains NO contributor digest axis (`body_source` remains the base source-kind axis), and warm parent reads never re-run child queries.

**Conditional per-key spec mask (RULED).** The query-key spec's `Instantiate` env-dim row is CONDITIONAL by `body_source` (`EnvDimSpec::Conditional`, one `Instantiate` query tag — no variant split): `FileBacked(P)` ⇒ `P R T L J`; `NonFile` ⇒ `R T L J`. A single static mask is wrong in both directions — `P R T L J` over-claims for `NonFile` (contradicting the R21 clause above); `R T L J` hides the file-backed parse-env dependency. The generated spec table renders both cases; guards exhaustively match `InstantiateBodySource` and prove `FamilyKey::Instantiate` folds P only for `FileBacked`.

**Backfill bound.** NO backfill across locator prefixes: a whole-body result never backfills a sub-locator entry (it does not prove the sub-position was materialised under its own lexical/type-param context), and never the reverse — the same lattice discipline as the existing exact-path satisfaction rule that rejects deep↔prefix satisfaction. With the fixed `LocatorShape` context there are no mode/demand siblings on a `LowerLocator` family — one shape entry per locator/env; projection-time variants live (and backfill, recorded-materialised-point gated) on `Instantiate` under the existing family rules. A future explicit materialised-locator-point fact plus a proven locator satisfaction relation may extend this; this design does not.

**Fail-closed slot/locator gate + sealed construction.** `LocatorLoweringKey` and `InstantiateContext` have PRIVATE fields with checked constructors — direct struct literals are impossible outside the defining module (invalid identities are UNCONSTRUCTIBLE, not merely rejected later; the R6 exhaustive-destructure witnesses stay compatible because they destructure inside the defining module, and outside readers use accessors — `family_and_slot` folds via getters). `LocatorLoweringKey::new_unsubstituted(slot, locator, parse_env_hash, resolve_env_hash) -> Result<Self, LocatorKeyError>` performs the slot/locator anchor match BEFORE key creation (there are NO standalone T/L/J parameters to cross-check — env coherence is by construction, per the slot-carried rule above): it REJECTS with a typed error unless the locator anchor matches the slot ownership exactly (`anchor.canonical_id == slot.defining_canonical`, `anchor.symbol == slot.merged_symbol_name`, `anchor.space` maps to `slot.symbol_space`). A mismatch is a malformed identity — never a silent lower under the wrong slot, and never deferred to a dispatch-time `ReturnOnly` (the wrong family/lane must never come into existence). `InstantiateContext::file_backed(...)` / `::non_file(...)` are the ONLY source-kind constructors.

**R6 witness is RECURSIVE for the new B1 substrate.** The landed `LocatorLoweringKey` R6 witness (`crates/verter_session/src/locator_identity.rs`) does NOT prove only the standalone env dimensions while trusting composite fields as `_`. It is a sealed `R6KeySafe` witness proven RECURSIVELY over EVERY key field — `slot`, `locator`, `projection`, AND every dimension (the B1-landed shape; B2 removes the `projection` + `substitution` fields AND the standalone T/L/J dims (slot-carried, above) per the paragraphs above, and the witness re-proves over the narrowed `slot + locator + P + R` key) — via exhaustive-destructure witnesses (no `..`, no `_` composite field) on each content-free composite (`AuthoredBodyLocator` and its leaves, `ProjectionReductionContext` and its enums, `ResolvedDeclSlotIdentity`, `SessionDemandIdentity`). ## 7. [P1] — span-recovery-before-identity gate (BLOCKING for B1)

### 7.1 The soundness problem (verified)

`ObjectProperty` (`verter_type_expr/src/lib.rs:651`) derives `PartialEq`/`Eq`/`Hash` over ALL fields **including `spans: MemberSpans`** (`#[serde(skip)]` excludes it from the wire but NOT from identity; `MemberSpans` is itself `Eq + Hash`). The same holds for `MethodSignature`, `FunctionExpr`, `IndexSignature` (derived), and `FunctionParam` (hand-written `PartialEq`/`Hash` include `.span`). Therefore **member spans participate in node identity**: two structurally-identical members with different declaration sites compare unequal and hash differently.

The synthesized-(d) `ResolvedLocalType` path builds members via `ObjectProperty::with_spans_public(name, ty, field.is_optional, false, MemberSpans::name_only(field.span))` (`verter_semantic/.../macros.rs:1423`), where `field.span` is the REAL authored prop-name span. If a narrowed fact reconstructs/interns an `ObjectProperty` WITHOUT recovering `MemberSpans::name_only(field.span)` — e.g. with `Span::default()` / byte-0 — the reconstructed node is `Eq`/`Hash`-UNEQUAL to the authored node. That is a soundness failure (identity divergence → cache-key divergence). This is a **pre-implementation gate**, not carry-forward debt.

### 7.2 The sound mechanism

**Recover-via-locator-before-identity.** Spans are NEVER stored as fact fields (facts stay content-free; over-storing a `Span` as a fact-identity field is ITSELF a violation, enforced by the `NoStoredSpan` witness of §9). Instead, every fact family that reconstructs/hash-interns an IR struct whose derived identity includes span fields MUST carry a **producer-emitted origin locator** sufficient to recover the exact spans from the producing-canonical retained `DeclBodyMemo` snapshot, BEFORE any `Eq`/`Hash`/interning/projection/reconstruction.

**Explicit per-span-class contract (codex REVISE finding 4 — "member-origin path" alone is insufficient).** The design REQUIRES an explicit origin locator for EVERY identity-participating span class, not one blanket "member-origin path":

| Span class | Bearing struct(s) (`verter_type_expr/src/lib.rs`) | Required origin locator |
|---|---|---|
| `MemberSpans` | `ObjectProperty` (:651/:665), `MethodSignature` | a member-origin locator recovering `MemberSpans` (declaration / name / type_annotation spans) |
| `IndexSignatureSpans` | `IndexSignature` | an index-signature-origin locator recovering `IndexSignatureSpans` |
| `FunctionSpans` | `FunctionExpr`, `MethodSignature` | a function-origin locator recovering `FunctionSpans` |
| `FunctionParam.span` | `FunctionParam` (hand-written `PartialEq`/`Hash`) | a per-parameter origin locator recovering each `FunctionParam.span` |

A single **explicit `SourceSynthetic` variant** is permitted ONLY for a TRULY synthetic node with no authored origin (documented per site); it is never a fallback for an authored node whose locator was omitted.

Concretely for the synthesized-(d) object-member schema (the [P1] amendment target): the `ResolvedLocalTypeFact` object-member schema carries, per member, `name` + REQUIRED `optional: bool` + `ty` (fact-or-locator) + a **producer-emitted `MemberSpans` origin locator** recovering `MemberSpans::name_only(field.span)`. `readonly = false` / `visibility = Public` are producer-constants (documented as such). The origin locator is emitted by the producer, NEVER derived from `*.span` at reconstruction and NEVER an embedded `TypeExpr`.

### 7.3 Discriminating fixture spec (`fixture_p1_span_recovery`)

Coverage matrix — one fixture per identity-participating span class: `ObjectProperty`/`MemberSpans` (property member), `MethodSignature`/`FunctionSpans` (method member, also exercising `optional`), `IndexSignature`/`IndexSignatureSpans` (`[k: string]` vs `[k: number]`), `FunctionParam.span` (param span in hand-written identity), `FunctionExpr`/`FunctionSpans`. Each fixture drives the REAL reconstruction path (the body-source provider deref, not a hand-built struct) and asserts:

1. **Positive**: the node reconstructed via `fact + origin locator` through the real provider path produces an IR struct whose spans are byte-identical to the pre-change producer output (`MemberSpans::name_only(field.span)` for the synthesized case), so it is `Eq`/`Hash`-EQUAL to the authored node.
2. **Negative (MUST FAIL pre-change; PASS post-change)**: reconstructing the same node with `Span::default()`/zero (or lacking the origin locator) produces a struct that is `Eq`/`Hash`-UNEQUAL to the authored node. The fixture asserts BOTH `reconstructed_with_locator == authored` AND `reconstructed_with_default_span != authored` — proving discrimination. It fails against the pre-change tree precisely because default/reconstructed spans produce different `Eq`/`Hash`.
3. **Over-storage negative (structural)**: no fact family carries a `Span`-typed field — enforced by the `NoStoredSpan` marker witness (§9), NOT by `NoTypeExpr` (which admits `Span`). A fact family that added a `Span` field must fail to compile.

This closes [P1]: the synthesized object-member arm now specifies span recovery, and the fixture discriminates default-span reconstruction.
