# Runtime-constructor matrix — mutation receipts

Every receipt follows the shape `.claude/skills/testing/SKILL.md` §1a requires:
verify the starting SHA; run an **unplanted control** and require non-zero
selection and GREEN; prove the plant is NEW, PRESENT and UNIQUE and that it
actually changed the file; run the guarding selector and record the **named
RED**; restore; re-verify clean tree identity; run **GREEN** again.

The receipts are generated by `.feedback/plant.sh`, which **aborts rather than
running** if any precondition fails — including a zero-selection selector, a
control that is not already green, a marker that already exists, or a plant whose
`git diff --numstat` is empty. That last check is not decoration: it caught a
plant of mine that applied cleanly and changed nothing semantically (see P7).

Per-receipt files: `.feedback/receipts/<ID>.md`.

## Assertions that were NOT made to fail

Disclosed rather than papered over. Each is a real assertion in the delta that no
plant in this campaign reddened, with why.

1. **Negative-control property (1), "still publishes something"** — native
   `ShapeTag::Absent`, compat empty-string. No plant made a control publish
   nothing while staying non-fold. Property (3), the exact pin, subsumes it —
   `Absent` is not the pinned shape, so a genuine loss still fails the cell — but
   property (1) was never independently reddened.
2. **The published-prop-count assertion** (`published.len() == cell.props.len()`
   and its compat twin). No plant duplicated or dropped a prop.
3. **The cross-mode AGREEMENT assertions** — `cold == warm`,
   `sequential == concurrent`, `scalar == batch`, `base == overlay`, and the
   compat equivalents. **Structurally unreachable by these plants:** every plant
   is mode-independent, so it reddens the per-mode EXACTNESS assertions in every
   mode at once and leaves the two sides agreeing on the same wrong answer.
   Reddening an agreement assertion needs a genuinely mode-dependent defect — a
   view or cache race — which cannot be injected deterministically by a source
   edit. This is precisely why the per-mode exactness assertions exist beside
   them: agreement alone was never the guard.
4. **The batch and overlay slot-shape assertions** — `batched.len() == CELLS.len()`,
   the missing-canonical sentinel panic, the typed-failure panic in the batch arm.
   Not reddened.
5. **The `Ok(None)` forbidden-swallow arm** of the exposed-output regression. No
   plant demotes a typed failure to absence.
6. **The `Err` arm's exact-triple check** in that same test is, by construction,
   not verdict-bearing on an input whose correct answer is success — the test's
   own doc comment says so. F3's diagnostic oracle exercises the same predicate
   in a verdict-bearing way, but the in-test check cannot flip a verdict.

Items 3 and 6 are structural properties, not gaps that more effort would close.
Items 1, 2, 4 and 5 are simply uncovered by this campaign.

**Two invalid B2 attempts, recorded rather than dropped.** The first two plants I
wrote for B2 produced NO `Summary` line at all — they did not compile, because
they destructured a tuple pattern from an `Option`. A run that never compiled is
not a RED: it proves nothing about the assertion, exactly as a green run proves
nothing when the plant failed to apply. Both were discarded and rewritten; only
the third, which compiled and produced a named failure, is recorded above. The
harness surfaced them because it prints the `RED summary` line verbatim and it
was empty.

**Note on planting against uncommitted work.** `plant.sh` restores with
`git checkout -- <file>`, which reverts to HEAD — so running it while an
uncommitted fix lives in the target file silently destroys that fix. That
happened once with the B1 fix; it was caught immediately by re-grepping for the
new call, re-applied, and committed BEFORE any further plant. Commit the fix
first, then plant.
