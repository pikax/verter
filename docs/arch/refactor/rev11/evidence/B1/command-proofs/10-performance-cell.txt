0. Protocol correction from the prior (stale) capture
--------------------------------------------------------------------------

The previous evidence at this path recorded a candidate SHA that was not the block's tip, and
deviated from the locked `alternating_invocation_abba` policy: it built only ONE binary (the
candidate) and argued by source-diff that a baseline rebuild was unnecessary, rather than
building both arms and alternating invocations between them. That reasoning was not wrong about
the source-identity claim, but it is not the locked protocol, and the corpus/toolchain/machine
noise a "real" second binary would surface (linker layout, different section addresses, a
different unit-graph hash even for identical source) is exactly what an ABBA session is for.

This capture builds BOTH arms from real, separate release builds and alternates invocations
between them in the exact order `performance-gates.toml`'s `[statistics] interleave_policy`
requires: "baseline and candidate binaries are built with the identical toolchain and profile
and invoked alternately within one session in A,B,B,A order, at least four invocations per arm".
