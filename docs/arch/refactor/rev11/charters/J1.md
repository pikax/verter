## 1. Context

Three independent CSS-family syntax implementations coexist in the workspace today, plus a further set of
readers that independently re-derive CSS structure from bytes instead of consuming any of the three. The
maintainer's parsing-only bound (`MAINTAINER-RULING-J-TRAIN-SCOPE-IS-PARSING-ONLY.md`), narrowed by two
addenda and generalised by a governing invariant (`MAINTAINER-RULING-ONE-CSS-PARSER-PARSE-ONCE.md`), settles
which of these are Track J's concern. That invariant is the single test every row below is judged against:
**a second parse, or a scan over already-parsed input, is a violation regardless of which surface performs
it.** A consumer needing CSS structure reads the existing parse result; if the result does not carry what it
needs, the fix is to extend what the parse records, never to add a scanner beside it. The inventory below is
this charter's full investigation to date — it is not claimed exhaustive; a newly discovered five-dialect
CSS reader is presumptively in scope and needs a recorded disposition against this same rule (J1-A24).

Additionally, Vue-owned CSS semantics (scoped selectors, `v-bind()`, `:deep`/`:global`/`:slotted`) are
currently implemented in **JS**, not Rust, on the Vite bundler path: `packages/unplugin/src/index.ts`
resolves the user project's own `vue/compiler-sfc` and calls `compileStyleAsync()` (`index.ts:822-855`) — a
live deviation the maintainer's directive requires removed. The non-Vite path calls Verter's legacy NAPI
`processStyle()` (`index.ts:856-869`).

The maintainer has ratified a clean-cutover directive: `StyleSyntaxIr` becomes the sole CSS-family syntax
authority for the five native dialects; `lightningcss` is removed completely; no legacy
parser/printer/normalizer path survives beside `StyleSyntaxIr`; Vue-owned CSS semantics are executed by
Verter (Rust), not by JS/`vue/compiler-sfc`; external preprocessing (SCSS/Sass/Less/Stylus → CSS) stays
JS/builder-owned via a sealed round-trip protocol Rust never invokes directly. The architecture ruling
additionally moves J4's parser-coverage/no-fallback/no-duplicate-grammar evidence into J1 (J1 cannot delete
the legacy route before the replacement's Native coverage is proven), and sets J1's capability floor:
parity-gated for every currently-retained Native operation — `Unsupported` is not an acceptable temporary
landing state; SCSS/Sass/Less/Stylus **lowering** is `External`, not `Unsupported` (lowering itself stays
JS-owned; that's not a Verter gap). A separate architecture ruling
(`ARCH-RULING-CSS-FRAMEWORK-CONSTRUCT-VALIDITY.md`) assigns carrier-construct validity, diagnostics, and
ambiguity handling to J4; J1 supplies only the prerequisite neutral IR facts (J1-A19) and must not itself
claim that authority.

## 2. Intent Contract

**Actor/problem.** Verter's CSS-family syntax and Vue-CSS-semantics ownership is split across three parser
implementations and two languages (Rust + JS), plus the further hand-rolled readers §1.1 rows 6-13 and row 23
name that re-derive parsed CSS structure from bytes. This is the CSS-family instance of splitting a shared substrate
the way multiple type-resolution engines would — the project's "exactly one engine" principle for types
applies by direct analogy.

**Required observable outcomes:**
- `StyleSyntaxIr` (inventory row 1) is the only entry point that parses CSS/SCSS/Sass/Less/Stylus syntax for
  any decision feeding compiler output or Lightning CSS removal, anywhere in the production Rust workspace —
  for semantic-fact extraction, Vue-owned byte transforms, Svelte's CSS scoping/analysis, compile-time
  diagnostic arbitration (row 6, once its §1.1 work lands), every inline `style=""` declaration-list read that drives
  emitted VDOM/SSR runtime codegen (rows 7-8), the inline `style=""` read that feeds the `css_var_flow`
  analysis query (row 9 — an analysis-query input, not compiler output), the code-action provider that
  re-derives selector/rule structure to emit destructive edits (row 10), and every LSP CSS reader that
  re-derives CSS structure where Verter's own parse already carries the answer (rows 11-12). This is scoped
  to items that parse CSS or re-derive parsed
  structure (§1.1) — it does not reach rows 20-22 (§1.1's dispositions govern them), which consume a foreign
  parse, not silently forbidden by omission.
- `lightningcss` is absent: not a Cargo dependency of any crate, not imported anywhere, no reachable
  production code path calling it.
- All Verter-owned CSS byte transformations (Vue and Svelte) go through `CodeTransform` as the sole
  edit/mapping mechanism; no second style-specific edit/mapping implementation exists. Output is
  `input bytes + explicit framework edits`, never `parse(input) -> serialize(AST)`.
- The NAPI `process_style`/`ProcessStyleOptions`/`ProcessStyleResult` wire contract (row 14) is removed and
  replaced by an explicit three-way boundary API — `analyze_style` / `prepare_style_for_preprocessor` /
  `transform_vue_style` (exact names are an implementation decision; the three-way separation is not).
  `compose_source_maps` is the directive's named fourth op but is explicitly NOT J1 scope — J3 owns generic
  multi-stage source-map composition (`verter_source_map`); J1 must not build a CSS-specific composer
  standing in for it.
- Both the Vite and non-Vite `packages/unplugin` bundler paths invoke Verter's own Rust `style_planner`
  transform for Vue CSS semantics (scoped, `v-bind()`, `:deep`/`:global`/`:slotted`, `:is`/`:where` per their
  real conditional scoping rule, scoped-`@keyframes` identifier uniqueing, CSS Modules class analysis).
  Neither path calls `vue/compiler-sfc`'s `compileStyleAsync()`. `:global`, `:is`, and `:where` are a
  distinct forwarding-selector class from `:deep`/`:slotted`, and NOT uniform among themselves:
  `:global()` unconditionally discards its surrounding local selector context; `:is()`/`:where()` are
  CONDITIONAL on an outer local anchor (§3 oracle table, A10f).
- No lightningcss-style modern-syntax normalization of untouched declarations survives anywhere in the
  transform path (e.g. `@media (min-width:1px)` must not silently become `@media (width >= 1px)` — a
  confirmed live regression today, §3).
- External preprocessing (Sass/SCSS/Less/Stylus → plain CSS) continues to be JS/builder-executed. J1 OWNS
  the complete external-preprocessor RESULT boundary (row 18): it extends `BlockOverrideEntry` so the
  round-trip carries all six fields the directive's preprocessor contract requires as distinct typed data —
  processed bytes, source map, dependencies, diagnostics, processor identity+version, and configuration
  fingerprint — not folded into today's single untyped `supplied_provenance: Option<String>`. J2's "exact
  identities" scope is downstream: J2 decides how these opaque VALUES combine into the canonical style
  content-identity/cache-key model; J1 supplies the typed fields.
- The Rust-LSP baseline (no preprocessor provider) analyzes authored CSS-family syntax natively but returns
  `External`/unavailable for any result depending on preprocessing it cannot perform — never a silent
  internal preprocess.
- The capability matrix's product×dialect×operation closure (`capability-matrix.md`) is ratified from
  `VERIFY` to concrete dispositions (A9): the single aggregate `CSS | parse/format/index/transform` seed row
  splits into per-product rows — `Vue (CSS-family)` and `Svelte (CSS-family)` — each carrying every dialect
  (CSS/SCSS/Sass/Less/Stylus) × operation (parse/format/index/transform) cell that product exercises.
- `extract_css_class_names` (row 15) is replaced by `StyleSyntaxIr::complete_static_classes()`.
- The SFC compile-time style pipeline applies Vue-owned transforms and Native CSS-Modules class *analysis*
  consistent with the directive's required pipeline ordering: module-class analysis is not silently
  restricted to `dialect == Css`, and the 3-stage cascade (v-bind → modules → scoped) does not re-parse
  unchanged content between stages (A10i) — a real, found defect: today every stage independently calls
  `parse_style_ir` regardless of whether the previous stage changed any bytes.

**Forbidden observable outcomes:**
- No second CSS-family syntax authority for the five native dialects, for any decision feeding compiler
  output or Lightning CSS removal — Vue, Svelte, or otherwise (§1.1 governs every row including row 5;
  Svelte's grammar is not a surviving exception to this bullet).
- No independent hand-rolled CSS declaration-list scanner (`split(';')`/`find(':')` or equivalent) at any
  call site that parses CSS itself (rows 7-9). No independent hand-rolled byte scan, regex, brace/comma
  walk, or comment/string mask re-deriving CSS structure Verter's own parse already carries, at the
  code-action provider that re-derives rule/selector extent (row 10) or either LSP CSS reader (rows 11-12) —
  per the governing invariant, "no re-scanning" applies regardless of surface.
- No dual Vue-CSS-transform implementation: `crates/verter_compiler/src/css/{scoped,modules,walk,prepass,mod}.rs`
  and `style_planner.rs` do not both exist performing the same job.
- No compatibility shim reproducing lightningcss-normalized byte output.
- No silent `Unsupported` landing state for any dialect/operation currently retained as working.
- No Rust-side invocation of external preprocessor tooling, filesystem, or subprocess execution to perform
  SCSS/Sass/Less/Stylus lowering.
- No JS package (`vue/compiler-sfc` or otherwise) implementing Vue CSS semantics that Verter owns.

**Authority/fallback order:**
1. `StyleSyntaxIr` — sole CSS-family parsing authority for CSS/SCSS/Sass/Less/Stylus (rows 20-22 consume a
   foreign parse and are not a fallback from this).
2. `verter_compiler::style_planner` — sole Vue-CSS-transform authority, operating on `StyleSyntaxIr` output
   via `CodeTransform`.
2b. Row 5's Svelte CSS policy modules (`svelte/runtime/css/{analyze,match,hash,render}.rs`, once §4's
   required work lands) — sole Svelte-CSS-transform authority, same shared parse, policy-only, no
   independent grammar.
3. External preprocessors (JS/builder-owned) — sole authority for non-CSS-dialect lowering, reached only
   through the sealed round-trip; Rust never invokes them.
4. `verter_semantic::analysis::style_syntax` — sole semantic-fact projector for IDE/LSP consumption, reading
   `StyleSyntaxIr` only.

No dialect/operation falls back from (1)/(2) to a second parser or transform implementation, for Vue or
Svelte.

**`format` operation:** no dedicated standalone CSS formatter exists in the workspace today (§3) and this
charter does not add one — the `format` cell in both new capability-matrix rows is dispositioned
`Unsupported`/not-Verter-owned explicitly (J1-A9), rather than left to be invented silently.

- **Cold.** Vue's style codegen runs up to three independent stages in sequence — `transform_vue_v_bind`

  Today EACH stage calls `parse_style_ir` independently even when the previous stage returned
  `StyleRewriteOutcome::Unchanged` — a real, found re-parse-of-unchanged-content defect (A10i fixes it): a
  stage returning `Unchanged` must hand the SAME already-parsed `StyleSyntaxIr` to the next stage. With that
  fix: for S applicable stages (1-3) of which K actually change bytes (0 ≤ K ≤ S), total `parse_style_ir`

lightningcss-backed route; a live, framework-specific parser remains a second syntax authority regardless of
non-legacy provenance or conformance-pinning purpose.

Concrete required work:

- Delete `crates/verter_compiler/src/svelte/runtime/css/parse.rs` and the grammar-owning portions of
  `types.rs`.
- Extend `StyleSyntaxIr` with whatever lossless spans, dialect distinctions, and raw-source-fidelity facts
  Svelte's byte-exact scoping requires — extending the shared authority, not building a second one.
- Re-home Svelte analysis/scoping (`analyze.rs`, `match.rs`, `hash.rs`) downstream of `StyleSyntaxIr`; these
  modules may survive as framework-specific *policy* only — they must not tokenize, reparse, classify new
  syntax, or maintain a competing grammar/AST node set. Proved by A11d's PAIRED structural-plus-review
  discipline, not the type witness alone: the tree-shaped parameter is nominally `StyleSyntaxIr` (Rust's
  nominal typing forbids a decoy/alternate tree type substituting for it, an in-crate invariant needing no
  cross-crate proof) — but nominal typing does NOT bound what the retained `source: &str` co-parameter is
  used for, so A11d additionally requires review-enforced body inspection confirming every `source: &str`
  read in `analyze.rs`/`match.rs` is span-slicing into an offset `StyleSyntaxIr` already recorded (e.g.
  `content[span.start..span.end]`), never fed to a tokenizer, lexer, regex, or independent parse entry
  point. A11b's single-parse-per-block call-count proof additionally bounds re-parsing (it would catch a
  second `parse_style_ir` call), but does not by itself catch a hand-rolled scanner that never calls
  `parse_style_ir` at all — that gap is exactly what A11d's review-enforced body inspection above closes.
- Replace `render.rs`'s grammar-level printing with source-preserving `CodeTransform` edits — the sole Verter
  transform mechanism. No alternate "canonical shared serialization" printer path is permitted.
- Remove the current double-parse: `validate_svelte_style_ir`'s admission-gate reparse is retired once
  Svelte's real transform consumes `StyleSyntaxIr` directly — one canonical parse per style block.
- `svelte_css_no_vue_reuse_guard.rs` stays grandfathered, byte-for-byte, per A11f — zero edits, not even
  mechanical ones. It is NOT amended with a new pattern list for the separate "no compiler-local Svelte CSS
  grammar/reparse" invariant; that is enforced structurally instead (A11d), not by extending this scanner.

**Mandatory acceptance gate, not best-effort:** Svelte's transform must remain byte-for-byte compatible with
the pinned `svelte@5.56.10` golden corpus (hashing, selector scoping, global/local constructs, nesting,
keyframes, comments, malformed-input recovery, spans/maps) throughout this convergence. If evidence during
implementation shows this parity cannot be met without regression, **J1 stops and escalates for maintainer
ratification of a Preserve/Defer exception** — not grounds to silently keep the old parser, per §7.

## 7. Abort/rescope

The template's literal trigger is "multiple semantic syntax authorities, an unaccounted dialect/product
contract, or a mapping/preprocessor owner outside the charter closure" with no numeric carve-out. §1.1 is
this charter's resolution of that trigger for every item found to date. §7 governs a **new** trigger firing
*during implementation*, after §1.1/§4's dispositions were already ratified: stop if evidence surfaces an
undocumented grammar authority not accounted for in §1.1, an unaccounted dialect/product contract, or a
mapping/preprocessor owner outside this charter's closure (e.g. a preprocessor-execution authority claimed
by Rust, or a source-map composition owner other than the J3-assigned `verter_source_map` crate).

Additionally, specific to this charter's own findings: stop and escalate for maintainer ratification if
implementation evidence shows a Native dialect/operation cannot reach parity without silently regressing to
`Unsupported` (parity floor violation), or if the Svelte CSS grammar convergence (§4) cannot meet its
mandatory byte-exact `svelte@5.56.10` parity gate without regression — in either case this is not grounds to
silently keep the old implementation; it is grounds to stop and obtain the required ruling.
