# F2 — InputBasis load waves negative facts retry

**Status:** LOCKED — contains binding acceptance criteria from the ratified timing directive; this charter is not separately authorized or dispatched. See the [landed timing ruling](../rulings/ARCHITECT-RULING-2026-08-23-TIMING-ARCHITECTURE.md).  
**Class:** Foundational.  
**Predecessors:** `F1`, `C2`.

## Objective

Make every reusable derivation explicit about the exact immutable observations it used while preserving bounded coherent load/retry behavior.

## Acceptance criteria

- `InputBasisId` identifies, as applicable, the exact document revision, relevant source-root/project revision, configuration/resolver epoch, provider/program-applied generation, and dependency read-set or dependency stamp.
- Every dimension is typed and non-interchangeable. A provider dimension is admitted only from a producer-owned exact applied-generation receipt; it is never synthesized from transport completion, sleep, or idle state.
- Positive and negative dependency observations are stable facts with the basis that made them valid.
- Value-side validation compares the relevant typed dimensions and dependency facts. It does not compare a universal `EngineRevision` or opaque workspace generation.
- Unrelated edits preserve unrelated candidates; no cache or flight may use `EngineRevision` as a universal invalidation/cache key.
- Load waves remain normalized, batched, coherent, no-progress detecting, and bounded by exact retry/churn/resource limits.

## Proof

Tests must cross each basis dimension independently, including a cross-file dependency edit and an unrelated edit. They prove exact invalidation, unrelated reuse, stable negative-fact behavior, and clean preloaded equivalence without sleeps, polling, or elapsed correctness thresholds.

## Non-scope

F2 defines and validates the basis; G2 owns flight lifecycle and H2 owns provider readiness receipts.
