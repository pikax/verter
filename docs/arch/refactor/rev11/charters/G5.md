# G5 — Scheduler pool host runtime convergence

**Status:** LOCKED — contains binding acceptance criteria from the ratified timing directive; this charter is not separately authorized or dispatched. See the [landed timing ruling](../rulings/ARCHITECT-RULING-2026-08-23-TIMING-ARCHITECTURE.md).  
**Class:** Foundational.  
**Predecessors:** `G3`, `G4`.

## Objective

Converge scheduler, pool, and host execution on G2/G3 ownership and remove duplicate readiness/admission mechanisms.

## Acceptance criteria

- Production queues remain bounded with reserved foreground capacity and priority-aware admission.
- Background work coalesces latest-wins, records explicit supersession, and remains bounded by active keys/documents rather than edit count.
- Background work runs when capacity permits; it does not require the whole server or all request handlers to remain idle for an arbitrary period.
- Semantic DAG duplication, duplicate pools/dedupe/task taxonomies, and transitional generation machinery are deleted only after their final owner exists.

## Required deletion

G5 deletes the global handler-idle readiness/admission role in `server/handler_guard.rs`: `HANDLERS_IDLE`, `HANDLER_ACTIVITY_EPOCH`, `wait_for_handlers_idle`, `wait_for_handlers_quiet`, `wait_for_idle_counter`, `wait_for_quiet_counter`, their server re-exports, the `workspace_scanner` wait call sites, and the displaced `DISCOVERY_IDLE_GRACE` and `BACKGROUND_MAX_DEFER` timing policies. `HandlerGuard` and `ACTIVE_HANDLERS` may remain observation-only if they no longer gate work and satisfy measured overhead; they are not readiness. G5 also removes the tsserver pseudo-idle admission bridge (`TsserverPendingRequests::{interactive_in_flight,interactive_idle}`, `TsserverTransport::wait_for_interactive_idle`, `request_background_batch_results_with_preemption`, and `BACKGROUND_IDLE_GRACE`) wherever G3 priority/capacity replaces it; H2 retains only external-provider protocol/liveness policy. K3 verifies the host/LSP deletion closure and deletes any missed residue before closing.

## Scheduler-owned same-key coalescers

G5 owns the scheduler's OWN coalescing, not only the idle/admission bridges above. `charters/K3.md`'s inventory assigns it these, and they are named here so the cutover has an owner that knows it: `SchedulerDag::{by_identity, waiters, file_waiters}` (`verter_scheduler` `dag.rs:611,616,620`) — the demand-MERGE index where a second `submit` of the same `WorkNodeIdentity` merges into the existing node instead of minting a second token, the `DepKey`-keyed group released together, and the per-`(canonical, generation)` request groups that mint the already-named `DedupJoinerEvent`; `Scheduler::nodes` (`scheduler.rs:1048`), whose losing creator BLOCKS on the shard lock and reuses the winner's `Arc<FileNode>` (`:2406-2412`) — the strongest join in that inventory; `Scheduler::scoped_cache_flights` (`:1073`, `:1606-1611`), the map behind `ScopedCacheFlight`; plus the `CompletionInner` completion rendezvous (`job.rs:249-256`) and the `CpuConcurrencySemaphore` permit counter (`cpu_concurrency.rs:36-95`), which are primitives rather than same-key joins and are preserved, not deleted.

G5 does not leave a second dedupe or admission taxonomy behind: `DedupeHook`, `DedupJoinerEvent`, `ScopedCacheFlight`, and the DAG rows above converge on one. K3 verifies the residual and deletes anything missed before it can close.

## Proof

Contention tests prove foreground progress and bounded background work without manipulating handler-idle state. Structural ownership evidence proves no second scheduler/readiness service survives.
