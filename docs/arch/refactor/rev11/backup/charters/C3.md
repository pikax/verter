# C3 — Project-aware Vue macro projection

**Status:** PROPOSED amendment / LOCKED. **Predecessor:** C2.

C3 retains sole ownership of project-aware imported Vue macro projection. It fulfils
the closed typed project-information demands accepted in BV1 using the canonical
project/type substrate. It cannot reinterpret framework options, replace Vue semantic
analysis/codegen, invoke the official compiler, or introduce open-ended fact bags.

## Closed BV1→C3 demand protocol

Every demand carries the exact prepared-root `SourceIdentity`, macro
`syntax_index`, closed macro role, closed product lane, typed subject identity,
`TypeScriptSemanticProfileId`, and `ProjectionPlanToken`. A subject is the closed
`TypedSubject { position, locator, lexical_owner }`, where `position` is
exactly `TypeArgument`, `locator` is the content-free
`MacroPayloadLocator` validated against the prepared-root identity, and
`lexical_owner` is the exact `TopLevelOwnerId`. C3 lowers that locator through the
canonical retained-snapshot service to owned `TypeExpr` typed IR; the demand never
contains source text, an OXC/AST handle, a resolver callback, or a raw semantic query.

The demand vocabulary has exactly one variant: `MacroPayload { role, subject, lane }`,
where `role` is `Props`, `Emits`, `Model`, `Slots`, `Expose`, or `Options`. `Props`,
`Emits`, and `Model` admit `RuntimeBindingNames`, `RuntimeConstructors`, `PublicApi`,
`Tsc`, and `Declaration`; `Slots`, `Expose`, and `Options` admit only the three
type-product lanes. When typed `defineProps` is wrapped by `withDefaults`, its demand
still names only the inner props type argument. BV1 retains the wrapping syntax,
association, and defaults application; none of them enters C3 demand identity.

This is the typed-IR macro shape retained from `CLAUDE.md`: C3 resolves one typed
subject through the single five-mode project dispatch and then applies a thin
role-specific normalizer. There is no macro-specific resolver, eager unrelated-import
walk, text reparse, or compiler-local fallback. Runtime-form object/array arguments,
the `withDefaults` object and its eligibility/merge semantics, and all other
source-local macro syntax remain parser/BV1-owned. They never lower to `TypeExpr`,
enter a C3 demand, or get merged by C3.

Each variant has one corresponding success payload:

- `RuntimeBindingNames` returns `MacroRuntimeBindingProjection`;
- `RuntimeConstructors` returns `MacroRuntimeProjection` with normalized
  props/emits/model shapes and typed member degradation;
- `PublicApi`, `Tsc`, and `Declaration` return `MacroTypeProductProjection` for the
  named product.

Every payload is wrapped in the closed result envelope
`DemandResult<T> = Success { value, dependencies, profile, input_basis } |
NotFound { reason } | Stale { reason } | Error { reason }`. `NotFoundReason` is
exactly `MissingImport`, `MissingExport`, `MissingDeclaration`, or
`UnavailableProjectInput`. `StaleReason` is exactly `RootRevisionMismatch`,
`InputBasisMismatch`, `DependencyFingerprintMismatch`,
`SemanticProfileMismatch`, or `ProjectionPlanMismatch`. `ErrorReason` is exactly
`UnsupportedTypeShape`, `BudgetExceeded`, `Recursion`, `Cancelled`, or
`InternalFailure`. Every arm repeats the demand identity; success additionally
carries the sorted unique dependency identities and the exact semantic profile/input
basis that produced it.

Demand identity is the deterministic tuple of every common field above plus the
`MacroPayload` discriminant. The batch order is source `syntax_index`, then role
(`Props`, `Emits`, `Model`, `Slots`, `Expose`, `Options`), then lane
(`RuntimeBindingNames`, `RuntimeConstructors`, `PublicApi`, `Tsc`, `Declaration`).
Exact duplicate identities may share computation, but C3 returns one result per
planned identity in that order. Missing, extra, duplicate, or reordered results, or
any token/profile/root mismatch, reject the entire facts batch before codegen.

BV1 converts an omitted result or any top-level `NotFound`, `Stale`, or `Error` arm
to a typed `ProjectProjectionUnavailable` non-success at the authored macro/type
anchor and publishes no artifact. A `Success` may carry only the explicitly typed
member-level degradation allowed by its payload contract (for example an unresolved
runtime constructor becomes `null` plus its typed diagnostic); it may never become an
empty successful surface, silently omit a member, fabricate a reference, or fabricate
a bound-free binder.

## Required exit

Exit proves every demand and result variant is exhaustively handled, source-local
compilation requests no project data, and the real canonical project/type substrate
obeys the identity, ordering, freshness, and typed-degradation rules above.
`FC-TS-001-PROJECT` passes for every jointly owned project-aware Vue PublicApi,
TSC/TSX, declaration, and imported-macro cell by running accepted BV1 codegen with C3;
that proof closes `FC-TS-001` for those Vue cells. Project-aware compilation preserves
BV1 outputs except for the declared projected information.
