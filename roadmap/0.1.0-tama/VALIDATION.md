# Validation

Tama validation checks only the static plan:

```text
node roadmap/0.1.0-tama/tools/validate-program-dag.mjs --strict
node --test roadmap/0.1.0-tama/tools/implementation-ledger.test.mjs
```

The first command cheaply checks DAG structure, charter/header parity, catalog references, ledger node membership, and schemas. The focused tests exercise the small readiness and ledger model.

A closure instrument adds two more commands, scoped to the instrument it owns:

```text
node roadmap/0.1.0-tama/tools/closure-register.mjs --check
node --test roadmap/0.1.0-tama/tools/closure-register.test.mjs
```

The first derives every claim, finding, and remainder status from the input register, fails when the generated human view is stale, and refuses to print its pass line unless the derived state is reviewable — a command that owns a derivation may not publish a verdict its own derivation does not support. Publication is the stricter half of that: a run that produced errors writes no view at all, so a partial reading of a register the same run refused can never become the artifact the staleness comparison is then made against. The second is the instrument's own negative-control suite: it mutates a hermetic fixture register once per mandatory failure class, requires the validator to refuse each mutation, and re-executes every evidence record whose runner it can invoke against that record's own transcription. Both run in the same `Tama Roadmap` CI job as the two commands above — an instrument that is never executed proves nothing about the register it claims to validate.

Evidence the instrument cannot re-run itself is not therefore unrefreshed: each such record names the CI job that does re-run its work, the command that job issues, and the filter gating it, and the validator resolves all three against this repository's workflow — plus a fourth thing the other three do not imply, that the lane's own universe reaches the record's packages. The declared command is the job's COMPLETE command line rather than a prefix of it, because a prefix satisfies a containment check while hiding the very flags that decide what the lane selects. Those flags are then read: narrowing the check can relate to the record — the packages a lane names or excludes, the single build target it selects — is compared against the record's own selection and refuses the binding when it does not run the record's work, and an archive-consuming lane resolves only against a job that actually RUNS the archive build, not one that mentions the path in a comment or an echo. An unresolved binding, an unresolved lane universe, a lane narrowed away from the record's packages, or an artifact the record cites that the filter does not cover becomes a derived limit that forces the covering claim to bounded.

A lane's own SELECTION is resolved by asking it, not by naming it. Where a lane narrows at run time — a filter expression spelled `-E "$SOME_VAR"` — the validator resolves the assignment in that job's own step, requires it to equal the producing command the register declares, runs it, and decomposes the expression it prints: a package the predicate excludes that the record selects is a derived limit, while name-scoped exclusions inside a package the lane still runs are published by package and explicitly not evaluated, because whether those names reach the record's cases is a property of the test binaries. Where a lane's runner instead iterates its own declared list, the register declares an enumeration of that list which must be a run of the same script, and the record's own selection is resolved against what it printed — "the runner's default universe" is otherwise a sentence about a list nothing read. Only the allowlisted `node` runner is executable, and both commands come from the register with the workflow required to agree, so nothing is searched for.

What such a binding still does *not* establish is derived and published too, and stated as a limit of the check rather than as a property of the lane. The generated view states, per record, whether the instrument re-derives its counters or only names the lane that re-runs the work. Every script a lane's selection is read out of or enumerated by is itself a cited artifact and has to be covered by both that lane's filter and this job's own. That citation follows the script's transitive first-party imports rather than stopping at the file the lane names: a lane selector is routinely a thin entry whose excluded package set and name-scoped selectors are declared one import away, so citing the entry alone would leave the module the published expression actually comes from outside both filters. The walk over-reads — an import counts as a contribution — which can only widen what a change has to re-run.

The `Tama Roadmap` job is also triggered by the artifacts the *validator* reads, not only by the plan tree. `--check` reads a negative control's subject bytes, re-derives a directory-counted record's selection from that directory, and resolves every cited fixture, evidence anchor, and package manifest, so those paths are in the job's trigger filter: otherwise an ordinary change to one of them could turn `--check` red on a pull request where this job never runs, and the break would surface later on an unrelated change.

One direction of that pairing is enforced: an artifact the validator opens that no trigger path covers is a hard error, so the list can never be too narrow. The other direction is not checked — a trigger path that nothing cites is accepted silently, so an over-broad or stale pattern costs eligibility rather than failing. The list is therefore kept at file granularity by review, and only where the instrument cites a crate ROOT — a fixture directory whose contents are counted, an evidence anchor for a record covering a crate's whole test surface — is a whole subtree listed, because a root is covered only by its own subtree pattern.

Two consequences of this coupling are deliberate rather than incidental, and both widen who meets this job. A change to a lane's own selection scripts — the core nextest filter and the modules it reads its excluded package set out of — can make a published narrowing stop matching a record's selection, which this instrument derives as a limit and refuses; the fix is to re-derive the affected record in the register, in the same change that moved the lane. And listing `crates/verter_session/**` makes this job eligible on a large share of Rust pull requests. Both are accepted: a stale narrowing that nobody is forced to re-derive is exactly the published-claim-outrunning-its-evidence defect this instrument exists to refuse, and the job costs minutes.

Pull requests that change Tama-managed paths run these commands in the `Tama Roadmap` CI job. This is deliberately a cheap shape and scope check for agents: it rejects unknown fields, malformed rows, broken DAG references, charter drift, and catalog drift without introducing Git-identity validation.

No command here resolves ledger commit hints or validates them against Git or GitHub. No commit SHA, tree, ancestry, receipt, lease, runtime journal, content digest, or external authorization participates in readiness.

Strict validation also checks `catalogs/contract-dependencies.toml` against its schema and proves a transitive DAG path from each declared producer to every consumer. Removing such a path fails even when the consumer's charter header still matches the edited DAG. This selected inventory is maintained through reviewed amendments; it does not infer semantic dependencies from code or certify runtime adoption.

`node roadmap/0.1.0-tama/tools/programctl.mjs products [PRODUCT]` emits a read-only JSON summary of implemented foundations, ready work, product/final acceptance gates and pending work without explicit release inclusion. `evidence_status = "not_inspected"` is intentional: the ledger report does not infer review, CI execution, runtime quality or product acceptance from node counts.
