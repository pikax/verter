# CVO1 — Pinned vue-benchmarks external workload probe lane

Readiness comes only from trusted implementation-ledger rows. A READY node may start; tooling does not validate commit locators, Git identity, receipts, leases, external state, or runtime admission.

## Independently acceptable outcome

A bounded real-workload CI lane that exercises Verter against one pinned `pikax/vue-benchmarks` revision through normal/public compiler request routes, classifies every case with the CVO0 taxonomy, and emits one compact machine-readable summary. The current owner is **no continuous external workload evidence**. The final and sole owner is **the table-driven workload probe lane and its probe-state manifest**. This charter accepts one boundary; it contains no independently dispatchable subblocks.

## Concrete surfaces and APIs

- Production surfaces: none; the runner and manifest are test/CI tooling.
- Named API/data boundaries: the workload runner (`crates/verter_validation_probe/src/runner.rs`, table/data driven, no one-test-per-fixture jobs) bound to the public NAPI batch route `compileRequests` on the exported host object (`crates/verter_napi/src/lib.rs`, owned by CCA1O2J; the single route `compileRequest` is not used, so exactly one carrier shape exists) and to no other entry point — each case issues exactly one canonical `HostCompileRequest` on the `vue` arm, `{ framework: "vue", identity: { filename: "<case relative path>", componentId: null, isProduction: false, forceJs: false }, products: [{ kind: "runtimeClient", inline: null, runtimeSourceMap: false }], options: { backend: "vdom", ssr: false, isCustomElement: [], babelParserPlugins: [] } }` — every optional option field intentionally omitted so the host's own defaults apply (matching the reference's `dev`, non-SSR, VDOM compile), the serialized request recorded verbatim as `request_vue` with its SHA-256 `request_digest` in the summary and in every observation artifact header; the corpus adapter `crates/verter_validation_probe/src/corpus/vue_benchmarks.rs`; `ProbeStateManifest` entries with stable case ids `vue/<relative-path-in-corpus>`; the summary artifact `target/validation-probe/summary.json` written by the crate's `summary` module, which the workflow publishes twice: uploaded through `actions/upload-artifact` as `validation-probe-summary-<workflow_run_id>-<run_attempt>`, and rendered by the crate's `summary --markdown` mode into `$GITHUB_STEP_SUMMARY` as the compact human summary (one table with attempted, passed, gated regressions, canary and known failures by class, skips, XPASS candidates, crashes, timeouts, harness failures, per framework and total).
- Comparator and the meaning of `pass`: the lane compares Verter's product against the output of the pinned upstream reference compiler (`@vue/compiler-sfc` at the version pinned in the root `package.json`) using the existing conformance comparator `verter_vue_conformance::compare::compare_modules` and its canonicalizer (`verter_vue_conformance::canon`); nothing new is written to decide equality. `pass` is defined per dimension and never borrows from a later one: at `Route`, the route returned a valid typed envelope for the entry (a response, or a typed failure the classifier recognizes) — a diagnostic or an unsupported product is still `Route = pass`; at `Compile`, exactly one `runtimeClient` product with exactly one `main` node whose `main.code` parses and builds; at `Structural`, the comparator reported no diff. `semantic_mismatch` carries the comparator's `DiffReason`. The reference output is comparator input, not expected-output authority: a mismatch is evidence for the owning semantic node (the `compiler.vue-compiler` train), never a verdict on Verter, and comparator equality never creates a gate by itself. Initial expected states are bounded by implemented authority: a `gate` entry may cite only `compiler.public-request-route` and only for `dimension = Route`, and only for the outcomes CCA1O2J actually owns — route callability and typed refusal transport — through the durable atoms `route-callable` (`Route`/`pass`: a supported request is answered) and `typed-refusal` (`Route`/`request_refused`: a shape, framework, or binding refusal is returned typed), which the roadmap catalog maps to CCA1O2J's "Acceptance and evidence/1" and "Acceptance and evidence/6". A runtime-surface or product refusal (`unsupported`) and a compiler diagnostic are `Compile` outcomes: they are never `Route` gates, and a manifest that tries is rejected; they are `Compile` canaries or known-fails citing the framework product authority, and may become `Compile` gates only after that authority is implemented and CVO4 promotes them; CCA1O2J owns route callability and transport equivalence, not framework product validity, so `Compile` cells (the product parses and builds) and every `Structural` cell are `canary` (expected class recorded) or `known-fail` citing `vue.runtime-client-product`, and only CVO4 may promote them once that authority is implemented. JavaScript driver boundary: the routes are addon methods bound for JavaScript, so the Rust runner never links the addon; it spawns `node crates/verter_validation_probe/driver/probe-driver.mjs`, which loads the addon through `@verter/native` (`packages/native/index.js`, built by `pnpm --filter @verter/native build`, resolved artifact `packages/native/dist/verter-native.<platform>.node`), reads one request JSON object per line on stdin — `{ probe_id, entries: [{ canonicalId, source, request: HostCompileRequest }], observe?: { memory: boolean } }`, one entry per probe, the optional `observe` being the additive observation command CVO2 uses (absent in the lane's own runs), where `canonicalId` is the case id string, `source` is the component text (UTF-8, JSON-escaped; the driver never re-reads the corpus), and `request` is the typed `HostCompileRequest` — builds each `HostCompileRequestsInput` as `{ canonicalId, source: Buffer.from(source, "utf8"), request }` (the route requires a `Buffer` carrier), calls `compileRequests(entries)` once, and writes two authenticated frames per request on stdout, in order: the compile frame `{ probe_id, frame: "compile", elapsed_ns, entries: HostCompileRequestsEntry[], memory?: { peak_bytes, live_bytes } }` immediately after `compileRequests` returns and before any reference work, then the reference frame `{ probe_id, frame: "reference", reference: [...] }`; the runner ingests the compile frame as soon as it arrives, so a reference-phase death can only ever cost the `Structural` cell (`reference_failure`) and never the already-observed `Route`/`Compile` terminals; `elapsed_ns` brackets exactly the `compileRequests(entries)` call with `process.hrtime.bigint()` immediately before and after it and `memory` is present only under `observe.memory`, taken in the same process as `memoryAuditEnable()` once at driver start, `memoryAuditResetHighWater()` immediately before the call, and `memoryAuditSnapshot()` immediately after it (`crates/verter_napi`, owned by CPER0M; `memoryAuditSites` is not used), each entry being the addon's `{ canonicalId, response, failure }` object serialized whole (`response.diagnostics` and `response.products` intact; `failure` with its `kind`, `diagnostics`, and kind-specific fields intact, never reduced to its message). Reference production goes through a per-framework producer registry in the driver: this node registers the `vue` producer, which produces the reference product for the same source with the pinned `@vue/compiler-sfc`, exactly as `scripts/compare-per-file.mjs` does in its direct layer (`parse` → `compileScript` → `compileTemplate`, mode `dev`), emitting `reference[i] = { code } | { error }`; for an entry whose framework has no registered producer the driver emits `reference[i] = { inapplicable: <framework> }` and never runs another framework's reference over it (CVO1S plugs Svelte in and registers no producer); a driver-level exception is written as `{ probe_id, elapsed_ns, error }`. Classification reads structure, never message text, and every entry yields a set of observed classes that goes through `ProbeOutcomeClass::terminal`, never a single hand-picked class: (i) whether the entry is a `response` or a `failure`, an error-severity entry in its `diagnostics` contributes `verter_diagnostic` at `Compile` (the route answered, so `Route` is `pass`); (ii) `failure.kind` contributes: `binding` or `frameworkMismatch` → `request_refused` (the route's typed refusal of binding or framework — a public-boundary outcome, never hidden as a harness defect); `refused` contributes nothing of its own because the live route constructs it for fatal product diagnostics and whenever compile diagnostics carry errors, so a `refused` with an error diagnostic folds to `verter_diagnostic` through rule (i), and a `refused` with no diagnostic is unexplained and fails closed as `harness_failure`; `host` → `host_failure` at `Route`, any diagnostic it carries retained as secondary evidence by the fold (a host failure with a diagnostic can never pass a diagnostic gate); `request_refused` is likewise a `Route` class, while `unsupported`, `verter_diagnostic`, `product_not_produced`, and `product_malformed` originate at `Compile`; `harness_failure` is contributed only by the harness itself — `SpawnFailed`, a driver-level `{ error }` line, an unparseable line, or an observation failure; `runtimeSurfaceRefused` or `unsupportedProduct` → `unsupported`; `productNotProduced` → `product_not_produced`; (iii) a `response` with an empty `products` contributes `product_not_produced`; the fold then applies the CVO0 precedence, so an error diagnostic outranks product absence whichever arm carried it. Product extraction is exact: the request asks for exactly one product (`products = [runtimeClient]`), so `response.products` must contain exactly one `HostRuntimeCompiledProduct` of kind `runtimeClient` (zero → `product_not_produced`; more than one, or another kind → `product_malformed`), and that product's `nodes` must contain exactly one node with `node.kind == "main"` (zero → `product_not_produced`; two or more → `product_malformed`); `main.code` is the emitted module every later step reads. A `main.code` that parses and builds → `Compile = pass`. The `Structural` cell is decided only when `reference.code` is present, by the exact call `verter_vue_conformance::compare::compare_modules(&ModuleInput { code: main.code, diagnostics: rows(response.diagnostics) }, &ModuleInput { code: reference.code, diagnostics: [] }, &verter_vue_conformance::authored_identifiers(source), MAX_REASONS)` with `MAX_REASONS = 32` fixed in the crate and `rows(...)` the existing severity-ordered `DiagnosticRow` projection; the authored-identifier set is always the real source's, so a source-authored name is exact and alpha-equivalence cannot false-green. Both comparator inputs are prevalidated with the same parse-and-build check the `Compile` cell uses before `compare_modules` is called: a Verter-side failure is already `product_malformed`, a reference-side failure is `reference_failure`, and an `Err(CompareError)` returned after both inputs prevalidated is an internal comparator failure classified `harness_failure` without parsing the error string. With `reference.error` the cell is `reference_failure`, with `reference.inapplicable` the cell is `Terminal::NotApplicable { reason: reference_inapplicable }`, and in both cases no comparison result of any kind is emitted, so comparison evidence never exists without a reference. Before any classification or serialization the runner validates batch identity on every response line: `entries.length` and `reference.length` both equal the requested count, `entries[i].canonicalId` equals the requested `canonicalId` at position `i`, and no `canonicalId` repeats; any violation classifies the whole line `harness_failure` and nothing is paired positionally, so a dropped, duplicated, or reordered entry can never attach one case's product or reference to another case (one planted reordered-batch fixture proves it). The driver wraps every JavaScript step in try/catch and reports failures as lines, never as exits: a JavaScript failure after the `compile` marker but before native entry (building the `Buffer` carriers, the call site itself throwing synchronously before the addon runs) is written as `{ probe_id, error, phase: "compile", stage: "pre-native" }` and classified `harness_failure`, and a failure after the native call returns as `{ ..., stage: "post-native" }`, likewise `harness_failure`; therefore an unacknowledged termination in phase `compile` (signal, abort, timeout with no line) can only originate inside the native call and is rightly `crash`/`timeout`, and the same holds in phase `reference`, where a caught exception is `reference[i] = { error }` and a hard termination is `reference_failure`. One planted control feeds a pre-native driver exception line and asserts `harness_failure`. The driver protocol is phase-authenticated so termination is attributable: before loading the addon the driver writes `{ probe_id, phase: "load" }`, before the bracketed `compileRequests` call `{ probe_id, phase: "compile" }`, before reference production `{ probe_id, phase: "reference" }`, and the runner supervises each phase with its own deadline. The runner classifies raw execution through one in-process function, `runner::classify_execution(event: ExecutionEvent) -> ProbeOutcomeClass` with `ExecutionEvent { SpawnFailed, TimedOut { phase }, Signaled { phase, signal }, Exited { phase, code, response_line } }` where `phase` is the last phase marker read (`None` before any marker): `SpawnFailed` → `harness_failure`; a `TimedOut`/`Signaled`/non-zero `Exited` before any marker or in phase `load` → `harness_failure` (addon load or driver start failed); in phase `compile` → `timeout`/`crash`; in phase `reference` → `reference_failure` (the compiler already answered; the reference hung or died); so a reference hang, an addon-load failure, and a compiler crash are three different classes (`SpawnFailed` → `harness_failure`, `TimedOut` in `compile` → `timeout`, `Signaled` in `compile` → `crash`, `Exited { code: 0, response_line }` → the parsed line's class through `runner::ingest_response_line`; a non-zero `Exited` discards the line unread and maps by phase — `load` or no marker → `harness_failure`, `compile` → `crash`, `reference` → `reference_failure` — the one phase-specific mapping, applied to timeouts, signals, and non-zero exits alike), and every process outcome enters the per-dimension fold through it. Workflow steps, in order: `pnpm install --frozen-lockfile`, `pnpm --filter @verter/native build`, checkout of the pinned Vue corpus at its exact SHA into `.integration-tests/repos/vue-benchmarks`, then `cargo nextest run -p verter_validation_probe --features external-corpus`. The runner, manifest, summary, and workflow are framework-neutral, but this node provisions and executes Vue only; the node that plugs in another corpus (CVO1S for Svelte) adds that corpus's checkout and any materialization step to the same workflow. CVO2 reuses this driver unchanged. `runtime_mismatch` and `source_map_mismatch` are declared inapplicable by this lane (never emitted; the manifest records `comparison = structural`) until a later owning node binds an existing runtime executor or map validator.
- Hermeticity (repository policy “Testing-Hermeticity”): the corpus checkout lives at `.integration-tests/repos/vue-benchmarks` and is read only from tests behind `#[cfg(feature = "external-corpus")]`; the default canonical run (`node scripts/gate.mjs`) neither reads nor requires it, and the guard `external_corpus_paths_not_present_outside_gated_tests` must stay green. Only the dedicated workflow `.github/workflows/validation-probe.yml` provisions the pinned checkout and enables the feature.
- Test/CI homes: `crates/verter_validation_probe` (modules `corpus`, `runner`, `manifest`, `summary`; integration cases under `tests/cases/`, wired through the single `tests/main.rs`) and `.github/workflows/validation-probe.yml`, which invokes `cargo nextest run -p verter_validation_probe --features external-corpus` directly. The workflow lives under a `release_orchestration` root (`.github/workflows`), which this node therefore also leases; no file under `scripts` (a `performance_evidence` root) is touched. No fallback home: if any of these paths cannot be used, stop before mutation and obtain an authority amendment; never place the runner in another train's test home such as `crates/verter_compiler/tests`.
- Mutation boundary: test/CI bytes only; production LOC is zero.

## Source-specific scope

- **Intent:** prove the probe infrastructure and establish a useful signal-to-cost ratio against representative real Vue inputs.
- **Problem:** without continuous external workload execution, real-workload regressions surface late, failures stay unclassified, and deferred gaps cannot be distinguished from new regressions.
- **Solution and architecture decisions:**
  - one pinned `pikax/vue-benchmarks` revision, the full 40-hex commit SHA recorded in `manifest/vue.toml` as `external_revision` (initial pin: `5ac27ef2df618855c5855adcd9487488e0b18f25`, whose fixture set is `tests/confirm/fixtures/*.vue`, 324 files) and checked out exactly by the workflow; a representative slice defined by strata, not by count alone: the manifest carries `strata = [{ id, pattern, min_cases }]` over the fixture basenames — `app` (`App*`), `child` (`Child*`), `component` (`Component*`), `format` (`format*`), and `feature` (every remaining fixture, each named for one template or directive feature such as `VModel*`, `VFor*`, `TeleportHost`, `TemplateRef`) — and the smoke slice must contain at least 2 cases from each of the first four strata and at least 8 from `feature`, chosen deterministically (lexicographic first-N within each stratum); the main lane is the complete ratified inventory of the pinned fixture set, listed case by case in the manifest. `ProbeStateManifest::validate` proves every listed case exists at the pinned SHA, every stratum meets its `min_cases`, and the main-lane inventory equals the pinned fixture set (a missing required case or an unmet stratum is rejected); stable case ids; aggregate reporting;
  - the corpus is an external workload probe, not an oracle, semantic authority, expected-output authority, golden source, normalizer authority, or reason to change compiler behavior, and not a replacement for official conformance coverage;
  - requests go through normal/public compiler routes; no test-only semantic shortcuts;
  - the runner, manifest, and summary are framework-neutral: `framework` is a case attribute, never a runner variant, so CVO1S plugs the pinned `pikax/svelte-benchmarks` corpus into this same lane without a second runner or summary format;
  - pull requests run a small deterministic smoke slice bounded structurally, not by wall clock: at most 24 Vue cases, one CI job, one `compileRequests` call per case (no warm repeats in the smoke lane), listed by case id in the manifest; elapsed time is reported as an observation only. The broader main lane runs the complete ratified inventory of every pinned corpus (Vue: the 324 pinned fixtures; Svelte: the generated fixture set at its pinned SHA) as one job, its size fixed by the manifests rather than by a cap; the summary validator refuses an inventory that differs from the manifests in either direction; it may contain canary/known-fail cases and runs separately from the required fast gate;
  - the summary artifact reports cases attempted/passed, gated regressions, canary/known failures by outcome class, skips, XPASS/promotion candidates, crashes, timeouts, and harness failures;
  - scope rule for failures: classify first; a cause owned by a future DAG node is recorded with its owner and kept canary/known-fail or skip; a defect in the probe infrastructure itself is repaired here; a regression of an already-gated behavior follows normal regression handling. A test failure alone does not override DAG ownership.

Preflight evidence selection: preserve all four acceptance outcomes below, then select the smallest evidence set that actually discriminates the touched contract. Existing behavioral coverage, compiler/type/capability enforcement, static validation, canonical gates, bounded inspection, and benchmarks are valid when accompanied by a terse rationale.

- **CVO1-AC1 — sole-owner outcome:** no per-fixture test definitions or per-case CI jobs; the lane is table/data driven and every probe/cell is a manifest entry. Prefer static/structural enforcement over new test scaffolding.
- **CVO1-AC2 — positive contract:** a pinned-revision run produces a deterministic summary (same slice, same classification, stable case ids) containing all required counters; the smoke slice inventory in `manifest/vue.toml` is non-empty and has at most 24 cases, every selected case id exists at the pinned corpus revision, the summary reports `attempted == selected > 0` for `vue`, and the workflow has exactly one probe job; a planted zero-selection manifest must fail the lane through the workflow's own entry point (`cargo nextest run -p verter_validation_probe --features external-corpus`) rather than produce a green summary; the default canonical gate passes with the corpus checkout absent; the committed manifest contains zero classless canaries and `validate-probe-authorities.mjs --manifest crates/verter_validation_probe/manifest` passes on it; the uploaded JSON artifact and the job summary both carry every required counter (a planted summary missing one counter fails the lane); and the lane disposition is a real exit, not a number: after publication the workflow's final step runs the crate's `summary --dispose`, which exits non-zero when `gated_regressions > 0` or any `gate` cell is `NotRun`, so the required job fails — proven end to end by a planted `GateRegression` driven through the workflow entry point that must turn the smoke job red after the summary and artifact are published; and one real-addon positive in the probe workflow (not the hermetic gate) proves a constructed, supported single-file component reaches a `runtimeClient` product through the driver rather than a `binding` or `host` failure, so the lane cannot be satisfied by a driver that never reaches the compiler.

- **CVO1-AC4 — bounded work:** not applicable as a hot path; the runner must not add production counters or instrumentation.

- Do not implement successors or silently enlarge this charter. Discovery of a second independently acceptable outcome requires an amendment and a new DAG node before mutation.

## Abort conditions

- Stop before mutation if the pinned corpus cannot be checked out deterministically, an ancestor lacks an implemented ledger row, or the complete diff will not fit one review context.
- Abort the candidate if a workload failure tempts a compiler change; record the owner and keep the case canary/known-fail or skip instead.

## Targeted verification

1. Run the lane against the pinned slice locally and confirm the summary artifact is produced and deterministic.
2. Run every final command in the bound `targeted-domain` profile on the squashed review candidate; targeted success alone is iteration evidence, not acceptance.
3. Bind the preflight evidence selection and terse rationale in the review report. Behavioral tooling changes require TDD with a failing discriminating regression before the change; do not invent a test solely to populate evidence.

## Review and lower-severity findings

Apply `semantic-3`: 2 fresh distinct harness tasks covering exactly `adversarial`, `conformance`. P0/P1 block final acceptance. A P2 follows the owning review policy and must have a named owner when deferred; otherwise it blocks. P3 follows the currently binding owning policy and must be recorded when that policy requires it. Any post-review content change invalidates every verdict. Final acceptance requires the complete current-round profile to contain independent clean PASS reports on the squashed review candidate, plus `targeted` confirmation when required. A failed review/fix cycle is complete only after all assigned lenses and a FIX_REQUIRED disposition.

## Trusted implementation ledger

Before squashing or review, the implementation patch transitions this node's predeclared row in `authority/state/implemented.toml` from `status = "pending"` to `status = "implemented"` with the planned squash commit message, approximate date with timezone, and optional pull-request number. The transitioned row is the implementation fact. Commit metadata is a loose locator only and is never resolved or validated against Git or GitHub. Reviewers inspect the squashed candidate patch without SHA-, tree-, ancestry-, receipt-, lease-, or digest-bound orchestration manifests.

## Reconciled source-plan contract

**Intent:** exercise representative real Vue inputs continuously, classify every outcome, and keep future-owned gaps visible without blocking required CI.

**Problem:** real-workload regressions are found late when no bounded external lane exists, and generic pass/fail cannot say whether the compiler, harness, product, comparator, or runtime failed.

**Solution and architecture decisions:**

- pinned `pikax/vue-benchmarks` revision, deterministic representative slice, stable case ids;
- table/data-driven runner over the public compiler request routes;
- PR smoke slice plus a broader non-fast-gate main lane;
- compact machine-readable summary with all required counters;
- failure scope rule: classify → associate owner → canary/known-fail/skip → continue.

**Suggested predecessors:** `CVO0`, `CCA1O2J`; no unfinished compiler work.

**Normative source decomposition:**

1. **CVO1-A — Corpus checkout and slice definition.** Pinned revision, deterministic slice, stable case ids.
2. **CVO1-B — Runner.** Table-driven execution through public routes, timeout handling, outcome classification via the CVO0 taxonomy.
3. **CVO1-C — Manifest materialization.** Expected states per case with owners, reasons, pinned revision.
4. **CVO1-D — Summary artifact and CI wiring.** Required counters, PR smoke lane, broader main lane.
5. **CVO1-E — Failure triage pass.** Classify current failures, associate owners, no compiler repairs.

**Acceptance:** the lane runs the pinned slice deterministically; the summary reports every required counter; known future failures execute without blocking required CI; gated regressions and XPASS candidates are surfaced; the probe infrastructure defects found are repaired here.

**Forbidden:** per-fixture CI jobs, oracle or expected-output claims over corpus output, compiler repairs from this train, scope expansion to corpora other than the ones this train's own nodes pin (CVO1S adds `pikax/svelte-benchmarks`), Vue-shaped assumptions baked into the runner or summary.

**Deletion/abort:** delete any ad-hoc per-case test scaffolding in favor of the table-driven runner; abort on inability to pin or classify, recording the blocking evidence.
