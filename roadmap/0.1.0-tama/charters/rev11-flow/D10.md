# D10 — Guard-narrowing residue: in-key intersection, lib Function global, nominal instanceof derivation

Readiness comes only from trusted implementation-ledger rows. A READY node may start; tooling does not validate commit locators, Git identity, receipts, leases, external state, or runtime admission.

## Independently acceptable outcome

The guard-narrowing arms of the sole shared flow authority (`narrow_in_key`, `narrow_typeof`, `narrow_instanceof` in `crates/verter_session/src/project_semantic_dispatch/flow_return.rs`) close their four typed-gap rows: the positive `"k" in x` edge for a key no arm declares publishes the checker's `(subject) & Record<"k", unknown>` intersection; `typeof x === "function"` over `object` resolves the lib `Function` global and publishes it; and the `instanceof` arm decides derivation by class heritage — the declaration identity chain the class surface already carries — instead of structural assignability, so `x: K | KSub` under `x instanceof K` publishes `K | KSub` CLEAN and warm with no `FlowGap(GuardNarrowing)` (`N138`) and a subclass test over a base subject narrows to the subclass (`N94`). A structural twin with no heritage relation takes the checker's subtype fallback; an arm whose heritage cannot be decided (opaque carrier, unresolved import) stays gapped and never warm. No gap in this set is ratified permanent. One independently acceptable outcome; no subblocks.
