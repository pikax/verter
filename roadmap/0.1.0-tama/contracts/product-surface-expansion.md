# Product-surface expansion contract

The project-model, source-module, bundler-host, and project-profile trains turn existing product behavior into explicit authorities. They are successor work: they consume the accepted Rev11 and compiler contracts and may not reopen their semantic ownership.

## Shared laws

- Rust and WASM never execute arbitrary ecosystem configuration. JavaScript in `packages/*` may run framework and bundler hooks, load the host tool's configuration, and capture typed facts. The canonical core consumes only versioned facts with provenance and read sets.
- `VID0`/`CAT0` own opaque identity type law and immutable registration. Configured-project, project-environment/snapshot, source-module-environment, bundler-session, and project-profile identities are distinct; PM/SM/BND/PPR derive values and publish facts over them but do not mint a second type family. If an exact required identity is absent from the kernel catalog, the implementing node must stop for a VID0/CAT0 amendment. A filename, process handle, generated directory, or bundler object is not an identity.
- Dependency direction is project model → source-module facts → bundler host → project-profile integrations. A lower train may expose a typed extension/input slot for a later train, but may not key correctness on, interpret, or require an identity whose authority has not converged yet.
- Resolution is layered without divided authority: PM owns canonical probing, package/TypeScript/project-reference algorithms, and the final proof; SM owns source-module syntax and captured host alias/query/asset facts; PPR owns framework-defined alias/generated-module contributions. SM/PPR contributions are versioned resolver inputs, never independent resolvers or permission for PM to interpret framework semantics.
- Vue and Svelte are equal compiler/tooling inputs. Nuxt and SvelteKit are paired first-class project profiles; neither may be promoted through fixtures that omit the other framework's counterexamples.
- An index supplies bounded candidates, never semantic truth. Project resolution, source-module facts, framework facts, compiler artifacts, and language-service operations remain with their named owners.
- Every cached or published result binds the complete source/project/profile/config/tool-version basis. Cancelled, stale, partial, `NeedInputs`, ambiguous, and unsupported outcomes never warm-admit as complete.
- Migration uses characterize → introduce typed boundary → shadow only for measurement → atomic route switch → delete displaced authority. Indefinite dual reads and compatibility fallbacks are forbidden.
- Hot paths publish equivalent-work counters. Required modes include cold, warm, incremental edit, edit-revert, config/package change, project open/close, client/SSR switch, cancellation, and disabled/inapplicable zero work.
- A product terminal may record a cell as inapplicable only when the external host or framework contract cannot expose that capability and the negative proof is versioned. An applicable required cell that is unsupported blocks promotion; it cannot be converted into a passing capability row.

## Shared proof and rescope rules

Every implementation charter must prove a positive contract, a planted stale/identity/duplicate-owner failure, incremental=fresh where applicable, and bounded work. A terminal may certify and delete but may not add semantics. Discovery of another independently acceptable outcome, another public/wire boundary, or a fourth unrelated package requires a DAG amendment before implementation.

The numbered items under each charter's binding-architecture section are binding internal subblocks, not suggestions. A dispatch packet must map every item to exact production paths/symbols, expected changes, at least one discriminating acceptance ID or an explicit evidence-only rationale, and its deletion/abort owner. If an item develops an independently useful result, separate deletion population, public/wire migration, or concurrency/lifetime concern that cannot be reviewed with the rest, the node must split before mutation under `contracts/successor-charter-quality.md`.
