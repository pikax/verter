## Global Names (one resolution path)

A bare name no scope declares or imports is a GLOBAL name, and every reader resolves it through ONE path in `project_semantic_dispatch::build`:

Ambient global reads carry an `AmbientSymbolSpace` through the resolver port. `program_ambient_symbol` filters the loaded libraries in program order by that namespace, observing each inspected header through the normal indexed serve. An interface in an earlier library cannot hide a later value of the same name, or the reverse; an unreadable earlier candidate remains a failed read rather than selecting a later declaration. The registry remains a name inventory, and no declaration body is lowered to select the library. Every loaded library contributor to a global type is recognized as that global, including a declaration outside the first library; named-annotation nominal certification can therefore reach the contributor that declares the member.

- **Types** — `first_global_declaration(demand_canonical, name)`: the merged global declaration's FIRST declaration in declaration precedence order. The project's library comes first (a checker's `lib` files precede every program file), then the program's `declare global` contributions (from modules) and script file-scope interfaces, by the program's file order and then canonical path. Program file order is TypeScript's: the `files` roots as listed, then `include` matches grouped by authored entry in directory-walk order (a `.d.ts` match never shadows its same-stem `.js`), each file placed after the files its `/// <reference path|types>` directives and imports pull in (first visit wins). A module augmentation's name is resolved to the module it merges into but pulls nothing into the program. The libraries the program loads — its `lib` selection or target default (unless `noLib`), every `/// <reference lib>` a program file carries, and what those libraries reference — are listed before every program file by TypeScript's library priority (its `libEntries` table order, then visit order). A registered ambient library only makes a library's bytes available: whether and where the program loads it is the order's decision, never registration order; a host that registers none of the libraries its configuration names supplies its own environment, and every library it registers is a root. `VerterHost::library_order` decides a project's libraries from configuration and library references alone (no walk of program files; kept per configuration and registry), and `VerterHost::program_file_order` shares the composition settled at configured-program ingestion, before population snapshots (including empty and singleton populations) and after batched workspace publication. Discovery consumes shallow reference/contribution inventories, lowers no declaration bodies, and retains unchanged files' edges as roots grow. The immutable `ProgramMembershipRoot` is captured beside source/project roots: imports and references retain their configured program's compiler options and aliases even outside `files`/`include`. Persistent and transient resolution share this context selection and retain the real importer's directory. Contributor ordering consumes the same composition from `FileArtifactStore`'s `ProgramOrderIndex`. A result ordered by it, or filtered by an imported contributor's reachability (even a singleton), observes the route-surface fact `FactKey::ProgramFileOrder { program }`; the validator accepts it while no file the order read, no path it probed, the configuration, the candidate file set, the registered libraries and the resolution world moved (an edit elsewhere re-stamps it), and a rebuild re-reads only the files that changed. So an import or library-reference edit in a non-contributor that reorders the program misses every warm result ordered by it, and an edit that does not keeps them. The declaration's `Instantiate` folds in every later declaration (`stitch_global_declarations`), so a program's `declare global { interface String { … } }` merges behind the library's `String`.
- **Values** — `global_value_declarations(demand_canonical, name)`: every declaration of the global value in the same order — library first — each with its kind. A `var` declared in several files is one variable typed by its first declaration; a function's overloads are every file's; an enum declared in several files is one enum listed by its first declaration, which carries every block's members (`enum_type::enum_blocks`); any other kind spanning files fails closed (TS2451). A listed declaration that is a module's `declare global` one while the module also declares a module-scope value of the name fails closed too, since `(module, name)` addresses the module's own value; a later such declaration a `var` or an enum does not list is still read. `global_value_declaration` is its first entry. `typeof` over a free name, a `globalThis` member path (only a `var` or a function is a property of the global object), a namespace member path and the widening read all ask this.
- **The library** — `lib_global_declaration(demand_canonical, name, GlobalSpace)`: the first library in program order that the project's program loads and that declares the name (`resolver_core::ambient_resolve::resolve_ambient_global` → the session's `VerterHost::program_ambient_symbol` over the workspace's per-project symbol index; the consumer → library reverse-dependency edge is recorded) narrowed to the requested space through the library's header index. It never reads a library declaration body, and it is the ONE library lookup: the global type and value lookups above and the builtin availability check (`lib_global_is_available`) ask it, and a primitive's apparent wrapper (`global_wrapper_surface`) and the callable apparent `Function` surface ask `first_global_declaration`, so a program's own declaration of the wrapper counts and a miss depends on the program's global contributors (`global_contributors_in` observes the per-name population fingerprint; a production host registers its libraries only when it is constructed). A new reader of a library global asks it too — never `lookup_ambient_symbol` directly, never a walk over library or ambient files. Pinned by `lib_global_tests::a_library_global_read_materializes_only_the_declarations_it_names`.

Apparent wrapper surfaces instantiate with Published Shallow demand. Selected member and signature reads demand their interiors; comparing an array or tuple does not eagerly evaluate every unrelated library member's conditional types.

What the lookups see is decided by the declaration inventory:

Project filtering and declaration-precedence ordering are shared views of the
published `GlobalContributorPopulation`, keyed by membership revision as well
as contributor snapshot and overlay population. Repeated base demands borrow
their `Arc` slices. The first global declaration lookup therefore reads the
first eligible entry instead of scanning every contributor again. Every base
of a global interface routes its merged body through that first interface's
instantiation, preserving one assembly and the full contributor fact rail.
Configured project filtering follows its program composition, so an imported
contributor belongs to every program that reaches it, and a detached contributor
is excluded even if its indexed declaration remains resident. Unconfigured
projects retain contributors with no workspace owner, including dependency
declarations and eligible automatic libraries, while excluding contributors
owned by a different project.

- A script's `var` declared in a nested block (an `if` / `else` branch, a bare block, any loop and its head, `try` / `catch` / `finally`, a `switch` case, a labeled statement — never a function or class body) hoists to the top level, so it is a file-scope value of the script and a global (`type_eval_build::for_each_hoisted_var`, mirrored by the header index). A `for…in` variable is a `string`, a `for…of` variable an element of a literal array or string (any other iterated value leaves it untyped); a declarator with neither an initializer nor an annotation declares the implicit `any`. The global-contributor pre-filter (`source_may_have_file_scope_global_contribution`) admits a script whose only global is such a nested `var`.
- A declaration file is ambient: its namespace bodies (and a `declare namespace`, and a namespace in a `declare global` / `declare module` block) are EXPORT CONTEXTS unless they hold an export declaration (`export {}`, `export { … }`, `export =`, `export *`, `export default <expression>` — `route_inventory::statements_have_export_declarations`), and a declaration-file module without an export declaration exports every top-level declaration. A namespace member is its own declaration under its qualified name (`NS.Inner.f`, `NS.T`).
- A type, class or nested namespace declared without `export` in a namespace body that is not an export context is recorded in `DeclHeaderIndex::namespace_private_members`: its qualified name serves the namespace body's own references, but a reference from outside the body — a named import of the namespace (`import { NS } from './m'; NS.T`), a namespace import's export (`import * as M from './m'; M.NS.T`), an `export =` module's member — cannot name it (`namespace_member_is_exported`, the checker's TS2694). The type side resolves these qualified members in `bare_name_resolve::resolve_namespace_member_from_facts`, the value side in `ProjectSemanticDispatch::qualified_value_member_root`.
- A primitive (`string`, `1`, `T[]`) is a node every project shares, so its wrapper read depends on the demanding project. `apparent_type::global_wrapper_surface` reads the wrapper through `first_global_declaration`, and the dispatch prelude rewrites a `SignaturesOfType` key with such a subject to the same read over the demanding project's wrapper (`scope_apparent_signature_subject`; `never` when the project declares none) BEFORE memo admission, so the key names the project and the lookup facts root the entry. A wrapper read reached inside another subject (a union arm) folds `cache_suppress` instead (`lib_global_tests::a_primitive_wrapper_read_is_the_demanding_projects`).
- An ambient module (`declare module "amb" { … }`, no file resolving the specifier) declares values as it declares types: `ProjectSemanticDispatch::ambient_module_blocks` lists its blocks in declaration order (observing the augmenter-set shape fact), `ambient_import_member_root` resolves a named, default, namespace or import-assignment import to the block's member, and `ShallowFileState::value_fallback_augmentation_scope` / `type_fallback_augmentation_scope` let the declaring file's identity `(canonical, owner, name)` address the one module block that declares a name.
- A module read as a value is its module object (`project_semantic_dispatch::module_object`): `file_module_object` (value exports plus `export *` names except `default`), `namespace_object` (a namespace's exported values and value-declaring namespaces, `DeclHeaderIndex::namespace_value_members`), the ambient module's blocks, and a module assigned with `export =` its value — which a namespace import wraps with `default` when `SignaturesOfType` finds a call or construct signature. `build_typeof` reads it for a namespace import and a namespace name, and for an unbound name with no global value it reads `global_namespace_object` (every script's top-level namespace of the name, from the global contributor population); `typeof import("…")` reads `file_module_object` without the interop. A namespace is a value when some block of it is INSTANTIATED (`NamespaceBlockRecord::instantiated`: it declares a value, exported or not), so one exporting no value is an object without members and one holding only types is none.
- A module's function merges the declarations of every `declare module` block augmenting that module (`module_file_augmentation_blocks`, over the `ResolvedRelativeCanonical` augmentation index) after its own, as a global function merges every script's; `build_typeof` appends their signature groups in declaration order.
- A read of a value declared outside the flow frame (a module `const`, an import, a namespace member, a global) widens exactly where a bare literal would when its declaration's `ValueTypeAnnotationFact::literal_freshness` says its declared type is the fresh literal type (`const c = 1`; `const d = c` follows `c`; a class's `static readonly s = 1` through `WideningStaticMembers`); `value_read_widens` resolves the read the way its `typeof` resolves, and a copy cycle reads no literal. With `strictNullChecks` off, a declaration whose initializer is `null` / `undefined` / `void` and has no annotation (`DeclaredLiteralFreshness::WideningNullish`) is `any` in `build_typeof`.
- An enum is assembled from its BLOCKS by `enum_type::enum_blocks`, each block read in the declaration scope that declares it, through the shared augmentation collector (`collect_augmentation_contributions` with `AugmentationContribution::EnumBlocks`, which orders a script's `FileScopeValue` blocks beside the augmenters by `FileScopeContribution::EnumBlock`). A GLOBAL enum — a script's top-level enum, an enum a script's namespace exports (`namespace N { export enum E {} }` is the global `N.E`: the population lists exactly the exported qualified names), or a module's `declare global` enum, nested in a namespace or not — is every such block of its qualified name in declaration precedence order, whichever block the reference reached; a module's enum is its own declaration followed by every `declare module "./m"` block of it; any other enum is its own declaration's blocks. Augmentation blocks are prepared in their scope (`prepare_augmentation_value`, which retains `enum_members`), so a module's own `E` and its `declare global { enum E {} }` stay two enums. Blocks of another project are not the enum's. The enum's identity is the first block whose `(canonical, owner, name)` addresses it; members' declared positions come from the scope's enum header (`DeclHeaderIndex::enum_header_in`), and a member's block is a direct index, so assembly and provenance lookups grow linearly with the blocks (`enum_literal_tests::assembling_a_merged_enum_grows_linearly_with_its_blocks`). The collector observes the per-name contributor population (exported membership and header kind included), the augmentation-index shape and each contributing file's `FileWholeHash` + `FileSourceEnv`, the empty answers included, so a block added, removed, edited, or entering the enum (a namespace starting to export it, an augmentation appearing) misses the warm read; a contributor it cannot serve makes the read uncacheable (`UnobservableSource`). An enum's `Instantiate` takes no type-body augmentation stitch: its member union already holds every block. A namespace merged with the enum adds no member; its exported values are properties of the enum object (`EnumDeclaration::namespace_members`), read from the enum's own file or, for a global enum, every script's namespace of its name, each file observed.
- An enum member has its own nominal literal type, `SemanticNodeData::EnumLiteral` (the enum's type declaration, the member name, the base value, the member count); `project_semantic_dispatch::enum_type` is its one producer, reading the merged member inventory the enum's blocks carry (`enum_declaration`): the enum type is the canonical union of its members (a one-member enum's type IS the member), `typeof E` the object of the members, `E.A` in type position `resolve_enum_member_type` (a namespace's enum through `value_path_declaration`). A member's value is `verter_semantic::analysis::enum_constant`'s constant evaluation: a declaration evaluates what it declares itself, and a member naming another declaration (another enum, a merged declaration, a `const`) stores its program on `EnumMemberEntry::initializer` for the session to evaluate. Every member read is fresh (`value_read_widens`) and widens to its enum (`widened_literal`); relations are nominal between members and through the base otherwise; `printed_union_arms` is the one rule printing a union holding every member of an enum as the enum (display, raise and the checker-probe matcher read it).
- A function declared in a namespace is indexed under its qualified name (`function_program::discover_namespace_block`), and its body reads the namespace's members unqualified: `flow_slice_content`'s free read rewrites a name the enclosing namespace block (or a same-name sibling block's export) declares to its qualified path.
